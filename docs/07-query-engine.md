# 07. Query Engine

## 1. Language: `zuQL` = Cypher-flavored, GQL-conformant

- Surface: openCypher-compatible core (MATCH/WHERE/RETURN/WITH/UNWIND/ CREATE/SET/DELETE/MERGE/OPTIONAL MATCH), plus GQL constructs: `FILTER`, `LET`, `FOR` with `WITH ORDINALITY` and `WITH OFFSET`, match modes (`REPEATABLE ELEMENTS` / `DIFFERENT EDGES` [default]), path modes (`WALK|TRAIL|SIMPLE|ACYCLIC`), selectors (`ALL|ANY|ANY k|ANY SHORTEST|ALL SHORTEST|SHORTEST k|SHORTEST k GROUP`), `NEXT` statement chaining. Checklist = Neo4j's GQL-conformance appendix; goal: mandatory-GQL conformant by v1.0 (declared per standard §24.2, Ultipa precedent).
- Statement composition: a query is the four levels GQL builds one out of (ISO 12.1 through 12.4) rather than one list of clauses, being a composite query statement, a linear query statement, the simple statements that chains with `NEXT`, and the result statement each of those ends with. What `NEXT` hands the statement behind it is the result the one in front of it returned and nothing else it had in hand, so a variable the first statement matched is out of scope past the chain. Writing it costs nothing: a chain plans as one pipeline, the same operators the same question written with `WITH` plans, so the composition is a way of writing a query rather than a slower query. The set operators join at the composite level: `UNION`, `EXCEPT` and `INTERSECT`, each in the ALL form that keeps every copy and the DISTINCT form that keeps one, with DISTINCT being what leaving the quantifier out means. Every conjunction sits at that one level and the fold is to the left, so unlike SQL there is no precedence between `UNION` and `INTERSECT` and a reader who wants one writes the operands in the order they should meet. `OTHERWISE` joins there too and is not a set operator at all: it answers the left operand, and the right one only when the left answered no rows. The operands are bound and planned apart, sharing nothing but the column names they have to agree on and the positional parameter list, which is why a name one of them binds is not a name the other can read, and neither may write, since how many times a write ran would otherwise depend on which operand the optimizer chose to hold.
- `FILTER` and `LET` (ISO 14.6 and 14.7): the two statements of a linear query that say what the rows in hand are rather than what to find. A `FILTER` is a condition with no pattern under it, so it reads what the statement already has, including what a `NEXT` handed it, and its `WHERE` is the standard's own optional word. A `LET` names values and drops nothing, which is the difference between it and a `WITH`, and the definitions read left to right so a later one may use a name an earlier one in the same statement gave. Neither costs an operator: a filter binds to a required match with an empty pattern list, which is the shape a queued predicate already had, and a let binds to a projection carrying the scope plus the new names, where a carried name is the slot it already was and not a copy. A definition that reads a name the same `LET` made starts a second projection, since one projection evaluates every item against the row it was given, so `LET a = x, b = a + 1` is two stages and the common `LET a = x, b = y` stays one operator.
- `FOR` (ISO 14.8): one row per element of a list, which is the one way a linear statement makes rows out of a value rather than out of the graph. `UNWIND` is the same statement under the Cypher spelling and stays, so a query written either way plans the same operator. `WITH ORDINALITY i` numbers the rows from one and `WITH OFFSET i` from zero, and the number is the position of the element in the list, so a `FOR` standing under a match starts again at each row that reaches it. The counter is a second column of the same operator rather than a stage after it, which is why it costs nothing: the operator already writes the value column of the chunk, and the counter is written beside it in the same pass. `WITH` is a clause as well as the first word of a counter, so the parser reads two words before it takes either, and `FOR x IN xs WITH x AS y` is the projection it looks like. The source may be a binding table as well as a list, ISO 14.8's second reading of it: a table is a sequence of rows the way a list is a sequence of elements, so the rows are what the statement runs over and each of them arrives as a record over the table's columns. Nothing else about the statement moves with it, so the counter numbers the rows of the table exactly as it numbers the elements of a list, and the only way to get at a value in one is the field read a record already answers.
- Grouping (ISO 16.15): a projection holding an aggregate groups by the items that are not aggregates, which is the Cypher rule, and `GROUP BY` says that same grouping out loud. The two have to agree: an item that is neither a key nor an aggregate has no one value in a group, and a key the projection does not carry would group the rows and leave no column saying which group each one is, so both are refused by name. A grouping with nothing to aggregate answers one row per group, which is what DISTINCT over the keys is, so it compiles to that rather than to a second kind of operator.
- A scalar function over a set function (ISO 20.9 with 16.15, features GF10 and GF12): `RETURN CARDINALITY(COLLECT_LIST(v.n))` is two things that run at two times, the list being accumulated over the rows of the group and the count being taken of what came out, and one clause cannot be both an accumulator reading a row at a time and a projection reading a group at a time. So the clause becomes two. The binder lifts every set function under such an item into a column of a grouping, leaves a name where each call stood, and puts what is left of the expression in a projection standing behind that grouping, which is the same hoist a sort key gets and for the same reason. A key and a set function written on its own are columns of the grouping already, so what stands behind reads them by slot and costs nothing, and a call the projection already carries is reused rather than accumulated twice, so `RETURN sum(n) AS s, sum(n) + 1 AS t` pays for one accumulator. Nothing happens to a projection where no item reads a set function without being one, which is nearly every projection there is, and then the clause stays the one clause it was written as. What is left out is a sort key holding a set function beside such an item, which would be a value the grouping answers and the projection behind it sorts by, and it is refused by name. The vector engine takes the grouping and hands the pair back, since the stage it runs above a grouping emits columns of the tuple the sink holds rather than working anything out of them.
- Sort keys over a grouping (ISO 14.9 with 16.15): a sort key is an expression, so a set function may stand in one, and `RETURN t ORDER BY count(*) DESC` orders the groups by their size without carrying the count as a column. The key is read once per group, so the clause is a grouping even where no item is one, and a key reading a name the grouping does not fix is refused for the same reason such an item is. What the binder does with it is take the aggregates out of the key and leave a name in each one's place: a set function the projection already carries becomes that column, so `RETURN t, count(*) AS n ORDER BY count(*)` accumulates once and reads twice, and one no column carries gets a slot of its own that the grouping fills and nothing but the sort reads. That is why the arithmetic around it works, `ORDER BY count(*) * -1` being a multiplication over the value the group answered, and why `ORDER BY size(collect_list(x))` sorts: the key runs after the grouping closes rather than being one of the columns the grouping answers. The listing names the hidden one where it is filled and where it is read, so `Aggregate count(*) AS #1 BY t` stands under `Sort #1 DESC`.
- Paging (ISO 14.9): `OFFSET` is the standard's word for the clause Cypher spells `SKIP`, and the two are one clause here, so writing both is refused rather than skipping twice. A page belongs to the primitive result statement it is written in, which is why a conjoin can only stand at the plan root and why a window taken before a `NEXT` is what the statement after it reads. An `ORDER BY` under a `LIMIT` of k runs as a bounded buffer per worker, so the ordered page builds k rows rather than the whole fan.
- Existence blocks: `EXISTS { MATCH (a)-[:KNOWS]->(b) WHERE b.id > 10 }` is a match written where a predicate goes, and `NOT` in front of it is the same match asked the other way round. The block sees the scope around it, which is what ties it to the row being tested, and the names it writes itself end with it, since it says whether a match was there and hands back nothing to read. It may be a whole conjunct of a WHERE, where it is a match of its own that runs after the clause it was written in, or it may stand under an OR, where it is being asked for a boolean and becomes a mark: the same match with the answer written into a column the predicate around it reads, so the row survives either way and the OR decides it. A block anywhere else, a projection or the WHERE of an OPTIONAL MATCH, is refused, since there is no row of the pattern left for the mark to be about.
- `YIELD` (ISO 16.14): which of the variables a match wrote leave it, and what they are called after it, so it takes names away where a `LET` adds them and renames them where a `WITH` would have to be written out to do the same. It narrows the columns and leaves the rows alone, so a yield answers the rows the match answered and is not a grouping. The items are variables rather than expressions, so a name the match did not write is refused by name, and so are two items ending under one name. It needs no operator of its own: the clause binds to the projection a `WITH` of the same names binds to, and projecting a plain variable keeps the slot it was already in, so what the yield carries is what the match matched rather than a copy of it.
- Inline procedure calls (ISO 13.2, features GP01, GP02 and GP03): `CALL { MATCH (a)-[:KNOWS]->(f) RETURN f AS friend }` is a whole statement written inside another one, and it runs once for each row that reaches it. What it returns is added to the row rather than put in place of it, which is the difference between a call and a `WITH`: the names the statement already carried are still there to be read after the call, beside the ones the block let out. A block that answers no rows for a row takes that row away, the way a match written beside it would have, since a call written without `OPTIONAL` is not optional; a block that answers several multiplies the row by that many. The parenthesized scope clause says what the block may read of the row it runs for, `CALL (a) { ... }` letting it read the one name and `CALL () { ... }` letting it read nothing, so a block with an empty scope answers the same thing every time and the call is the cross product. Leaving the parentheses out is the implicit scope, where the block may read everything the row carries. A `RETURN *` inside a block is what the block itself bound and not what it was handed, because a name the row already carries cannot arrive on it twice, and for the same reason a block letting out a name that is already in scope is refused with a message asking for an `AS`. `OPTIONAL CALL (p) { MATCH (p)-[:WORKS_AT]->(c) RETURN c.name AS company }` is GP03 the other way round: the word says the row survives the block answering nothing, and every name the block lets out is null on that row, which is what the same word says in front of a match. What it compiles to is that match, bound as one bracketed group so that the block matches whole or not at all, and the block's names are the group's slots, so a call that lets out an element it bound costs nothing at all: the name is the slot the group left null and there is nothing of the block left after the binder. A call that lets out anything else is where the word earns its keep, because `RETURN 1 AS n` has no graph in it and would be the number on every row, so each such item is asked for under whether the block matched and is null where it did not. What says the block matched is a slot the block bound itself, which means a block written out of nothing but the names it was handed leaves the row the same either way and is refused rather than answered wrongly, and so is a block written out of anything but one match, a second clause behind the match reading names the match may not have bound. The word is a match's too, so what tells the two clauses apart is the token behind it, and it is written in front of an inline call only: a procedure named in the catalog answers a table of its own rather than more of the row, and there is no row of the statement for the word to keep. The vector engine takes the call that lets out its own elements, that being the optional match it already runs, and hands back the one whose items are asked for under a case, having no kernel for one yet.
- What an inline call costs is nothing, which is the point of binding it rather than running it: the block's clauses are spliced into the statement around it at bind time, so a three level nest of blocks plans as the same operators the flattened text plans, asserted on the plan in `plan.rs`. A block is therefore not an optimization barrier, and a filter written inside one is a filter of the statement, free to be pushed down or taken into a walk like any other. The scope clause is settled entirely in the binder: narrowing the scope is a smaller name table for the block's clauses to bind against, and what the narrowing put away is noted so the row goes on carrying it underneath, which is what lets the nests read outward through each other. What leaves the block leaves as a projection only when it has to. Every escaping item that is a plain variable keeps the slot it already stands for and the name is written beside that slot, so a block letting out elements leaves no operator at all, and only an item that is an expression, `RETURN b.age + 1 AS older`, declares a slot and needs a projection to fill it. The statement forms a block cannot be spliced into are refused by name rather than silently flattened: a `USE`, a set operator, a `NEXT` chain, and a `RETURN` that says `DISTINCT` or carries a grouping, an order or a page, each of which would be a question about the whole block's rows rather than about the row the block ran for. A call the statement begins with runs for the unit row, so its body is taken out of the call and put in the chain around it instead of being spliced in, and none of those refusals reaches it, §9 below.
- Value query expressions (ISO 20.6): `VALUE { MATCH (p:Person) RETURN COUNT(*) }` is a whole query written where one value belongs, so it may chain with `NEXT`, join with a set operator, sort and cut, and it has to return one column because one value is what stands there. A query answering no row stands for a null and one answering several rows is refused. What it reads from the query around it decides what it costs. One that reads nothing answers the same value for every row, so it is a plan of its own run once before the plan that reads it starts, and what is left where it was written is a constant the run is handed, which is why the optimizer treats one the way it treats a parameter. That is the decorrelation. One that reads a name cannot be worked out once, because the value it stands for is the row's: the names it reads become captures, each a parameter position the executor fills from the row before running the subquery, and the subquery runs once per row. Such a statement answers with a `01000` warning beside its rows naming what the query inside read, because the rows are right and what is wrong with the statement is what it costs. `EXPLAIN` prints the subquery's plan under the plan that reads it, headed `VALUE {0} (once)` or `VALUE {0} (per row, reading p)`, so how often it runs is read off the listing rather than off the clock.
- Named procedure calls (ISO 13.1, feature GP04): `CALL pagerank('KNOWS') YIELD node, rank` names something the catalog holds rather than writing a statement out, and the ten graph algorithms are what the catalog holds. The name is a catalog object reference and is read the way a graph's name is read, so `CALL /wcc('KNOWS') YIELD node, component` says the same thing by path and `CALL AT / wcc('KNOWS') YIELD node, component` says it by schema. The two are never written together: whitespace is nothing to the lexer, so a path after a path reads as one longer path, and the parser settles which of them a token run is by looking at what follows it, splitting the last segment back off when the next token is the argument list. A name looked for in a schema that does not hold it is a reference refusal saying which schema was searched and what is in it, and a name that is in the root schema instead is told so by name, because the caller spelled the procedure right and looked in the wrong place.
- What a procedure takes and what it yields are the procedure's own, so they are rows of a catalog table rather than arms of a match in the binder. A row carries the schema, the name, the parameters and the one value column, and each parameter carries the words for it as well as its type, which is what lets a wrong argument count and a wrong argument type be refused in the sentence the row already holds: `sssp takes the rel table and a source node id` is generated from the row and not written out per procedure. The first argument is the rel table and has to be a string literal, since which table a call reads is settled while the statement is bound and not while it runs, and that table has to join one node table to itself, an algorithm over a graph being a thing about one kind of node. A parameter that names a column is checked on what was written rather than on what it works out to, for the same reason. The yield columns are checked against the row's own pair, `node` and the value column, so a call that asks for a column the procedure does not answer is refused before anything runs.
- Graphs and binding tables as arguments (ISO 13.1, features GP14 and GP15): the two things GQL has that a procedure takes and that are not values are a graph and a table of rows, and a call takes both. A graph is written in front of the arguments, `CALL wcc(/twin, 'knows') YIELD node, component`, and it says which graph the procedure reads, so the rel table named after it is looked for in that graph rather than in the one the statement is running against, and the call answers what running it inside that graph would have answered. Naming the graph the statement is already in is the call that named no graph, said out loud. A name defined as a graph works where a reference does, which is GP12 and GP15 written together, but a graph a query would answer is refused by name, because which rel table the call walks is settled while the statement is bound and a query has not run by then; the refusal says to write a graph reference instead. Nothing under the binder had to change for the cross-graph read: a rel table's id is a fact about the file and not about the graph, so the plan a call compiles to is the same plan either way, and what the binder gained is the other graphs' tables to look a name up in. A rel table the named graph does not hold is a reference refusal naming the graph that was searched.
- A binding table stands where a list of arguments stands, `CALL betweenness('knows', seeds) YIELD node, centrality`, which is GP14. That one is the other side of the same idea and it is settled at the other time: a list of sources is read when the call runs, so it may be anything a query answered, and `BINDING TABLE seeds = { MATCH (p:person) WHERE p.id < 2 RETURN p.id AS id }` answers the numbers writing them out by hand answers. The table has to be the one column the list would have been, since the sources are node ids and nothing says which of two columns holds them; a table of any other shape is a data exception saying how many columns it had, rather than a first column read as a sample nobody asked for.
- The `AT` schema clause (ISO 16.1, feature GP16): `AT /algo CALL pagerank('KNOWS') YIELD node, rank` says which schema of the catalog a name written without a path in it is resolved in, and it stands in front of the graph clause and the definitions because it is a fact about the whole statement rather than about one clause of it. What it reaches today is every procedure name a call inside the statement writes, that being every catalog name a query holds. A call that names a schema of its own is written against this one and wins, which is not a rule about precedence so much as what the two things are: a path says where a thing lives and the clause is only the default for a name that gave none. `AT CURRENT_SCHEMA` and `AT HOME_SCHEMA` both name the schema the session opened in, nothing moving a session out of one yet, so both are the statement that was going to be written anyway and are here for the client that builds the clause from a setting and needs something to put there when the setting says stay. The parser earns one wrinkle from the lexer knowing nothing about keywords: `AT / MATCH (p)` is the same tokens as `AT /MATCH (p)`, so a path segment is a name that does not open a clause, which makes the root what a clause word straight after the slash leaves behind and leaves a schema really called `MATCH` reachable in quotes. A clause written on a `CALL` body that is spliced into the statement around it is refused, since a spliced body resolves names where that statement does and a second answer to a settled question is worth saying out loud; a call the statement begins with is taken out of the call whole, so the clause its body carries becomes the clause of the query the statements land in.
- The binding variable definition block (ISO 13.3, features GP05 through GP13 and GP17): a statement may carry a head of definitions naming things no row carries, `VALUE cut = 35 MATCH (p:Person) WHERE p.age > cut RETURN COUNT(*) AS n`, and each one stands for a value, a binding table or a graph. What defines it is either an expression or a whole query in braces, and the two are one thing below the parser: an expression is turned into the query that returns it, so there is one shape for the executor to work out and one place for that to be wrong. What a definition compiles to is a parameter position. The query is bound on its own with no row in scope, the position is filled before the statement runs, and every reader of the name is a parameter read, which is why nothing under the binder has to know that a binding variable is different from a value the caller passed in and why a name read in a million rows is worked out once as a fact about the shape rather than as a promise about the executor. The definitions are worked out in the order they are written, so one may read the ones in front of it and not itself, and a name defined twice in one block is refused because the second would have nothing to say. Two things are refused that the standard leaves open. A definition may not read a row, since there is none yet, which is what makes `CALL (p) { VALUE mine = p.age ... }` a reference condition rather than a value that quietly turned out null. A definition may not write, because a statement is taken apart at its write and run in parts, each part filling the positions it reads, so a definition that wrote would write once per part; reading a graph twice answers the same thing and writing to it twice does not. What the kind decides is which of the two things the query gives up: a `BINDING TABLE` written with a nested query is its rows, that being the one place in the engine where a result becomes a value and being what GP10 is, and a `BINDING TABLE` written with an expression is whatever the expression already stands for, GP09, because a reference and a parameter both name a table that exists and collecting their rows would build a one row table holding a table. A definition whose kind is not `BINDING TABLE` has to answer one column, for the same reason a value query expression does, and one written with a type is checked against what the query answered by the same decision `IS TYPED` makes, so a type means one thing wherever it is written. That type is GP06, and the standard writes the separator in front of it two ways and allows it to be written with neither, so `VALUE t :: INT = 3`, `VALUE t TYPED INT = 3` and `VALUE t INT = 3` are one definition and the equals is what says the type is over. A block written inside a `CALL` body carries definitions of its own and they go out of scope with the block, which is the lexical half of GP17; what does not go is the value, since every definition in the statement, however deeply written, is worked out where every other one is. The vector engine declines a statement carrying definitions and the row engine takes it, for the reason it declines a value query expression: the definition is a query run before the plan starts and an engine that does not run one would read a position the caller left null, which is a wrong answer rather than a slow one. `USE g` naming a graph variable is GP11 through GP13 and works, with one thing settled first and one thing given up. What is settled first is which graph the statement runs against, that being what the names in it are bound against, so the clause is answered while the text is being read rather than where the other definitions are worked out: a graph variable a `USE` reads has to be defined as a graph reference, a word or a name or another graph variable or a parameter, and one defined by a query is refused by name rather than compiled against one graph and run against another. GP13's query form is read as a reference exactly as far as it is one: a body that is a bare `RETURN` of a graph reference, `PROPERTY GRAPH g = VALUE { RETURN CURRENT_PROPERTY_GRAPH }`, says which graph in its text and is read where a reference is read, and a body with a clause in it, a second statement, a grouping or a page answers what the rows say rather than what the text says and goes back to being refused. Which of the two a definition is is a fact about its shape and not about the engine's mood, so both sides of the line have a case. A bare name is a graph variable's before it is the catalog's, a definition being the nearer of the two, which is what lets one variable be defined as another and is the same lookup a procedure argument gets. The clause itself may be written behind the definitions as well as in front of them, and has to be: a clause naming a graph a definition above it defined can be written nowhere else, and ISO puts the graph clause on the statement rather than on the head the definitions are. What is given up is where a body naming a graph may stand. A spliced `CALL` body runs against the graph the statement around it does, so a body that named one is taken out of the call the way a body carrying a schema clause is, and its definitions come with it since the clause may read one; because zu runs one graph per query, the clause then governs the whole chain the statements land in, so a statement written behind such a call may only project what the call answered, and one that reads the graph is refused rather than read against a graph nobody wrote it for.
- Match statement blocks (ISO 14.4 and 19.4): a block may hold several match statements, each with a WHERE of its own, and they are all required and share the names they write, so a block is one conjunction and the same thing the commas of a single statement are. `EXISTS` takes one and asks whether it answered a row; `OPTIONAL { ... }` takes one and keeps what it answered, as one operand, so a block that matches half of itself matches none of it and every name it writes reads null. A degree read is how the pipeline answers a block over a bare pattern, and that shortcut is not available on a level some bracket walks, since the runner binds such a level to a null row while it runs what stands past the bracket, so those shapes go to the interpreter instead.
- The existence predicate's three shapes (ISO 19.4): a graph pattern, a block of match statements, and a whole query. The first two are one thing to the parser, a block being a pattern with more matches behind it, and either may stand in parentheses as well as in braces. The third is different in kind, and a `RETURN` at the top level of the brackets is what tells it apart, since a block answers the names its patterns wrote and a query answers the columns it returns. A query here reuses everything a value query has: it is filed beside the statement and reached by index, uncorrelated ones run once before the plan and correlated ones run per row with the names they read filled into parameter slots. What differs is the question, and it is one mark on the query rather than a second kind of plan: the run stops at the first row, so a predicate over a query that would match a million times costs the first match, the columns are never read, so it may return as many as it likes, and a query answering no row is false rather than the null a value query stands for. A query has a scope of its own, so a pattern in it writing a name the row around it already carries would be two elements under one word; that is refused, and the message points at the block form, where a pattern and the outer row are the same element. Correlation runs through the expressions instead, so `WHERE q.id = p.id` is how a query inside is tied to the row outside, and `EXPLAIN` heads its plan `EXISTS {0}` where a value query reads `VALUE {0}`.
- Character string expressions (ISO 20.22 to 20.24): `'ab' || UPPER(x)` joins two strings, and the operator sits between the comparisons and the additions the way the standard puts it, so `a || b = c` asks about the joined string and `'n=' || 1 + 2` joins the sum rather than joining the one and adding the two. Both sides are strings and nothing else: a plus over two numbers adds them and a plus over two strings would have to guess, so the two operators are written apart, and a query that meant the digits of a number says so with a `CAST`. The measuring and folding functions take one argument each. `CHAR_LENGTH` counts characters and `CHARACTER_LENGTH` is the same function spelled out; `OCTET_LENGTH` counts the bytes the store keeps, so the two agree on ASCII and part company on anything else, which is why both are here rather than one standing in for the other. `UPPER` and `LOWER` fold, and `TRIM` of one argument takes the spaces off both ends, the forms that name an end or a character being features of their own. Normalization is the sixth and it is written two ways: `NORMALIZE(x, NFKC)` answers the string in the form it names, defaulting to `NFC` the way the standard defaults it, and `x IS [NOT] NORMALIZED [NFD]` answers whether the string is in that form already. The form is a word and not a value, which is the arrangement `CAST` has, so the parser takes it before the binder sees a call and carries it on the function rather than in the arguments; that way no row can change which normalization runs. The predicate is answered by normalizing and comparing rather than by the quick check properties, because a quick check is a fourth table and a second algorithm to be wrong about, and the tables it does keep are generated from the Unicode data files checked in beside them and held to the Consortium's own `NormalizationTest.txt`. `IS NOT NORMALIZED` is a `NOT` around the same call, so a null argument needs no rule of its own. A null argument is a null answer, and a non-string argument is refused by name rather than measured by its spelling. Both of them are vector kernels, which the bullet on the normalization kernel below takes up, and the predicate is the one string function whose answer is a truth value rather than a value a column can hold.
- Byte string values (ISO 21.3, features GV35 to GV38 and GF07): a byte string is a sequence of octets and is written `X'00AB'`, two hexits to an octet in either case of letter, with whitespace inside the quotes ignored so a long one can be broken up. It is a type of its own and not a flag on a character string, and everything follows from that: `X'0041' = 'A'` is false rather than a decode, no cast crosses between them in either direction, since a cast that did would have to pick an encoding on the user's behalf and picking one is the whole of what such a cast would do, and `CHAR_LENGTH` refuses a byte string, a byte string having no characters to count. What the two share is the two functions ISO defines over both. `OCTET_LENGTH` counts octets and takes either, which is the same question it asks of a string, and the trim family takes either and answers the type it was handed, trimming octets rather than characters. The octet a trim takes when none is written is `X'00'` and not a space, a space being a character and a byte string having none, and `X'00'` being the octet a short fixed length byte string is padded out with. `TRIM` trims one octet and raises `22027` for more, exactly as it trims one character, and `BTRIM`, `LTRIM` and `RTRIM` take a set of octets. Ordering is by octet, because there is no collation over bytes that are not text, and a byte string sorts immediately after the character strings in the total order the engine keeps over mixed types. Equality is the octets and nothing is padded away first: IA016 leaves an engine free to call two byte strings differing only in trailing `X'00'` equal, and zu does not, a value whose last octet is nought being a different value from one without it and a query that meant to ignore it being able to trim. A stored byte string goes down the same blob side of the props store a character string does, the column's declared type being what tells the two apart on the way back out, so a byte string column costs what a string column of the same octets costs. Arrow hands it back as `DataType::Binary`, the C ABI as a pointer and a length through `zu_value_bytes`, and the CLI's JSON as the hexits in a string, JSON having no byte string and base64 being a second spelling of a value that already has one.
- Property reads (ISO 20.11): a property reference to a property the element does not have is null and not an error. It is the same answer an element that carries the property and holds nothing in it gives, which is the point: a query cannot tell a property nobody wrote from a property nobody stored, and `PROPERTY_EXISTS` is the one thing that can, since it reads the column list rather than a value. Edge properties already answered this way, so the change is nodes catching up to edges rather than a new rule. What it costs is the typo: `p.naem` is null for every row instead of a refusal, and what catches that back is a closed graph type, where the declared property list is a statement the query can be held to. The `id` of a table with no stored `id` column is still the row offset, which is the dense contract a load without `REORDER` keeps, so `id` is the one name that is never null.
- Edge patterns: the seven of ISO 18.9, `-[]->`, `<-[]-`, `<-[]->`, `~[]~`, `<~[]~`, `~[]~>` and `-[]-`, each with an abbreviated form that drops the bracket, so `->` is `-[]->` and `~` is `~[]~`. A dash asks for an edge that has a direction and a tilde for one that has none (GH02); whether it has one is a property of the rel table, so a pattern picks its tables by what it admits before it walks anything. An undirected edge is stored once and both adjacency indexes answer for it, which is why `~[]~` reads both lists and finds the edge from either end. `-[]-` admits either kind, either way round, which is what a query that does not care writes.
- Deliberate exclusions: no Gremlin, no LOAD CSV (use `COPY`), no dynamic labels in patterns (v1).
- Programmatic tier: prepared statements with typed params; Arrow RecordBatch results (`arrow` feature, zero-copy for fixed-width); `LOAD FROM 'x.parquet'/'x.csv'` table functions for ingestion/interop.
- Parser: hand-written recursive-descent (rationale: error quality, no build deps, fuzzable; grammar frozen in `docs/grammar.ebnf`).

## 2. Compilation pipeline

```
text → AST → bind (catalog, types) → logical plan (graph algebra)
     → rewrite (predicate pushdown, label pruning, pattern normalization)
     → join order (DP ≤ 12 rels, greedy beyond) + WCOJ injection
     → physical plan (pipelines) → morsel-parallel execution
```

Plans cached by (query text, catalog epoch, param types), LDBC short reads are parameterized point queries; plan cache is mandatory for T2 (< 1 ms includes zero planning on repeat).

## 3. Vectors & factorization (execution kernel)

- Vector size 2048; columnar `ValueVector`s with validity bitmaps and a selection vector; segments decode directly into vectors (or serve predicates compressed: zone-map skip, dict-code compare, constant short-circuit).
- **Factorized tuples** (Kùzu model): a `DataChunk` group = one flat prefix + unflat list vectors. Multi-hop m:n expansion emits `(src-flat, nbr-list)` without flattening; aggregations (`count`, `sum`, `collect`) and `DISTINCT` prefixes compute directly on factorized form; flatten happens lazily, only when an operator requires it (e.g., ORDER BY on leaf values).
- Morsel-driven scheduling: pipelines end in sinks (hash tables, sorts, results); morsels = node-group-aligned ranges (a morsel never spans groups, keeps segment decode, zone maps, and NUMA locality aligned).
- **Lanes.** A stored column reaches a kernel as one of a few physical lanes rather than as a tagged value: integers and doubles a word wide, strings as sixteen byte views into a shared buffer, and the temporal types as the count each of them is. A date is days since the epoch, a time and a datetime are nanoseconds, and a duration is months or nanoseconds depending on which kind it is, so all four ride the word an integer rides and compare, hash and group exactly the way one does. What the word means travels beside it as a tag on the column, not inside the cell, which is what lets a filter over a date be the same loop as a filter over a number and still hand back a date at the end. The zoned types have no lane: a zoned value is a count and an offset from UTC, which is two numbers, and a lane is one word, so a query over one stays with the row engine rather than answering an instant that prints somewhere else. An extreme or a total over a temporal column stays there too, since the accumulators hold words and answer numbers, and the smallest of a column of dates is a date. What a register carries besides its width is the lane, and only the temporal registers carry one, because an interval is a count of months or of nanoseconds and a timestamp is a reading of a clock or an instant since the epoch and nothing about the word says which. That is what lets an expression produce a temporal value rather than only read and compare one: two durations of a kind add and subtract in the arithmetic kernel, the words being counts of one unit, and the answer comes back a duration of the kind both sides were. Two of different kinds decline, which is what the two kinds exist to say, and so does a duration scaled by a number, and so does an instant shifted by a length of time, since a month has to land on a day that month has, a day-time shift has to keep the time of day it made, and the end of the calendar has to be an error rather than a wrap, and the arithmetic kernel has an op for none of those.

## 4. Operators

| Operator | Notes |

| Expand(CSR) | factorized neighbor expansion; direction fwd/bwd, resolved per rel table because an undirected one answers both ways (GH02); label/type mask; slack/tombstone aware; the pin is held per storage group rather than per source row, and when nothing above the expand reads the source level the neighbor lists concatenate across source rows so the pipeline below runs on full vectors; a membership filter over the level the walk builds is taken into the walk rather than left as the operator after it, so a neighbor no build key can match is dropped while it is still a value in a list and no row is ever made for it |

Filters written in the bracketed clause compile into the group, so they decide the match rather than the row. In the pipeline a block over a bare pattern is not a group at all: the question is the row's degree, so a semi or an anti is a filter and a mark is a column of the level the block was written on. Only the semi hands its keys sideways: what the filter says is that no key on the build side can match the row, and only under a semi is that the same as dropping it, since the anti keeps exactly those rows and the left join carries them on with a null bound to the group |

| FtsScan | BM25 seed (feature `fts`) |
| HashAggregate / Sort / TopN / Limit / Distinct | factorization-aware; an ORDER BY under a LIMIT of k runs as a bounded buffer per worker, which reads a row's sort keys, drops it against the k it already holds, and only materializes the row when it wins, so the ordered query builds k rows where the unordered one builds the whole fan |
| Conjoin | the one operator with two inputs: it meets the result tables of two operands of a composite query. `UNION ALL` streams both through and keeps nothing, `UNION DISTINCT` keeps one ordered table of what it has answered, and `EXCEPT` and `INTERSECT` hold the counts of one operand and stream the other past them, so the memory a set operator costs is the smaller operand and not both. Which one that is the optimizer decides from the row estimates and writes onto the plan, so EXPLAIN prints `build left` or `build right` and a plan-reading test can say the decision was made. `OTHERWISE` builds nothing: it runs the left operand, and the right one only when the left answered no rows |

**Edge identity.** A rel value is its table, its two endpoints, and the row its properties sit in, which is the edge's place in the load order. The row is on the value rather than derived from the endpoints when it is read, because a pair may run more than once and each copy carries its own values: on the generated finance graphs an account sends three hundred transfers to a hundred and fifty counterparties, so a sum over an amount read by endpoints alone is wrong by whatever the copies differ by. Two rel values are the same edge when the row agrees as well as the endpoints, which is also what tells the copies apart under a trail's no-repeated-edge rule. An operator that walks an adjacency list counts the rows out with it, forward and backward alike, and that is Expand and the variable-length hop. An operator that holds both endpoints asks `edge_run` instead, which answers with the row of the first copy and how many copies there are, and emits one row per copy: a pattern with both ends bound matches once per edge and not once per pair, so ExpandInto, the ASP probe and the intersection close agree with the expand pair they stand in for. Undirected is no exception and was the one place it used to be: a pattern that names no direction over a pair joined both ways matches through the forward edge and through the backward one, because those are two stored edges and not two readings of one, so the close answers both where it used to answer only the forward one. That is what the expand it stands in for counts, walking the out list and then the back one and keeping whatever each of them holds, and it is why a triangle whose every side is stored both ways round counts eight paths per ordering of its corners rather than one. The bitmap the close uses to test a whole vector of neighbors at once records that an edge exists and cannot record how many, so a probe side holding a neighbor twice takes the galloping walk instead, which counts. An edge with no stored row, one a write staged before its fold landed, carries `Value::NO_REL_ROW` and reads null.

**WCOJ policy** (Umbra/Free Join findings): binary ASPJoins by default; the optimizer marks a subplan for MultiwayIntersect iff the pattern is cyclic (triangle+) *or* estimated intermediate/output ratio exceeds a threshold (default 16×). Sorted CSR gives us the tries for free, no runtime trie build for pure-adjacency intersections (cheaper than Umbra's lazy hash tries).

## 5. Recursive & path queries

- `RecursiveBFS` implements variable-length and RPQ-style patterns as a frontier fixpoint: per-iteration dense/sparse frontier bitmaps over node groups; **hybrid morsel policy** (arXiv:2508.19379): few sources ⇒ frontier-partitioned morsels; many sources ⇒ multi-source morsels; switch at runtime by frontier statistics. The floor between the two is one full lane batch (64 sources), which is where the sweep in `crates/zu-query/benches/kernels.rs` puts it: a lane batch pays for three arrays the width of the graph however few lanes it carries, and below a full batch the single BFS side wins on a deep walk.
- Path semantics (GQL): default `DIFFERENT EDGES` (trail) with **shortest/ bounded-walk fast paths**; unbounded `WALK` requires a selector or explicit upper bound (avoids infinite path sets; standard-compliant). `SIMPLE/TRAIL` general cases use per-path filtering over PMR enumeration with documented exponential worst case (NP-hard territory; LMCS 2023).
- The four path modes differ only in the repeat they forbid: `WALK` forbids none, `TRAIL` a repeated edge, `ACYCLIC` a repeated node, and `SIMPLE` a repeated node except that the path may end where it began. The last two are not substitutes for one another, because a cycle is a simple path and not an acyclic one. In the enumeration a simple path is allowed one step back to the node it started at and is then finished, since every node ahead of it repeats either the start or something the path already holds.
- The seven path selectors say how many of the paths a pattern matches are kept per pair of endpoints, and they split into two searches. `ANY SHORTEST` and `ALL SHORTEST` keep the least length and nothing else, which the level pass answers without building a path that will be thrown away, and they are the two that make an unbounded `WALK` finite, since a path of least length repeats nothing. The other five read a length off a path the walk built: `ALL` keeps every path, so it lowers to no selector at all; `ANY k` keeps the first k the walk comes to per endpoint, which the standard leaves to the engine; `SHORTEST k` keeps k paths counted shortest first, so it may take some of the paths of one length and leave the rest; and `SHORTEST k GROUP` keeps every path whose length is one of the k least, so it cannot answer half of a length. The last two hold what they have per endpoint, by length, and throw the longest away as shorter ones arrive, which bounds what they hold by the answer rather than by the graph. `SHORTEST 1` is `ANY SHORTEST` and `SHORTEST 1 GROUP` is `ALL SHORTEST`, so the pairs run the same search.
- A match mode (ISO 16.9) says what a whole pattern list may bind twice, where a path mode says what one path of it may, so the two are separate words and separate types. `DIFFERENT EDGES` is what a list that names no mode means, and it settles two things at once: a pattern that named no path mode walks a `TRAIL`, and no edge answers two of the edge patterns of the list. `REPEATABLE ELEMENTS` lifts both, so a pattern under it walks and an unbounded one is refused for the same reason any unbounded `WALK` is. Both are written four ways, `EDGE` and `EDGES` and `BINDINGS` after either, and all four say one thing. The mode reaches a pattern list and not a match statement block: a block gathers the lists of several statements, and two patterns of one statement may not take the same edge where two of two statements may.
- The edges a `DIFFERENT EDGES` list keeps apart are the ones whose steps describe the same pair of ends, `MATCH (a)-[e]->(b), (a)-[f]->(b)`, which is where any graph at all can answer both patterns with one edge and where the query plainly means two. A step beside a variable-length one over the same ends is the same rule with the walk's edges as the list, `NOT (e IN es)`. Two steps that end somewhere else are not checked yet, and that is a gap rather than a reading of the standard: `(a)-[e]->(b)-[f]->(c)` answers both with one edge when the graph holds a loop at a node and all three ends land on it. Testing that pair costs a comparison on every two hop walk of every query, and it rules out a shape that no graph without a loop holds, so it waits on the engine knowing which tables hold a loop and which hold parallel edges; then the test is planted where a graph can break the rule and dropped where none can. Two variable-length steps over the same ends are the third gap, there being no test between two lists of edges to plant. The one pair of that shape the engine does test is two copies of a repeated stretch, below, where the two steps are one step the query wrote once.
- `KEEP` (ISO 16.9) says the prefix once behind the whole pattern list, `MATCH (a)-[:KNOWS]->+(b), (a)-[:KNOWS]->+(c) KEEP ANY SHORTEST`, which is the same query as the one that writes the prefix in front of each pattern and answers the same rows. It reaches every pattern of the list rather than the one it stands behind, and it carries a selector or a mode or both, since the clause holds a whole path pattern prefix. What it says fills in what a pattern left out rather than overruling what one wrote, so a pattern naming a mode and a `KEEP` naming another is refused by name, and so is a `KEEP` with nothing after it, both being a query whose reader would have to guess which of two prefixes ran. That is why a pattern remembers whether it wrote a mode at all instead of only which mode it walks under: a pattern that wrote `TRAIL` and one that wrote nothing walk the same way, and the `KEEP` is the one place the difference is asked about.
- Brackets around part of a pattern (ISO 16.11) match nothing of their own, so a pattern reads the same walk with them and without them, and what they are for is that three things can then be said about a stretch of it rather than about the whole. A name inside them binds a path over that stretch, so a two hop pattern whose second hop is bracketed answers a path of one hop beside the path of two. A path mode inside them speaks about the steps they hold, the tightest pair of brackets around a step being the ones that speak about it, so an outer walk may hold an inner trail. A `WHERE` inside them is a condition on the stretch, and since it may read a variable the pattern bound outside the brackets it is the non local predicate. The parser flattens all of this: a bracketed stretch is a pair of node positions on the one line of steps the binder already reads, which is why nothing downstream of the parser knows the brackets were written.
- A quantifier behind those brackets (ISO 16.11, feature G035) repeats the stretch they hold, and a fixed count is written out rather than searched for: `((x)-[:LINK]->(y)){2}` is spliced into the one line of steps as the two steps it stands for, so the binder, the plan, the optimizer and the executor see the pattern a reader would have written by hand and nothing along that line needs a case for it. A count of several lengths is written out the same way and run over the fork seam the bar below runs on, since a stretch repeated between one and three times matches paths of three lengths, which is a pattern per length rather than one pattern: the parser reads the term once per length, or once per combination where a term holds more than one such stretch, and hands the clause the walks the way an alternation hands it the alternatives. The question mark of feature G037 is the range of nought or one written as a word, so `((x)-[:LINK]->(y))?` is the stretch walked and the stretch skipped, and skipping it leaves the nodes at its ends standing on the one node, which is what a factor holding nothing does anyway. A count with no ceiling on it, `+` or `*` or `{2,}`, is refused by name, since the lengths are walked as patterns of their own and there is no writing out a list with no end to it. Reading a term twice is safe because nothing but the position moves while one is read, and it is the shortest way to say this: how many nodes a stretch contributes decides where every position behind it lands, so a term of several lengths cannot be built once and patched.
- What the repetition does to the names inside the brackets is the rest of the feature. Every repetition binds them again, so a name written there stands for one element per repetition rather than for one element, and that is the group variable of GQ17. It is not a slot of its own: the parser records the positions the name was bound at, the binder turns those positions into the slots the walk already fills, and reading the name builds the list out of the row in hand, so a query that never reads a group pays nothing for having one. Reading a property of a group reads it off every member, and an aggregate written around one folds that row's bindings rather than the rows, which is the horizontal aggregate of GE09: one row in and one row out, nothing grouping under it, and the same accumulator the grouped aggregates use, so a null member is dropped the way a null row is. The fold reads the members out of the slots the walk filled rather than out of a list built to be walked, which is what `bench/fold.rs` prices: over fifty thousand walks of eight repetitions, the fold costs 0.7 of what reading the same group as a list costs and holds a scalar per row where the list holds twenty megabytes, and the ratio is gated because it is the number that moves the moment the fold starts building what it folds.
- The copies of a repeated stretch are kept apart from one another, which is the one pair of steps ending somewhere else that the edge distinctness above does test. The engine knows the copies are one step the query wrote once rather than two steps that happen to look alike, so the pair is worth a comparison, and it is paid only by a query that wrote a quantifier. Without it `((x)-[:LINK]->(y)){2}` would take a loop edge twice where `-[:LINK]->{2,2}` does not, and the two spellings ask the same question. The test goes away under `WALK`, whether the pattern said so or the `REPEATABLE ELEMENTS` match mode did.
- A bar between two paths (ISO 16.7, features G032 and G030) says either of them may be matched, and it is run as a seam rather than as an operator: the clauses in front of it end in a projection of what is in scope, each alternative is a plan of its own over those rows, and the rows they answer are put end to end for the clauses after it to read. That is the same shape a write runs in and it is used for the same reason. The alternatives walk differently, so each of them binds slots of its own and the row between the parts is where they meet; a single slot narrowed by two alternatives would be narrowed to the tables they agree on, when what the name may hold is the tables either of them says. The bar binds inside one path pattern and the comma binds between two of them, so `A | B, C` is the two pattern lists `A, C` and `B, C`, and the parser writes the alternation out that way rather than leaving a choice in the plan. Sixty-four lists is the ceiling, above which the query is refused and pointed at `UNION`, since the product of the alternatives across a long comma list is a walk count no reader wrote.
- What separates the two bars is the counting. `|+|` is multiset alternation and puts the rows end to end as they come, while `|` is path pattern union and answers a path both alternatives found once. What tells two paths apart is the elements the walk went through and not the names it bound, so each alternative projects its own elements, anonymous ones included, behind the row it answers, the fork takes the rows that are new by the whole of that, and the tail is dropped once the question is settled. `(a)-[:KNOWS]->(b) | (a)-[]->(b)` therefore answers the `KNOWS` edge once and every other edge once, where the same query with `|+|` answers the `KNOWS` edge twice. Three shapes are refused by name in an alternation rather than answered: an `OPTIONAL MATCH`, which would have a row of nulls per alternative; a path variable, which is assembled out of the slots of the walk that bound it; and an existence block, which is a match of its own that would be lifted once per alternative. So is an alternative that binds a name another does not, since the clauses after the fork read one row whichever alternative answered it. A group variable is the one thing an alternative may bind and the clauses behind it may not read: the alternatives walk different numbers of steps, so the elements the name stands for are in a different place in each of them, while the row between the parts holds one column per name. Binding it costs nothing, so it is the reading of the name that is refused and the walk stands, which is what lets `((x)-[:LINK]->(y))?` answer a query that never reads the `x`.
- A factor written straight against another with no edge pattern between them is ISO's juxtaposition, and the node the left one ends at is the node the right one starts at rather than a second node beside it, so `(a:Step)((x:Step)-[:LINK]->(y:Step))(b:Step)` walks one edge through two nodes. The two node patterns that meet there describe one node, so their labels are joined with an `AND` and their properties gather, and two different names written there are two names for one node: one of them is the pattern's and the rest are aliases the binder points at the same slot, so either name reads the element for the rest of the query. A name that already stands for something else is refused rather than joined to it, which is the one shape of juxtaposition this does not answer: `MATCH (z)-[]->(a), (b)((a)-[]->(c))` means the node `b` is the node `a`, and saying so needs an equality between two slots rather than a second name for one.
- A simplified path pattern (ISO 16.12, features G039 and G080 through G082) writes a stretch of edges between one pair of slashes and lets the nodes between them go unwritten, so `-/ knows knows /->` is the pattern `-[:knows]->()-[:knows]->` spelled out in less. The parser lowers it to those ordinary steps and anonymous nodes before anything downstream sees it, exactly as it lowers a quantifier, so there is no simplified pattern in the AST, the binder or the plan. The arrow around the slashes is the same seven directions an ordinary arrow writes and defaults every step of the stretch, and a step overrides it by writing `<` in front of its type or `>` behind it, which is why the direction a step carries is an option while it is being read and only becomes a direction once the arrow is known. Inside the slashes a type is a step, two written against each other are two steps meeting at a node nobody named, a bar is the one step either type answers and lowers to the type union an ordinary step already carries, brackets group, and a quantifier repeats what stands in front of it. A count over a single step whose floor is one or more is the hop range the arrow writes anyway, so `-/ knows+ /->` is one operator and not a fork; every other count is written out the way a quantifier behind brackets is, so `-/ knows? /->` is the two lengths and runs over the fork seam, and a count with no ceiling over more than one step is refused for the reason any unbounded stretch of several lengths is.
- What ISO writes for label expressions inside those slashes that this engine has no store for is refused by name rather than answered wrongly. An edge here is kept under exactly one type, so a negated type, the wildcard and a conjunction have no reading, and the message says that and says what to write instead. A bar separating stretches of more than one step is refused too: that is an alternation of paths and not of labels, and the bar between whole patterns above already says it, with the fork to run it.
- A condition written inside an element pattern (ISO 16.6, feature G041) is asked of the one element that pattern stands on, at the point the pattern reaches it, so a node it refuses is never expanded from and an edge it refuses is never followed. A node writes it after its labels and its property map and an edge writes it inside the brackets, and both may read the names the pattern bound to their left, which is what makes them non local: `(a)-[:LINK]->(b WHERE b.step > a.step)` compares the node the walk reached with the node it came from. It lowers to a filter planted where the slot appears, carrying the same bracket the operators around it carry, which is what makes it different from the same text written behind the pattern: under an `OPTIONAL MATCH` it gates the match within the group rather than dropping the group's null row. Two conditions where two stretches of a pattern meet are both asked of the node they meet at, since the two node patterns there describe one node. One inside a repeated stretch is refused, because the name inside the brackets stands for the group rather than for the repetition's element, and one inside an inserted pattern is refused, an `INSERT` describing an element to make rather than one to find.
- A lower bound above one hop and a shortest selector are a fair question together, `ALL SHORTEST (a)-[:KNOWS]->{2,}(b)` being the shortest of the paths that are long enough, and it goes to the walk rather than the level pass: a level is the distance from the start, and the least length of at least two hops is not one.
- A `WHERE` written inside a relationship bracket, `-[t:transfer*1..3 WHERE t.ts >= $lo]->`, is asked of every edge the step stands on before it walks it, so an edge that fails it is never followed and no longer path is built through it either. The pattern variable means one edge inside that predicate and the list of edges everywhere else, which is why the binder gives the predicate an edge slot of its own and points the name at it only while the predicate is being bound. A fixed-length step has nothing downstream to prune, so its predicate lowers to an ordinary filter above the expand; a variable-length step carries it inside the operator, where the same gate covers the hop enumeration, the level pass and the meeting search. This is what the finbench `tcr*` queries need, since their windows sit on the transfers rather than on the accounts.
- A path variable binds the walk as a path value and not as the list of the same elements, which is what makes `p IS TYPED PATH` true about it and `p IS TYPED LIST<ANY>` false. `PATH [a, e, b]` builds one out of elements and refuses a sequence that describes a walk nobody can take, `PATH_LENGTH` counts its edges where `SIZE` counts its elements, and two paths over the same elements compare equal. `ELEMENTS(p)` answers the nodes and edges as a list, in the order the walk took them, and it is the one way to read what a path holds, since a path is a value of its own and nothing indexes into one. It is refused on a list, which is already the list of its elements, so a query that lost its path on the way in fails rather than answering about the wrong value.
- The builtin functions of ISO 20 are one table (`crates/zu-query/src/functions.rs`). A row says what the function is called, what other spellings reach it, how many arguments it takes and of what kind, what its answer's type is, whether it folds a group or answers a row, whether the same arguments always give the same answer, and, for a scalar, the kernel that answers it. The binder resolves the name a statement wrote against that table and checks the call against the signature it found, so a refusal reads in the function's own words and a plan names the function the way the statement did. Adding a function is a row here rather than a name written into a match in the binder, another in the printer and a third in the evaluator. What the binder settles it settles once: the number of the row that answers the call is on the bound call, and a row reads the kernel at that number and calls through the pointer rather than deciding again which function it is looking at, so a call costs the same however many functions the table grows to hold. A call every one of whose arguments is a literal does not reach a row at all, since a deterministic kernel answers the same thing every time, so it is answered while binding and the plan carries the answer; a kernel that refuses those arguments is left alone instead, because the condition it raises belongs to the row that asked for it and a statement that never reaches that row never raises it.
- The numeric library (ISO 20.22, features GF01 to GF03) is twenty one rows of that table: `ABS`, `CEIL` with `CEILING` as its long spelling, `FLOOR`, `ROUND`, `SIGN`, `MOD`, `SQRT`, `POWER`, `EXP`, `LN`, `LOG`, `LOG10`, the six trigonometric functions with `COT` among them, the three inverse ones, and `DEGREES` and `RADIANS`. The exact half keeps an exact argument exact: an integer through `ABS`, `CEIL`, `FLOOR`, `ROUND` and `MOD` answers an integer, because the answer of each of those over a whole number is a whole number and a float would lose the digits above two to the fifty third. `ROUND` takes the digits to round to as a second argument, a negative count rounding tens and hundreds, and rounds a half away from nought rather than to the nearest even, all of it in the integers where the argument was one. The rest answer floats whatever arrived, since the answer of a root, a logarithm or an angle is irrational for all but a handful of arguments and a type that changed with the value would be a type nothing could be planned against. Where a function has no answer the kernel raises the condition the standard names and never hands back a NaN: `2201E` for a logarithm of a number that is not above nought or in a base that is not above nought or is one, `2201F` for nought raised to a negative power, for a negative raised to a fraction and for the square root of a negative, which ISO defines as the power of one half, `22012` for a remainder by nought and for a cotangent where the sine is nought, and `22003` for an inverse sine or cosine outside minus one to one and for an answer that left the range a float holds. A NaN would travel through every comparison below it as false, so a statement that got one would have been told nothing about what went wrong. An argument that was already infinite is left to IEEE 754 and travels, because what these conditions are about is a statement that asked for a number nobody has. All eighteen of the functions of one argument are vector kernels, so `abs(a.x - b.x) < 3` is answered a chunk at a time rather than taking the whole scan back to the row engine for the sake of one call. The kernel decides the condition before it fills anything, which is what keeps the loop that computes the answers free of branches: the exact half folds the column to the widest value it holds, and the approximate half folds it to the lowest and the highest, since every one of those conditions is about where the argument sits, below nought for a root, at or below it for a logarithm, outside minus one to one for an inverse sine, and far enough out for an exponential or a reading in degrees to leave the range a double holds. Only a fold that cannot rule a condition out is walked row by row, so an ordinary chunk pays one pass over the column and then one instruction per row. One instruction per row is a claim about the loop and not only about the fold in front of it, so which function runs is settled before the loop starts rather than matched inside it, the way the compare kernel has always settled which comparison runs. A match left standing in a compute loop is a branch the vectorizer will not lift, and the bench measured it at about seven times the price of the same loop with the function already chosen, which is the whole of the difference between a fold that costs a fifth of the answers it guards and one that appeared to cost seven times them. Two entries in `bench/budgets.toml` hold that down: `vec_guard_x` is a ceiling on what the fold and the walk together cost against a bare unguarded add, measured back to back in the one process because the ratio survives a loaded host where the rates do not, and `vec_condition_walk_x` is a floor on what the walk costs against the fold that skips it, which falls to about one the moment somebody moves a check back inside the loop and so catches the regression from the other side. The cotangent is the one no fold rules out, its condition being about the sine of the argument rather than the argument, so it is walked whatever the column holds. What can raise is also what the compiler asks about when it puts a call behind an `OR`, since the row engine never evaluates the second half of a condition the first half settled, and nine of the eighteen cannot raise at all. The two argument three, `POWER`, `LOG` and `MOD` under its function spelling, are kernels as well, and they read their conditions the other way round. A power and a logarithm cost tens of instructions a row, so working them out twice to decide whether the first time was allowed would double the price of the ordinary chunk; instead the answers are filled first and the conditions are read off them, since an answer that left the range is an infinity sitting in the output and finding one is a pass over the numbers the loop just wrote. What a fold over one column still settles is settled that way: a remainder needs a divisor that is neither nought nor minus one, a logarithm needs a base above nought that is not one, and a power that stayed finite has no condition left but the two the standard names about the pair. `MOD` is a kernel of its own rather than the modulus operator it shares its arithmetic with, because the two read their conditions from opposite ends, the function off the answers it has already written and the operator off a fold over its operands, and the words they use for the one condition they share are not the same words either, though the code is: a remainder that does not fit is `22003` from both, called an integer overflow by the operator and named with the pair it had no answer for by the function. Both arguments hold the one physical type by the time the kernel sees them, a whole number the statement wrote beside an approximate column having been widened by the compiler, so a query that mixes the two is a wider loop rather than a branch inside a narrow one.
- The length functions (ISO 20.9, feature GF04) are `CHAR_LENGTH` with `CHARACTER_LENGTH` as its long spelling, and `OCTET_LENGTH`. They are the first of the string library to be vector kernels, and they are first because of what a string function asks that a numeric one never does. Every numeric kernel writes its answer into a register the width of the register it read, so the only question it had was whether a row has an answer at all. A function that answers a string has to say where the answer's bytes are going to live, and the arena that holds a chunk is sized for the columns the scan produced rather than for whatever a call might make of them. A count is a whole number, so these two answer an ordinary integer vector and put nothing in the arena but numbers, which is what lets them settle the other half of the story before the harder half arrives. That other half is the encodings. A column of strings reaches a kernel three ways, as flat views, as one constant standing for the whole chunk, or as dictionary codes over a shared table of entries, and the numeric kernels refuse the third outright and ask the caller to materialize the column first. Here it is the cheapest of the three, since the length of a code is the length of the entry it points at, so a chunk is a measurement of each table entry and then a gather over the answers rather than a measurement of each row, and the narrower the table the wider the gap. A constant is measured once and the answer filled across. Only the flat encoding pays a measurement a row, and only half of it does: a view carries its byte count in its own header, so `OCTET_LENGTH` over a flat column reads headers and never touches a payload, where `CHAR_LENGTH` has to look at the bytes. The character count is written as a fold rather than a decode, a byte beginning a character exactly when it is not a continuation of the one before it, which is one comparison a byte and nothing the compiler cannot lay out flat. Neither can raise, every string having a length and no column holding enough of anything to trouble an integer, so unlike the numeric kernels there is no pass over the column to decide whether the loop may run, and a length is one of the calls the compiler will put in a projection or behind an `OR` where a root or a logarithm still goes back to the row engine. A null argument answers null and not nought, which is the one thing a count must not quietly get wrong, nought being the length of the empty string and saying something else entirely.
- The two folds (ISO 20.9, feature GF04) are `UPPER` and `LOWER`, and both are the ASCII fold: a letter of the English alphabet changes case and every other byte is left as it stands, which is the fold the standard's default collation asks for and the one that needs no table. A character outside ASCII keeps whatever case it arrived in rather than being folded by a rule zu has not written down, and that is the one place these two answer something another engine might not. They are vector kernels, and what makes them the string library's easy pair is that an ASCII fold never changes a byte's width. The answer is exactly as long as the argument, an answer that sat inside its view still sits inside one, and a chunk's worth of answers needs no more room than the chunk it was made from, so the buffer they write into is sized once and right the first time. That buffer is the thing the lengths never needed. A kernel whose answer is a number writes into a register the arena has already sized; a kernel whose answer is a string has to put the bytes somewhere, and how many bytes a chunk of answers comes to is not known until they are made. So there is a builder: one allocation for the whole chunk, answers of twelve bytes or fewer carried inside their own views and never reaching it at all, and views that hold offsets rather than pointers so the buffer may grow underneath them. The encodings decide how much folding happens rather than what the answer is. A constant folds once. Codes over a dictionary fold the table rather than the rows, so an entry's bytes are written into the answer once however many rows point at them and the rows themselves are a gather of views, which is why the coded column measures about twice the flat one on the bench. Only a flat argument folds a string per row. The answers are flat views whichever way the argument arrived, because a computed column is read back by row and a computed string column is read back exactly the way a stored one is. Neither fold can raise, so both stand in a projection, in a group key and behind an `OR`. What a fold did expose is that two string columns compared row against row had no kernel at all: every string comparison the engine had was against a constant, either through the dictionary or against the views, so `n.name = n.tag` and `upper(n.name) = n.name` alike reached a kernel that refused them. That arm is written now, equality still rejecting most pairs on the length and the four byte prefix a view carries before either side's payload is touched.
- The trim family (ISO 20.24, features GF05 and GF06) is six rows of the same table and one kernel behind all of them, since the whole of what tells them apart is which ends are trimmed and how many characters may be. `TRIM` takes one character, and the explicit form names the end it comes off: `TRIM(LEADING 'x' FROM s)`, `TRIM(TRAILING 'x' FROM s)`, `TRIM(BOTH 'x' FROM s)`, with either operand omissible, so `TRIM(s)` is the plain question and takes spaces off both ends. It is parsed the way `NORMALIZE` is rather than resolved as a call, because an end of a string is a word the statement wrote and not a value a row holds, and because `FROM` is not a separator a call has; the three words stay ordinary names everywhere else, so `TRIM(leading)` reads the variable a query bound. A trim character of more than one character raises `22027`, which is the condition the standard names and the reason the multi-character functions exist at all: `BTRIM`, `LTRIM` and `RTRIM` take a set of characters instead and trim any of them, in any order and however often they appear. The set and the character both default to a space, a set nobody wrote trims nothing, and a null on either side answers null. What the two ends of `Trim` mean is decided in the registry rather than in the parser, so the explicit form and the named functions land on the same three lines of code and a plan prints whichever function the statement reached. The six are one vector kernel as well as one row kernel, and the kernel knows three of the six rather than all of them, because the two questions that separate the rest are about what a statement wrote rather than about what a row holds: a trim set that is not written out sends the query back to the row engine, since a set that is a column would be a different set every row and the kernel prepares one for the chunk, and a `TRIM` handed more than a single character goes back as well, so the `22027` is raised in one place and worded once. What is left is which ends to walk. The kernel is the one in the string library that fills no buffer at all: what a trim answers is a part of what it was handed, and a part of a string is bytes that are already in a buffer somebody is holding, so a flat or constant argument's answers are views back into the argument's own bytes and the answer vector holds the same buffers rather than a copy of them. A dictionary is the one shape that cannot do that, an entry of a table not being bytes a view can name, so a coded column trims its table once and the rows gather over the answers. Matching is bytes rather than characters, an ASCII bitmask for the members below 128 and the written encoding for any member above it, which is exact because a byte below 128 is always a whole character in UTF-8 and no character's encoding is the front or the back of another's. That saving is in memory and not in time: a trim tests the set once for every character it takes off, so on the bench's fifteen byte strings it runs about level with the fold beside it. Nothing in the kernel can raise, so a trim stands in a projection, in a group key and behind an `OR` like the folds do.
- The normalization pair (ISO 20.24 and 19.7, feature GF08) is `NORMALIZE(s, form)` and `s IS [NOT] NORMALIZED form`, and both are vector kernels. They are the string library's hard case and it is worth saying exactly why, because each of the three kernels above them gets out of it a different way. A count answers a number, so nothing it writes is bytes at all. A fold answers something exactly as long as its argument, so the room a chunk of answers needs is the room the arguments took and the buffer is sized right the first time. A trim answers a part of its argument, so the bytes are already in a buffer somebody is holding and it writes none. A normal form has none of those out: composing makes a string shorter, decomposing makes it longer, and which of the two and by how much is a fact about the characters rather than about the count of them, so the answers are written out into a buffer whose size is a guess. The guess is the argument's own long bytes, which is right for everything a query normally holds and grows when it is not. What makes the kernel worth having anyway is the question it asks before any of that. No character below 128 decomposes, canonically or by compatibility, and none of them is a combining mark, so a string of them is in all four forms already and a normalization of it answers what it was handed. A column that is all ASCII, which is what nearly every stored string column is, is therefore answered the way a trim is answered: the argument's own views, the argument's own buffers held rather than copied, and not a byte written anywhere. Finding that out is a scan of the bytes with nothing to decide, which runs a word at a time, and on the bench the plain column comes out about a hundred times the accented one, which is the whole return on the scan. The same test is asked again a string at a time inside the slow path, because a chunk holding one accented string still holds plenty that are plain. The encodings sort themselves out the way they do everywhere else in the library: a constant is normalized once, a dictionary normalizes its table and the rows gather over the answers, and only a flat argument normalizes a string a row. A dictionary is also the one shape that cannot take the ASCII path, an entry of a table not being bytes a view can name. The predicate is the other half and it is the one string function whose answer is a truth value, so it writes a predicate bitmap the way a comparison does rather than filling a vector. A chunk of truth values is not a column this executor carries, so `IS NORMALIZED` is claimed in a filter, which is where a query writes it, and a projection holding one still goes back to the row engine. The `NOT` of the negated spelling is read by the compiler and handed to the kernel rather than run as an op of its own, and that is not a shortcut but the only correct place for it: a predicate bitmap has room for two answers where the language has three, so a null row is off in the bitmap under both spellings, and a complement of the plain answer would have called every null row unnormalized. It is also the reason there is no general `NOT` over a predicate register anywhere in the vector crate. Neither of the two can raise, every string having a normal form and either being in it or not, so a normalization stands in a projection, in a group key and behind an `OR` like the folds and the trims do.
- The substring function (ISO 20.24) is `LEFT` and `RIGHT` and nothing else. GQL has no `SUBSTRING`: the word is one the standard has reserved for a later edition to give a meaning to, so a query that wants the middle of a string writes one of these inside the other, `LEFT(RIGHT(s, 4), 2)`. Both count characters rather than bytes, the way `CHAR_LENGTH` does, so a count of two over an accented string answers the two letters a reader sees. A count above the length of the string answers the string, since there is nothing else to hand back and asking for more than there is is not a condition the standard names, and a count of nought answers the empty string. A negative count is `22011`, the substring error, and so is a count with a fraction on it, because the grammar takes any numeric expression where the length goes and half a character is not a thing a string has. These are the first two rows whose argument positions are not alike, a string and then a number, which the registry says with one kind rather than with a list of them, and the binder checks each position against it. A null on either side answers null. Both are vector kernels, and the kernel is the trim's arrangement rather than the normalization's: what a cut answers is a part of what it was handed, so a flat or a constant argument's answers are views back into the argument's own bytes, the answer vector holds the same buffers rather than a copy of them, and not a byte is written. What is new is where the part comes from. A trim's set and a normalization's form are words the statement wrote, one of each a chunk, but a count is an ordinary argument and a column may arrive in it, so two rows over one dictionary entry no longer answer the same thing: a coded column cuts its table once where the count is one number and a row at a time where it is not, a dictionary being the one shape that has to write at all. The walk is bounded by the count rather than by the column, `LEFT(s, 4)` being four characters however long the strings are, which is why the bench has it ahead of the trim of the same column, a trim paying a test of its set for every character it takes off. This is also the one string op whose condition is about a value rather than about what the statement wrote. A count written out is settled by the compiler the way a written divisor is, so those shapes stand in a projection, and a count that is a column is walked in the kernel before an answer is made, over the rows the selection kept and skipping the rows whose string is null, since a null answers null before the count is looked at. A projection holding a count that is a column goes back to the row engine, exactly the way a division by a column does, because a computed column is filled before the filter that would have dropped the offending row. A null on either side is a null answer, which is two columns' worth of validity rather than one.
- The temporal value functions (ISO 20.27) come in pairs: a word that asks what time the statement is running at and a word that reads the same type out of a string. `CURRENT_DATE`, `CURRENT_TIME`, `CURRENT_TIMESTAMP` and `LOCAL_TIMESTAMP` are bare words and not calls, the grammar giving them no parentheses, so `CURRENT_DATE()` is a call to a function nobody defined and is refused with `42002`. `DATE(s)`, `ZONED_TIME(s)`, `ZONED_DATETIME(s)` and `LOCAL_DATETIME(s)` must be bracketed, and `LOCAL_TIME` is the one the standard writes both ways. The brackets may stand empty, which reads the clock, so `DATE()` answers what `CURRENT_DATE` answers and `ZONED_DATETIME()` answers what `CURRENT_TIMESTAMP` answers. The words are reserved either way, so reading them in the parser takes no name away from a query. The three `CURRENT` words answer in the session's displacement and the two `LOCAL` ones answer without a displacement at all, which is the whole of what separates them, and zu's session displacement is UTC, one of the implementation-defined choices the standard leaves open. The one thing that makes these different from every other function here is that a clock reading is not the arguments': a clock read while the statement was bound would be folded into the plan, and zu caches plans, so every statement after the first would be told the time the first one compiled at. The instant is therefore a hidden argument. `Options` carries it, the executor reads it once before the first stage and hands the filled copy down, and the binder plants a `Clock` leaf under every one of these that was written no string, so the rows are ordinary registry rows with ordinary pure kernels and the clock is read once per statement however many of these it holds and however many rows they answer over. A scan of ten million rows makes one system call, every row of it agrees about what time the statement ran, and a query written inside an expression agrees with the query around it. That one hidden argument is also what makes the two halves one thing: a row takes the string the statement wrote or the instant it is running at, reads it at the type the row names, and answers, so the ten are ten target types and one kernel rather than ten pieces of date arithmetic. It is what settles the folding too, without a second rule. Every one of these rows is deterministic, one answer for one argument, so `DATE('2024-01-15')` is answered while the statement is bound and the plan carries the date; `DATE()` is not folded and never can be, because the folder folds nothing but literals and a clock is not one. ISO writes each parameter as a `<...string>` or a `<record constructor>`. zu reads the string. The record form, which names the fields of the value one at a time, is not implemented, and a query writing one is refused.
- The duration value functions (ISO 20.29) are `DURATION(s)` and `ABS(d)`. `DURATION` reads a length of time out of a string and is the one of these with no empty form, there being a date now and a time now and no length of time now, so `DURATION()` is refused where `DATE()` is answered. Which kind the answer is is the string's to say and not the call's: `P1Y2M` is a year-month duration and `P3DT4H` a day-time one. `ABS` over a duration is the same `ABS` the numbers are given, one row and one more arm on its kernel, because the length of a duration without its sign is the count it holds without its sign and the kind it counts in is untouched.
- The set functions (ISO 20.9) are `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` and `COLLECT_LIST`, which are the mandatory six, and `STDDEV_SAMP` and `STDDEV_POP`, which are feature GF10. `COLLECT` is openCypher's name for `COLLECT_LIST` and is a second spelling of the one row, so a plan and a refusal name the function the standard names and a query written either way runs. The two deviations differ in one thing, what the sum of squares is divided by, so they are two rows over one accumulator. That accumulator is Welford's and not the sum of squares. The sum of squares is how a one pass deviation is usually written and it is wrong: over values that are large and close together, the sum of squares and the square of the sum are two big numbers whose difference is small, and subtracting them throws away the leading digits of the answer, so an engine written that way returns a deviation of nought, or of a negative number under the root, for a column of timestamps. Welford's keeps a running mean and a running sum of squared deviations from it, subtracts nothing large from anything large, and costs one more multiply per row. It also merges, by Chan's formula, which is what lets the deviation be computed per morsel and folded at the end like every other accumulator here rather than being the one function that has to see the rows in one place. A multiplicity is folded by that same merge with a second set whose mean is the value and whose spread is nought, so an unflattened chunk standing for a thousand rows is one step and not a thousand. No values is null for both. One value is null for the sample and nought for the population, which is not a special case but what the two divisors say: a population of one sits on its own mean, and a sample of one is no sample of a spread at all. The set quantifier in front of the argument is `DISTINCT` or `ALL`, and `ALL` is what leaving it out means, so it is read and dropped: the two ways of writing the same query are one plan.
- The percentiles (ISO 20.9, feature GF11) are `PERCENTILE_CONT` and `PERCENTILE_DISC`, the two binary set functions and the only set functions that take a second argument. That argument is the fraction of the way through the group to answer, and the standard calls it the independent value expression because it is independent of the rows: it is one value for the whole group. zu takes the strict reading of that and refuses a fraction that reads a column, which is a compile time check, so a literal and a parameter both pass and `PERCENTILE_CONT(n, n)` is refused rather than answered from whichever row arrived first. A fraction outside 0 to 1 is `22003`, and a null fraction is a null answer. The two functions part on one question, what to say when the fraction lands between two values: the discrete one answers the first value whose running share of the group reaches the fraction, so its answer is a value that was there and has the type it had, and the continuous one interpolates between the two and answers a float that usually was not there. The median of two and four is three under one and two under the other. Both are exact rather than sketched. A percentile is holistic, so the values are kept, weighted by the multiplicity of the chunk they came from and sorted once at the end; a t-digest would bound that memory and would also stop the answer being the standard's answer, and in the discrete case would return a centroid, which is an average of values rather than one of them. If a sketch is wanted it belongs behind a name that says so.
- `DURATION_BETWEEN(a, b)` (ISO 20.28) answers the length of time from the first datetime to the second, with an optional `YEAR TO MONTH` or `DAY TO SECOND` behind the closing bracket saying which of the two duration kinds the answer is. Leaving the qualifier out reads as `DAY TO SECOND`. Three things about it are worth writing down. It is written like a call and is not one, because the qualifier stands where a call has nothing and the two words it is made of name fields rather than values, so the parser reads it and the qualifier picks the registry row rather than becoming an argument; the arity is still the row's, so `DURATION_BETWEEN(a)` is refused with the words every short call is refused with. The direction is from the first argument to the second, so the answer is positive when the second is the later of the two: the publicly readable part of the standard writes the two operands as `<datetime value expression 1>` and `<datetime value expression 2>` without saying which way the subtraction runs, and zu reads the name, which is also what every graph engine a query would be ported from answers. And the counting is `Temporal::between`, which is also what a minus between two datetimes runs, so the operator and the function cannot answer differently. A day-time answer is a count of nanoseconds and needs no calendar. A year-month answer is the largest count of whole months that does not carry the first argument past the second, stated against zu's own month addition rather than against a comparison of day numbers: 31 March to 30 April is one month here, because 31 March plus one month is 30 April and lands exactly on it, where a rule comparing the days of the month first would answer nought. Stating it against the addition is what makes `a + DURATION_BETWEEN(a, b) YEAR TO MONTH` land at or before `b` and one month more overshoot, and a law that holds is worth more than agreement with a rule that does not. The two arguments have to be the same shape, since a date and a time have no length between them, and a local datetime and a zoned one have none either, a local value naming a wall clock rather than an instant. It is a vector kernel, and it is the first one whose loop is picked by a type rather than by a physical width: the op carries the type both operands hold, so the choice between a scale of one and a scale of a day's worth of nanoseconds is made once a chunk and no value inside the loop carries a tag for the loop to read. The two kinds are not the same kind of work and the bench says so. A day-time answer is a multiplication and a subtraction a row, which over two million dates runs at 377 million rows a second against the row engine's 210 milliseconds, near forty times; a year-month answer is a walk over the calendar, which runs at 40 million and is five times, and it is here to be seen costing what it costs rather than assumed away, months being of different lengths so that no scaling turns one count into the other. What decides whether the call is claimed at all is the lane on each register: two registers that disagree are not two instants of one type, which is the pair the row engine refuses rather than reading one as the other, and a register holding a duration is not an instant. The call stands behind a filter and not in a computed column, and the reason is the condition rather than the arithmetic: a date the calendar has is not always a number of nanoseconds, so a pair of ordinary dates a single day apart in the year 9999 has no day-time duration between them, and a computed column is filled before the filter that would have dropped the row it happened on. Behind a filter the row engine evaluates the same rows, so the same rows raise. The compute loop uses checked arithmetic and notes only that some row had no answer; a second walk over the selection then finds which row it was and words the `22G03` the way the row engine words it, and a row the selection dropped is a row the row engine never evaluated and raises nothing.
- `ELEMENT_ID` (ISO 20.10, feature G100) answers an identifier for an element, and the standard leaves what the identifier is to the engine, listing the choice in both its implementation-defined and its implementation-dependent tables. zu answers a string. A node is `n:` and then its table and its offset; an edge is `e:` and then its table, the pair it runs between and which copy of that pair it is, which is what tells parallel edges apart. It is a string rather than a number because the one thing an identifier owes is to name one element, and a node's offset and an edge's row are two numbering schemes that overlap, so a query holding both could not tell whether it held one element twice. This is not `ID`, which is zu's own function and older than the standard's: `ID` answers a node's offset as an integer and null for an edge, and both keep the name they are asked for. A null element answers null rather than an identifier for null, and a list or a number is refused while the query is bound, since the standard writes the argument as an element variable reference. `ID` is a vector kernel and costs nothing to be one. A level of the pipeline carries the row each of its nodes came out of as the first vector of its chunk, which is the number `ID` answers, so the call reads a column the plan already holds rather than computing one, and it stands wherever a stored integer column stands: in a projection, in a filter, in an order, as a group key, and inside `count`, `min` and `max`. `ELEMENT_ID` is a kernel for the same reason, one step further on. Its answer is a string no row holds anywhere, so unlike `ID` it is written rather than read, but the two numbers it is written from are both to hand: the table is the level's and is the same for every row that level will ever produce, so the head of the identifier is written once for a chunk and a row's own number after it. Nearly every one of them fits in the twelve bytes a string view holds inline, so a chunk of a normal graph fills no buffer at all. An edge is the argument that goes back to the row engine, an edge being its table, the pair it runs between and which copy of that pair it is, and a level carries none of those as a column.
- The cardinality expression (ISO 20.10, features GF12 and GF13) is two words for one count. `CARDINALITY` takes the four things the standard's argument list names, a list, a path, a record and a binding table reference, and answers the elements, the elements, the fields and the rows. `SIZE` takes a list. What a path holds is its nodes and its edges, so a walk of two edges has a cardinality of five and a path length of two, and the two questions about a walk have separate answers rather than one: `PATH_LENGTH` is the standard's word for the second, which is why the first is not it. A binding table is the one argument form no statement can write, a table arriving as a parameter, and what it counts is the rows, the columns being the shape of a row rather than a second thing to count. zu's `SIZE` takes a string as well, which the standard's does not, `CHAR_LENGTH` being the standard's spelling for a count of characters; the extension stays because the openCypher queries that arrive here write `SIZE` and mean exactly that, and refusing them would gain nothing the other name does not already give. `CARDINALITY` refuses a string, which is the one place the two names differ, because a string has a length and not a cardinality and answering anyway would let a query that meant `CHAR_LENGTH` pass. A null argument answers null under both, the null rule being read before the type check rather than after it. A wrong type is `22G03` whichever side finds it, which is the registry's rule and not these two functions': a literal has a type the binder reads, so `SIZE(1)` is refused while the statement is bound, and a property read is `ANY` until a row arrives, so `SIZE(n.id)` is refused on the row that carried the value, and a client sorting failures by code does not have to know which of the two caught it.
- The case expression (ISO 20.7, mandatory feature GE01) is the one expression here that decides which of its parts to evaluate. Both forms are parsed into the one node, the simple form keeping the subject it named rather than being rewritten into an equality repeated once per branch, and the branches keep the order they were written in because that is the order they are asked in. The executor walks them and stops at the first that holds, so a branch below one that matched is never evaluated and neither is a `THEN` whose `WHEN` said no, which is what lets `CASE WHEN n.d = 0 THEN 0 ELSE n.x / n.d END` stand where the plain division would raise. A branch whose condition is null did not hold, a null subject of the simple form equals no branch, and a case that holds none and wrote no `ELSE` is null. `COALESCE` and `NULLIF` are ISO's case abbreviations and are parsed the way `CAST` is rather than resolved as functions, for the same reason the walk above exists: a function has every argument in hand before it is entered, and `COALESCE` is the decision not to evaluate the rest. The answer's type is folded over the branches, two branches of one type answering that type and an integer beside a float answering a float, which is the rule a list literal already uses. The vector engine declines a plan holding one and the row engine takes it, since a per row branch is not a kernel.
- The boolean test (ISO 20.20) is `x IS [NOT] TRUE`, `IS [NOT] FALSE` and `IS [NOT] UNKNOWN`, and it is the only construct in the language that answers a two valued question about a three valued expression. Everything else carries unknown through: `NULL AND TRUE` is unknown, `NOT NULL` is unknown, and a `WHERE` handed unknown drops the row without ever saying which of the two reasons it had. The test is where a query gets to ask, so it is the one expression node here that may be handed a null and must not give one back, and the negated spelling is an exact complement rather than a third answer, which is why a null operand satisfies `IS NOT TRUE` and `IS NOT FALSE` at once. It sits below the comparison the way ISO writes it, over a boolean primary, so `1 = 1 IS TRUE` is `(1 = 1) IS TRUE`, and the operand has to be a boolean where `IS NULL`'s takes anything, because whether there is a value is a question about every value and whether a string is TRUE is not a question with an answer. The word `UNKNOWN` is read as a literal (ISO 21.2) and it is the boolean type's null rather than a fourth kind of value, so one three valued table answers `UNKNOWN AND TRUE` and `NULL AND TRUE` alike. The vector engine has no op for the test and the filter holding one goes back to the row engine, for the reason the normalization predicate gives: a predicate bitmap has room for two answers where the operand has three.
- A `LET` written inside an expression (ISO 20.5, feature GE03) names a value for the length of that expression and no longer, which is the clause said in a smaller place: `LET n = f(x) IN n + n END` calls `f` once, where writing the call twice would call it twice. The names go into the ordinary scope and come out at the `END`, so the body reads one the way it reads a variable the match wrote and everything that works on a variable works on these, and the definitions are read left to right with each in scope for the ones after it. A name already in scope is refused rather than shadowed, which is the rule the clause keeps. Each value goes into a slot of the binder's own that is in no chunk, and the row supplies what the expression reads less the names it made itself, so the operator under it is asked for nothing it has not got. Two words collide here and the standard's own grammar does not separate them: a definition holds a whole value expression and `IN` is one of the operators a value expression is made of, so `LET n = a IN b IN c END` has two readings. The one taken is that `IN` at the top of a definition closes the definitions, and a membership test written there goes in parentheses. `LET` itself stays an ordinary name, since what makes it the expression is the definition behind it, and `RETURN let` is a variable read. The vector engine declines a plan holding one and the row engine takes it, for the reason it declines a case: a name written and read inside one row is not a kernel.
- The six pattern predicates (ISO 19.8 to 19.13, features G110 to G115) ask about an element a pattern already bound rather than about the walk, so they are expressions and the pattern matching knows nothing of them. What they need from the schema is settled while the query is being bound and written into the expression: `IS DIRECTED` carries the rel tables that store a direction, `IS LABELED` carries the label test for the node case and the rel tables whose name satisfies the expression for the edge case, and `IS SOURCE OF` carries the endpoint table triples, each list sorted by table so a row costs one binary search and no second read of the graph. An edge value already holds both of its ends, so relating a node to an edge is a comparison rather than a lookup. `ALL_DIFFERENT` and `SAME` compare elements pairwise and are ordinary variadic calls, while `PROPERTY_EXISTS` is parsed the way `CAST` is, its second argument being a bare property name that would otherwise read as a variable nothing bound. That one asks the table and not the value, so a property that is stored and null answers true, which is the difference between an element that has no such property and one whose property is unknown. All six answer null over an element that is null, which is the reading an unmatched optional row gets. Those two are answered by the pipeline over nodes, and half of every pair is settled before a row is read: a level has one table for every row it will ever produce, so two levels on different tables hold different nodes whatever their rows turn out to be, and two names for one level hold the one node. Either function is false outright as soon as one pair goes the wrong way, and what is left is a row against a row, which is one integer comparison. An edge argument goes back to the row engine, an edge being its table, the pair it runs between and which copy of that pair it is, and none of those is a number a level carries.
- Path returns use **PMR (path multiset representation)**: predecessor DAG per BFS level; paths materialized lazily as `LIST<alternating NodeId/RelId>` only at RETURN (PathFinder design). The level pass behind the shortest selectors builds that DAG as it levels, so `ALL SHORTEST` enumerates down it rather than reading each node's neighbors again for every path prefix that reaches it, and there is one prefix per path. The multiplicity comes off the same DAG without the paths: a node's shortest paths are its predecessors' shortest paths added up, parallel edges between the same two nodes counting as the different paths they are, so a walk whose rows nothing reads but one bare count answers with one breadth-first pass. Enumerating instead is one walk per path and two nodes can have exponentially many shortest paths between them, which is the difference between a number and a search that does not finish. It is the count-to-degree rewrite of docs/11 B4 reaching the variable-length case, and it is the one walk whose paths can be counted without being built, since the levels make the searched graph acyclic and every mode allows a path that repeats nothing.
- Unweighted `ANY SHORTEST` between a bound pair: the optimizer absorbs the equality that pins the far end into the expand, and the operator grows a frontier from each end until they meet, which visits two balls of radius d/2 instead of one of radius d. The one-sided hop-level pass stays for the unpinned case and for `ALL SHORTEST`, which has to know every node's minimum hop count before it can enumerate.
- Weighted `SHORTEST` (`COST` clause): bidirectional Dijkstra on CSR with binary heap; batched variant = Multi-Source Bellman-Ford.
- The `bfs()` and `sssp()` table functions run the same frontier the recursive operators do: a visited bitmap rather than a distance array, one group pin per group per round so a round decodes each group's CSR once instead of once per node in it, and a direction-optimizing switch decided per round. A round goes bottom-up when the frontier is about to read more edges than are left unexplored (alpha 14) and comes back up when the frontier has thinned below n/24 (beta 24). `bfs()` follows stored edge direction, which is what Graphalytics and Graph500 mean by a level; `sssp()` walks the undirected view under unit weights. `sssp_weighted()` is the weighted form and does not share that frontier: it names an edge property column, follows stored direction, and settles nodes by distance out of a ring of buckets one distance value wide, falling back to a binary heap where the widest edge is too wide for the ring to be worth building. An edge's weight is read by its slot in the forward list rather than by its endpoints, which is what lets a graph hold the same pair twice with two different weights.
- `triangle_count()` yields the number of undirected triangles each node is a corner of, so the single figure the GAP TC kernel reports is `sum(triangles) / 3`. It builds the upward half of the undirected adjacency once into a flat `u32` array, four bytes a stored edge, and intersects the two lists an edge joins, by merge when they are a similar length and by search of the longer one when they are not. Building it is two sequential sweeps of the forward CSR against one group decode per edge for a kernel that asks the reader for a far node's list as it goes.
- `betweenness()` accumulates shortest path traffic through each node from a list of sources by Brandes, following stored direction, which is the sampled GAP BC kernel. It keeps no predecessor lists: what the backward pass wants for a node is the nodes one level above it with an edge into it, and that is the node's in edges filtered by level, which the backward CSR already holds. Both passes take a level at a time in row order, so a level decodes each group once rather than once per node in it, and the backward pass is free to do that because only the order of the levels matters to it. A source naming no row of the table contributes nothing, since a fixed sample is drawn against the biggest graph in the family.

## 6. Cardinality estimation (no ML)

1. Per-direction degree histograms (log2 buckets) per rel table, and the l1/l2/l3/linf norms of both degree sequences alongside them. A frontier that already holds one row per edge sits on nodes drawn in proportion to their degree, so the mean an expand off it sees is the degree-weighted mean and not the plain one; the mixed norm, the sum over nodes of out-degree times in-degree, is that mean's numerator when the two hops read opposite sides and makes a two hop count over one rel table exact.
2. Label-pair join selectivities from edge counts.
3. **Color summaries** (COLOR, PVLDB 2024): quasi-stable coloring, default ≤ 1024 colors, built by `zu analyze`, stored in stats blocks; estimates multi-hop pattern cardinalities. Each summary is stamped with the epoch ANALYZE read and the edges the table held then. Writes land under a summary without moving it, so between builds the per-color counts scale by how far the table has grown and the coloring is trusted for the shape alone, which is the graceful degradation COLOR is picked for; past 8x drift either way it is a precise statement about a graph that no longer exists and the estimates fall back to the degree histograms. EXPLAIN prints a note naming the drift, and `zu stat` prints the stamp.
4. **Pessimistic caps** (AGM/degree-sequence bounds) clamp every estimate; join order falls back to the bound-optimal order when estimate and bound disagree by > 100x (robustness first). `ZU_BOUND_DISAGREEMENT` retunes the factor, and EXPLAIN prints a note naming the ratio whenever the fallback fires.
5. **Point seeds read their own degree at run time.** A `{id: $x}` lookup pins its slot to one node, and the step off that node reads one list, so a mean describes it only by accident: SF1 hands the short reads a person with 335 knows edges against a mean of 16.8. Join ordering cannot use this, because a plan is cached across parameter values and the answer differs between two of them; execution can, because by then the value is bound and the degree is an offsets subtraction away. The estimate walk therefore takes an optional reader, and where a point lookup pinned a slot the first step off it reports the count instead of estimating it. Nothing else consults the reader and the DP never gets one, so every plan is still chosen on statistics alone.

## 7. Execution-time adaptivity (small, deterministic)

The set is closed on purpose. An engine that may adapt anywhere is an engine whose plan does not predict its behaviour, and a slow query then has no explanation short of a profiler. Eight decisions, each named, each counted, each printed under the plan by EXPLAIN ANALYZE, is a budget: a new one has to displace an old one or argue its way in. Everything else about a query is settled before a row moves, and what is left here is only the choices that need a number the statistics do not have, because only the data itself has it.

1. **How the driving source is cut up.** The scheduler sizes the morsels off the rows the source actually reports and the workers it actually has, group-aligned so a morsel's CSR pins and zone reads stay inside one group. A seed's frontier is cut by weight rather than by position when the seed is a celebrity, since equal slices of a skewed neighbourhood are not equal work.
2. **Chunks the range pushdown empties before decoding.** The zone map answers off the chunk summary, so the payload bytes are never touched.
3. **Chunks that decode and then lose every row to the same range.** The summary said maybe and the values said no, which is the pushdown paying for itself halfway.
4. **A sideways filter switching itself off.** Each worker judges the filter it holds against the rows it drew, over a trial window, and stops asking once the filter is rejecting too little to pay for itself. Dropping it is always sound because the join behind it still has to match every row that comes through.
5. **A close that ends before it builds anything**, the far end of it having no edges at all.
6. **A bounded sink stopping a morsel** with the rows the limit asked for already in hand.
7. **Which worker takes which morsel.** Nothing hands them out in advance; a worker takes the next one when it has finished the last, so the spread between the busiest and the idlest worker is the only record of how evenly the work actually fell.
8. **Whether a neighbor list is read off a group decoded whole or out of the chunks that one list covers.** The walk knows how many of the group's lists it is about to want, storage knows how many chunks the group holds, and the pin starts paying at roughly a quarter as many lists as chunks. A scan morsel is far past that line and a point seed is far short of it, and the difference between the two on a seeded read is three orders of magnitude, since pinning decodes a group's two million edges to hand back one node's sixteen.

None of them persists. Nothing a run learns is written back into the statistics or carried into the next query, so two runs of the same query over the same data make the same decisions from the same evidence. What does move between runs is how the morsels landed on the workers, since decisions 4 and 7 are judged per worker off the rows that worker drew, and the rendering says which of the lines that applies to. The totals underneath are the same either way, because worker-local counts are added.

This list replaces three earlier sketches that did not survive contact with the engine. An ASPJoin side swap on an 8x estimate miss is not here because flipping the sides of a join is not a local re-plan: it was measured, and building the small side loses badly, since output rows come off a build side's payload list nearly free while every driven row costs a scan and a gather (see `crates/zu-exec/src/sip.rs`). A per-iteration morsel policy for RecursiveBFS waits on P4. Binary search against full list scan per morsel is a compile-time property of the hop, not something a morsel gets to choose, so it is a planning decision and belongs to section 4.

## 8. DML execution

Writes compile to the same pipelines producing a `CommitBatch`: node inserts append to group deltas; rel inserts go to CSR slack (or delta overlay if slack exhausted; folded at checkpoint); `MERGE` = IndexLookup + conditional insert under the writer lock. Constraint checks (pk uniqueness, endpoint existence) execute inside the batch before commit (§08).

## 9. Catalog statements

A catalog statement changes what a file declares rather than reading what it holds. There are six: `CREATE SCHEMA` and `DROP SCHEMA` (GC01, GC02), `CREATE GRAPH` and `DROP GRAPH` (GC04, GC05), and `CREATE GRAPH TYPE` and `DROP GRAPH TYPE` (GC03). The grammar is in `docs/grammar.ebnf`. They share the parser with queries and nothing after it: a catalog statement has no binding table, so it never reaches the binder or the optimizer, and it answers no columns, which the standard has a condition for (`00001 successful completion, omitted result`).

One may stand among data statements in a chain of `NEXT` (ISO 13.6, feature GP18). `INSERT (:thing {n: 1}) NEXT CREATE GRAPH twin ANY AS COPY OF CURRENT_PROPERTY_GRAPH NEXT USE twin MATCH (t:thing) RETURN COUNT(t) AS n` is one statement, and what makes it worth having is that the parts see each other: the graph the middle part made is the graph the last part reads, on the transaction local catalog rather than on what the file declared when the text arrived. A chain of query statements is what it always was, one linear query sharing its rows, and the chain is cut only where a catalog statement stands, since a catalog statement has no binding table to hand on. The parts run in order under one savepoint, so a part that raises takes the whole block back, the catalog it changed and the rows it wrote together, and the block answers what its last part answered. A word that begins or ends a transaction is not a part of one: it is refused among them, because the block is a transaction already and the word would be saying the unit is two.

A `CALL { ... }` body is a procedure body too, so the mixing may be written inside one, and where it is the parts are taken out of the body and put in front of the statement. `CALL { CREATE PROPERTY GRAPH side ANY NEXT MATCH (p:Person) RETURN COUNT(*) AS n } RETURN n AS n` is the block `CREATE PROPERTY GRAPH side ANY` and then `CALL { MATCH (p:Person) RETURN COUNT(*) AS n } RETURN n AS n`. That is only sound for a call the statement begins with. A call adds what its body answers to the row it ran for, and the row a leading call runs for is the unit row every statement starts from, so the body runs once and running the catalog statement once is what it meant either way. Further in, a body runs for every row that reaches it, and a graph is made once or not at all, so a catalog statement written there is refused with the reason rather than quietly hoisted out of the loop it was written in. A catalog statement written behind the data statements of a body rather than in front of them is refused for the same reason from the other side: taking it out would run it before the statements it was written after.

The body of a leading call is taken out of the call whether or not it holds a catalog statement, as long as it ends with `RETURN` and names no graph of its own. `CALL { A } rest` says what `A NEXT rest` says when the row is the unit row, and written the second way `A` is a statement of a chain rather than a body spliced into the clauses around it, so it may do the things a spliced body may not: count its rows, order them, take a page of them, or be several statements itself.

ISO writes an element type as the pattern an element of it matches, and almost every part of that pattern is optional. A statement lists them:

```
CREATE PROPERTY GRAPH TYPE IF NOT EXISTS social {
  NODE TYPE PersonType (:Person => :Employee
    {name :: STRING NOT NULL, nickname :: STRING}),
  (:Person)-[:KNOWS => :Close {since :: DATE}]->(:Company)
}
```

The labels before the `=>` are the key label set, the ones after it are the rest of the labels the element carries, and a pattern with no arrow declares no key at all, in which case the whole label set stands in for one (GG21, GG22). A name before the pattern is GG20, and it is what an endpoint elsewhere in the same graph type refers the type by: `(PersonType)-[:KNOWS]->(PersonType)` points at a type declared once, while `(:Person)-[:KNOWS]->(:Person)` declares it where it stands.

A property whose type admits null is one an element may leave out, so `NOT NULL` is what makes a property mandatory: one rule about null rather than two, and the value type grammar already had it.

A graph type written out in braces is closed, because a list nobody qualified is the whole list (GG02). Open graph types are spelled on the graph rather than on the type, which is `CREATE GRAPH g ANY` (GG01).

The catalog holds one name per element type, since a name is what an endpoint points at, and ISO's element types are anonymous. A pattern that carries no name gets one made of its labels, `KNOWS&Close` for the edge type above, with a number after it when that name is taken: GG24 is two node types over one label in one graph type, and the number is what keeps the second one from being the first one written twice. An endpoint written out is folded into a node type the graph type already has when it declares nothing of its own, so the three `(:Person)` patterns of a two edge type graph type name one node type between them.

One number in all of this is zu's rather than the standard's, impdef IL003: a written key label set names between 1 and 63 labels. Empty is a type nothing selects and 64 leaves no room in the 64 bit mask a label set is for the label the arrow adds, so the four conditions ISO reserves for the two ends of that range are raised here (`42012` to `42015`).

`CREATE GRAPH TYPE t LIKE g` is GG04: the closed type the tables of the graph named already describe, read off the catalog and not off the data, so it costs a catalog walk on a graph of any size. The tables stay the storage unit either way; a graph type describes them, it does not replace them (§03 §6).

### 9.1 Schemas and graphs

A schema is a directory the file holds and a graph lives in one. Both are names in the catalog and neither is a block on disk: `CREATE SCHEMA /app` adds a path, `CREATE GRAPH /app/social ANY` adds a graph in it, and a graph written as a bare name is a graph in the root schema. Every file has the root schema `/`, which is the one directory that is not one to drop, and every file starts with one graph in it called `home`. That home graph is what a file that was written before any of this said existed all along: a version 3 catalog reads as the root schema, the home graph, and every table in it, so an old file gains the vocabulary without gaining a rewrite.

Which graph a table belongs to is a field on the table rather than a list on the graph, so a table cannot be in two graphs and dropping a graph is a filter over the tables the catalog holds. A node table joins the graph a session is loading into and a rel table joins the graph of the table it comes from, which is what keeps an edge and its endpoints together.

A graph is created with the open type, with a graph type the file already holds (`CREATE GRAPH g :: social`), or with one written where the graph is created (`CREATE GRAPH g { (:Person {name :: STRING}) }`, which is GG03, and `CREATE GRAPH g LIKE h`, which is GG04 read at the graph). An inline type is kept on the graph and not added to the file's graph types, since nobody wrote a name for it.

`AS COPY OF` (GG05) says what the new graph starts with rather than what it is, so it is read after the type. What it names is a graph the file holds or `CURRENT_PROPERTY_GRAPH`, which is the graph the statement is against, and a copy of an empty graph is a graph with no tables.

A copy of a graph that holds tables is a copy by value: the catalog gets a table per table of the source, keeping the name and taking a new id, and the storage those ids address is copied block for block. Every segment block is read whole and written into a freshly allocated one, so a copy costs a read and a write per block and no decode, and what a column holds is none of the copy's business. The directories are re-encoded because a directory names the blocks its segments live in and those are now different blocks, and everything else, the labels, the validity, the key index, the CSR pair per group, the edge properties, and the tombstones a node table has, carries over byte for byte. The two graphs share nothing, which is the point: a copy that pointed at the source's segments would be a second name for one graph and the first write to either would show up in both.

`DROP GRAPH` is the one statement in zu that hands blocks back. It frees the props directory of every node table in the graph, the group directory of every rel table, the tombstone chain of every node table that has one, and the table index and stats chains it rewrites, then takes the graph and its tables out of the catalog. Nothing is published along the way: the checkpoint that stores the catalog makes the catalog, the table index and the stats visible together, so a drop that fails halfway leaves the file exactly as it was. Freed blocks become allocatable at the checkpoint after the one that published the free, and `block_count` is a high-water mark that never shrinks, so what a drop returns is measured in the free list and not in the size of the file. Dropping the home graph is allowed and is the reclamation path a file with one graph has; the next load puts an empty home graph back.

`DROP SCHEMA` is `RESTRICT` in the sense the standard gives it: a schema that still holds a graph is not one to drop, and the error says which graph is in the way.

`CREATE OR REPLACE` and `CREATE ... IF NOT EXISTS` are the two answers to a name that is taken, and a statement saying both says nothing, so it is refused. The replacement is built before the old type goes, which is why a replacement that cannot be kept leaves the type that was there.

Applying one is read, change, publish: the change happens on the catalog the call loaded and reaches the file through the same checkpoint every other write uses, so a statement that turns out to be impossible halfway through leaves the file exactly as it was, labels included. A session that runs one publishes a new epoch and refreshes itself, which drops the cached plans and readers that describe the catalog it just replaced.

### 9.2 Which graph a query is against

A query reads one graph, and `USE` is what names it (GQ01, ISO 16.2). A query with no `USE` in front of it is against the graph the session is working in, and `USE CURRENT_PROPERTY_GRAPH` says that out loud. `USE HOME_PROPERTY_GRAPH` names the graph the session started in, which is the same graph until something moves the working graph. `USE g` names a graph the catalog holds, by a bare name in the root schema or by a path. `USE $g` names the graph the caller passed in, which is the graph reference form: the value has to be a graph reference, taken from `Session::graph_ref`, and not a string that happens to spell a graph's name. A name the catalog does not hold, a parameter that was not given, one holding something that is not a graph, and a reference to a graph that has since been dropped are all references that resolve to nothing, which is `42002`. The graph an `AS COPY OF` starts from is written the same way and takes the same four forms.

A table's name is a name in its graph and not in the file. Two graphs may both hold a `person` and they are two tables, which is what a graph copied from another one is made of. That is why the binder schema is built per graph rather than per file: the tables a query can name are the tables of the graph it is against, and a `person` in another graph is not in reach of a pattern that never named that graph. The catalog enforces the pair rather than the name, and it enforces that a rel table and both node tables it ends on are in one graph, since an edge reaching out of its graph would put rows nobody asked for in reach of a walk.

A graph is also a value, which is GE01 and ISO 19.6, so the words that name one are worth the same where a value goes as they are after `USE`. `CURRENT_GRAPH`, `CURRENT_PROPERTY_GRAPH`, `HOME_GRAPH` and `HOME_PROPERTY_GRAPH` each answer the handle the session would have handed out for that graph, and a graph named rather than referred to is written as the path it is at, `/home` or `/social/people`. The path is the whole of how one is named there, and the reason is a division: `USE` also takes a bare name and takes `GRAPH` in front of it, and in an expression a bare name is a variable and a word with a path behind it is `graph / n` as often as it is a graph. `GRAPH $g` and `BINDING TABLE $t` do stand, because the dollar sign settles it, and they say which of the two reference types the parameter is expected to hold and nothing else, exactly as `USE GRAPH $g` says nothing `USE $g` does not. Which graph the words name is settled while the statement is bound, against the whole catalog rather than the graph being bound against, since `/other` names a graph the statement is not running against and answering it is the point: a reference says which graph, it does not read one. What comes out is a value of `GRAPH` (GV60), and two of them are equal when they name the same graph, the epoch each was taken at being when it was asked for rather than what it names.

A session builds one schema per graph a statement has named, on the first naming, and drops them all when the header epoch moves. The plan cache is keyed by statement text, and the `USE` is part of the text, so the schema a plan was compiled against rides with the plan rather than being looked up again at execution. A `USE $g` is the one text that does not say which graph it is against, so its plans are held one per graph under a key of the text and the graph, and the text itself holds the name of the parameter to read to find the right one. That costs a text naming no parameter nothing: an ordinary text is found under itself on the first lookup, which is the one the P0 plan-hit gate times.

### 9.3 The session statements

A session is a named mutable environment and not a transport detail (ISO 7.1): it holds the schema it works in, the graph it works in, the displacement it reads a clock in and the parameters it stands ready to answer, and the session statements are what move those five things. They answer no rows, they take no epoch and they touch no file, since none of them says anything about what is stored; what they change is what the statements sent after them mean. There is one entry point that refuses them outright, the one-shot `zu::query::run`, because a statement that changes what the statements after it run in needs there to be statements after it, and a call that both opens and closes a session has none.

A session parameter is a binding variable definition that outlived the statement that made it, which is the whole of the design. `SESSION SET VALUE $cut = 35` is `VALUE cut = 35` written with a dollar and kept, so the parser reads it with the same `parse_binding_def_body` a statement head is read with and the three kinds are the three kinds: a value (GS03), a binding table (GS02) and a graph (GS01). Because the body is shared, the forms the standard lists separately come free rather than one at a time: a query defines a binding table (GS10) or a value (GS11) because a definition body already may be a query, and a reference or an expression defines a graph (GS12), a binding table (GS13) or a value (GS14) because a definition body already may be an expression. Working one out is the same reuse a rung lower. The definition is wrapped in a synthetic `RETURN <name> AS <name>` query carrying it as its one binding, and that query is compiled and run, so the type written on the definition is checked by the check `IS TYPED` makes, the one column rule is the one a value query expression gets, a graph reference is resolved where every other one is, and none of it is a second implementation that could drift from the first. What the session then holds is the value that came back and not the query that produced it: a parameter set from `MATCH ... COUNT(*)` holds the count as of when it was set, which is what a parameter is, the alternative being a view nobody asked for.

A held parameter is read under the same `$name` a caller's is, and a caller's wins name for name, the way a definition at the head of a statement stands in front of a graph the catalog happens to hold under that name: the nearer of the two is the one that means what the writer just said. The set lives behind an `Arc` because a statement reads it while the session it belongs to is being run through, so setting one clones the map, which happens once per `SESSION SET`, and running a statement clones a pointer. A session holding no parameters at all does not even do that, which is what keeps the P0 plan-hit path free of allocation for every session that never set one.

`SESSION SET SCHEMA` (GS05) moves where a name written with no path in front of it is looked up, which is the graph a `USE` names and the procedure a `CALL` names, and `AT CURRENT_SCHEMA` becomes a clause that says something once a session has moved: it is the schema the statement was sent in, where `AT HOME_SCHEMA` stays the root, the schema the session opened in. A nested `AT CURRENT_SCHEMA` resolves against the enclosing `AT` and not against the session, since a clause is the default for what is written below it. `SESSION SET PROPERTY GRAPH g` (GS06) moves the working graph, and the dollar is what separates it from setting a graph parameter: `SESSION SET PROPERTY GRAPH $g = social` gives the session a name for a graph and leaves it working where it was. Both of these clear the plan cache when they actually move, since a plan was compiled against a lookup that may now land somewhere else, and both are free when they do not move.

`SESSION SET TIME ZONE` (GS15) is a displacement in minutes east of UTC and never a zone name. A name is a rule the zone database can change, so a session set to one would answer one thing today and another after an upgrade, where a session set to an offset answers that offset for as long as it holds it. The displacement rides in `Options` beside the clock, and the executor stamps it on the reading it takes before the first stage, so the instant a statement sees is the same instant either way and what moves is the zone the statement reads it in: `CURRENT_TIMESTAMP` answers the same moment with a different offset on it and `LOCAL_TIMESTAMP` is untouched, which is the whole of what separates the two families. A displacement the standard does not allow is `22007` and not `22009`, there being no such class in the table.

`current_status()` is the GQL-status object the statement before this one ended with, read as a record value, and it is the half of GA08 that is not about producing the record. ISO/IEC 39075:2024 writes no statement for reading a status back: there is no `GET DIAGNOSTICS` anywhere in the grammar, and subclause 23 is about producing the record and exposing it rather than about a statement that asks for one, so the name is zu's and it is an extension rather than a reading of the standard. What it answers is the standard's shape though: `gqlstatus` is the five characters, `condition` is the standard's own text for them, `severity` is the one character ISO writes it as, `message` is what the engine said or null for a statement nobody had to be told anything about, and `diagnostics` is the list of records under that, each with the code, the subject and its kind, the graph and the schema the statement ran in, and the place counted three ways. A session that has run nothing answers null rather than a record of nulls, because there being no statement before the first one is a different answer from a statement that said nothing. Because it is session state and not a constant, it binds to a leaf the way the clock does and reads out of `Options` at run time: a plan that folded it would answer every later statement with the status of whichever statement happened to compile it, and the session builds the record once on the way in, so a scan of ten million rows reading it clones a record rather than formatting one. It survives a caller replacing the switches for the same reason the time zone does, since changing a thread count between two statements must not be able to answer the second one with a blank where the first one's condition was.

The graph a session works in is a reference and not a name, and that is what decides how it behaves across an epoch. A session that moved into `scratch` keeps working in `scratch` however many statements anybody else publishes, because what it recorded was the catalog id: resolving the name a second time on every epoch move would send a session that had moved somewhere back home for no reason it could see. What it does not survive is the graph being dropped, and a statement that names no graph then raises `42002` saying so and pointing at the reset, since a session in that state is not broken, only pointing at nothing. That check is a catalog lookup per compile and nothing per execution, because a drop moves the epoch, an epoch empties the plan cache, and so a statement answered out of the cache is one whose graph was there when the plan was made and has not gone anywhere since.

A parameter holding a reference records the epoch it was read at, and this is the point at which it is worth saying what a pin in zu is and what it is not. It is a number written on a handle and it holds no blocks. A lease lives for a statement rather than for a connection, and a binding table parameter holds rows that were copied out of the snapshot rather than a reader into it, so a session sitting on a parameter from an hour ago does not stop a checkpoint from reusing anything and does not grow the store by a byte. What goes stale is the meaning of the reference and not the space behind it. A graph reference stops meaning something when the graph is dropped, which is a lookup; a binding table of numbers and strings means the same thing at every epoch and carries forward; a binding table holding element references means rows of one snapshot, and once the snapshot has moved the row at that offset may belong to something else, so a statement that reads it is refused with `42002` rather than told a plausible wrong answer. Everything else the session does keeps working, including the reset that puts it right, which is the difference between being told and being stopped.

Being told is a warning on the statement that follows rather than a refusal of it. A session holding a graph parameter whose graph has been dropped gets `01G03`, and one holding a binding table that has fallen further behind than the staleness bound gets `01000`, both attached to the result after the statement ran, since the epoch a pin is judged against is the one the statement ran at. The bound is a judgement rather than a fact, so it is configurable through `Config::stale_bound` and defaults to sixteen epochs, which is far enough behind to be worth mentioning and not so close that an ordinary busy store nags a session doing nothing wrong. The whole of this lives inside the branch the parameter fold already lives in, so a session that has set no parameters pays nothing for it.

Where the report comes out is one place this deviates from the plan, and deliberately. The plan asked `zu stat` to print the pinned epoch per session, which it cannot do and should not: `zu stat` is a separate process that opens a file, and sessions are process local, so it can no more see another process's parameters than it can see its local variables. More to the point the number would not mean what the plan wanted it to mean, since a pin holds no blocks and a stale session is not costing the store anything. So the report lives where the sessions are. The library answers `Session::pins()` and `Session::pinned_epoch()`, and the shell has `\session`, which prints the schema, the graph, the displacement and the epoch, then the parameters with what each one is pinned at and whether it has gone old or gone.

Session state is not transactional. A `SESSION SET` inside a transaction that rolls back keeps what it set, because what it set was never in the database: the transaction takes back the rows and leaves the schema, the graph, the displacement and the parameters exactly as the session left them. ISO is explicit about this and a test asserts it, since the opposite reading is the tempting one.

The resets put back what the session opened with rather than putting nothing in its place, which is why there are six of them and not one. `SESSION RESET CHARACTERISTICS` (GS04) is all of the others at once, `SESSION RESET SCHEMA` (GS05's undo) sends it back to the root, `SESSION RESET PROPERTY GRAPH` (GS06's) back to the home graph, `SESSION RESET TIME ZONE` (GS07) back to UTC, `SESSION RESET PARAMETERS` (GS08) empties the set and `SESSION RESET PARAMETER $x` (GS16) drops the one it names and leaves the rest, a name the session was not holding being nothing to complain about.

## 10. The declared limits

ISO/IEC 39075:2024 subclause 24.5.2 obliges an implementation to write down what it chose where the standard left the choice open. These are zu's, one item at a time, with the condition each one raises when a statement asks for more than the limit allows.

The numbers below are also declared where a program can read them, in the `[limits]` table of `conformance.toml` and in `zu conformance --declare --format json`, keyed by the item's code and the kind of element it is the limit of. That is there for a conformance harness, which cannot test a limit condition without knowing the number: a test asking for sixty-four properties is asking a question with two correct answers, and an engine that publishes its own maximum turns it into one. An item zu sets no maximum on is absent from that table rather than written as a zero, since the two mean opposite things.

IL001, the cardinalities of label sets. A node table's name is the row's key label and an edge is stored under one type, so a label set at `INSERT` holds exactly one label: minimum one, maximum one, for both kinds of element. A pattern naming none is `22G0N` for a node and `22G0Q` for an edge, and one naming more is `22G0P` and `22G0R` with `42007` beside it where the extra labels were written as a conjunction. The rest of an element's labels go on with `SET`, which is a different statement doing a different thing, and the catalog holds up to `MAX_LABELS`, which is 64, per table.

IL002, the cardinalities of property sets. Two numbers answer to this item. The first is flat: a node or an edge carries at most `MAX_PROPERTIES`, which is 4096, and a pattern writing more is `22G0S` for a node and `22G0T` for an edge. The second is the one a reader is more likely to meet. A table's property columns are settled when the table is created, so the property set an element can hold is the set its table declared, and a statement naming a property outside it is asking for one property more than the element has room for. That is the same two conditions, `22G0S` and `22G0T`, raised by `INSERT (:Person {nickname: 'Al'})` against a `Person` table with no `nickname` column and by `MATCH (p:Person) SET p.nickname = 'Al'` against the same table. The message names the columns the table does declare, because the useful thing to say is what could have been written instead.

Adding a column to a table that already has rows is not something zu does, and this is the limit rather than a bug with a limit written over it. A column is a segment chain row-aligned with the table's row domain, so a new one over ten thousand rows is ten thousand rows of nulls written before the first value goes in, and the write path is built to append rather than to backfill. A graph whose elements are going to carry a property declares it when the table is created, which for a graph with a type is where the type says so and for a graph without one is the first `INSERT`.

A statement runs against the one graph it names. ISO 13.1 admits `NEXT USE g ...`, a chain walking from one graph into another, and zu refuses it with `25G04`, invalid transaction state, accessing multiple graphs not supported, which is the condition for exactly this. The refusal is not a syntax error and does not pretend to be one: the grammar is fine and the engine is declining it.

IL003, the cardinality of a key label set. A key label set has to leave room in the word for whatever the pattern around it adds, so it is one short of the label set that has to contain it: 63 for a node type and 63 for an edge type, and a graph type asking for more is `42013` or `42015`. IL015, the maximum cardinality of a constructed value, zu sets no number on. A path or a list built by a query is bounded by the row it is built for rather than by a limit worth publishing, so it is absent from the declaration and `22G10`, path data right truncation, has no length to exceed. IW014, the test for visually confusable identifiers, zu does not apply, so no two identifiers it reads are confusable and `42004` has nothing to raise on. Both answers are choices the standard leaves open and both are conformant, and writing them down here is what subclause 24.5.2 asks for.

Four of the standard's conditions are ones no statement reaches here, and none of them is a gap a test could close. All four are unreachable because zu supports the feature whose absence they announce. `22G04`, values not comparable, requires a pair of values with no order, and zu supports GA04, universal comparison: an engine whose `x < y` said unknown while its `ORDER BY x` put x first would have two orders and be wrong in one of them. `22G13`, invalid group variable value, requires a group variable read as one value to be an error, and zu supports GQ17, so a property read off a group is the list of that property over the group. `25G02` says catalog and data statements do not mix in one transaction, and here they do, under GP18. `25G04` says two graphs do not, and here they do, under GT03, which is why the paragraph above is about a chain rather than about the general case. `08007` and `40003` were counted here as well, on the reading that no statement reaches either and so nothing could. Neither is about a statement, which was the true half of it: `08007` needs the connection to die between a commit and its answer and `40003` needs the same of anything else in flight, and what raises them is the channel dying rather than what the engine parsed. But a client that destroys the connection with a statement in flight reaches both, which is the only way either is reached at all, so they are conditions a harness provokes rather than conditions nothing provokes.

## 11. The three deviations

All three are places where zu does something the standard does not ask for, and all three are written down here rather than left to be discovered.

The forty pre-reserved words are names in zu. Subclause 21.3 says a `<regular identifier>` is not a `<reserved word>`, and `<reserved word>` has `<pre-reserved word>` as its first alternative: forty words ISO has taken for a later edition and given no meaning to. Read strictly, `ABSTRACT`, `DATA`, `NUMBER`, `QUERY`, `UNIT`, `VALUES` and thirty-four others are therefore not names. zu admits them. Refusing a word buys a query nothing until the word means something, and it costs everybody who has a label called `Unit` or a property called `data` a rewrite for a meaning that has not arrived. The 222 words reserved outright are refused, in any case, wherever a name is written plainly, and the accent quoted form puts any of them back: `RETURN 1 AS MATCH` is `42001` and ``RETURN 1 AS `MATCH` `` is a column called `MATCH`. `zu_common::keywords::is_pre_reserved` is public so that a tool that wants to warn about the forty can.

A trailing semicolon ends a statement. The character appears nowhere in the 814 productions and `<GQL-program>` has no terminator, so the standard neither defines it nor forbids it, and subclause 24.5.3 is what lets an implementation add a construct it documents. This is that documentation.

A reserved word is a property name and a field name. `<property name> ::= <identifier>` and `<field name> ::= <identifier>`, and the 21.3 rule reaches every `<identifier>` there is, so read strictly a property cannot be called `year` and neither can a record field. But the standard writes its own datetime constructors as records over exactly those names: `<date function parameters> ::= <date string> | <record constructor>`, and the fields the record is meant to carry are `year`, `month` and `day`, all three of which are in `<reserved word>`. So `DATE({year: 2024, month: 1, day: 1})` is a statement ISO both defines in subclause 20.27 and forbids in subclause 21.3, and one of the two has to give. In zu the rule gives, and only in this one slot. A name in a property map, a record type field, a record constructor field, or behind a dot always stands between a delimiter and a colon or between a dot and whatever follows it, so no word written there could be read as the keyword it is spelled like, and a rule whose whole job is to keep a keyword from being mistaken for a name buys nothing where there is nothing to mistake. Every slot where a word could be read either way keeps the rule in full: `RETURN 1 AS year` is `42001` and so is `MATCH (year:Person)`. Neo4j reads 21.3 the other way, as reaching property names too, and its conformance appendix declares the subclause not supported on that ground.
