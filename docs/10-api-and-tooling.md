# 10. API, CLI, Server, Tooling

## 1. Rust API (crate `zudb`)

```rust
use zudb::{Config, Database, Flow, params};

let db = Database::open("social.zu1")?;                              // zu1
// Database::open("social.db?engine=sqlite")                          // sqlite
// Database::open_with("s3://bucket/graphs/social", Config::new())    // s3

let mut conn = db.connect()?;                                        // cheap, Send
let rows = conn.query_with(
    "MATCH (p:person {id: $id})-[:follows]->(f) RETURN f.name AS name, f.born AS born",
    &params! { "id" => 42 },
)?;
for row in rows.iter() {
    let (name, born): (&str, Option<i64>) = row.get()?;              // typed, borrowed
}

// Compiled once, run per binding
let (stmt, wanted) = conn.prepare("MATCH (p:person {id: $id}) RETURN p.name AS name")?;
let rows = conn.execute_prepared(stmt, &params! { "id" => 7 })?;
conn.close_prepared(stmt);

// Rows in batches, for the results too big to want in memory
let mut out = Vec::new();
conn.query_stream("MATCH (p:person) RETURN p.id AS id", &[], |batch| {
    for row in batch.iter() {
        out.push(row.get_at::<i64>(0)?);
    }
    Ok(if out.len() < 1_000 { Flow::More } else { Flow::Stop })
})?;

// Plans and counters as structures rather than as text
let plan = conn.explain_plan("MATCH (p:person) RETURN p.id AS id")?;
let root = plan.root.as_ref().expect("a statement with operators");
root.walk(&mut |op, depth| println!("{}{} {}", "  ".repeat(depth), op.op, op.detail));
let profile = conn.profile("MATCH (p:person) RETURN p.id AS id", &[])?;
let slowest = profile.stages[0].ops.iter().max_by_key(|op| op.nanos);

// Bulk
let mut people = conn.appender("person")?;
people.append_row((1i64, "Ada"))?;
let loaded = people.close()?;
```

Design rules: `Database: Send + Sync` (one per process per graph), `Connection` cheap and single-threaded, rows borrow from a result arena (zero-copy strings), every blocking call has a `_timeout` variant, no async in the public core API (an `async` adapter feature wraps via a worker for s3-heavy apps).

`Database::open` takes a path and nothing else, and `open_with` is the second constructor for the callers that configure something. A required configuration argument is a tax charged to every user to serve the few who set anything, and `Config::default()` typed by everybody is a phrase that teaches nothing. `Config` itself is a builder with defaults that work: the memory budget the caches size themselves from, the thread count the executor picks when it is zero, and read-only, which opens the file on a descriptor this process cannot write through so that a database on a read-only mount opens and a statement that would write is refused by name rather than by errno.

The split is what the rest of the program is built on. A `Database` is a path and a configuration that have been checked against a real file, holding no descriptor and no cache, which is why it is shareable without a lock. A `Connection` is a file handle, the caches above it, and a plan cache, which is why it is not: reads through one handle seek, so two threads sharing one would serialize on the seek position at best. Taking one costs an open and a catalog load, tens of microseconds, so a connection per thread or per request is the intended shape and a pool is an optimization rather than a necessity. Every binding on the C ABI inherits this split (`dx/02` §3), which is why the Rust API has it first, and the C ABI's runtime ownership check is the same rule this API gets from the borrow checker for free.

A connection reads the database as of when it connected. It keeps the header it opened at, so a write another connection published since is not visible to it, and a reader that wants the latest catalog takes a new one. Making it otherwise means re-reading two header slots per statement, which is the entire cost of a warm query, so the answer to it is the snapshot machinery of `docs/08-transactions-mvcc.md` and not a read on the hot path.

Rows come back as columns and values, and `rows.iter()` is the typed view over them (`dx/04` §4). A `Row` borrows the result, so `let (name, born): (&str, Option<i64>) = row.get()?` reads the bytes the executor already materialized and copies nothing, and a caller that wants an owned `String` asks for one and pays for it there. One column at a time is `row.get_at(2)` by position and `row.get_by_name("name")` by the name the statement projected, and the untyped `row.value(2)` is still there for a caller doing its own matching, because the typed layer is built on the values rather than in place of them. Reading by name compares a column name per row and measures about five times reading by index, so a loop over a large result hoists `result.column_index("name")` out of itself and reads by position; that is the only performance advice this API has.

The two ways a typed read can fail are deliberately different conditions, and the difference is the one a program tests. Asking a `STRING` column for an `i64` is `22G03 invalid value type`, a data exception the standard defines, with both type names and the column's name in the message. Asking for a column the result does not have, by name or by index, or destructuring a three column row into a two slot tuple, is `ZuError::InvalidArgument` and carries no condition code, because no value was involved: the caller and the query disagree about the shape of the answer, which is a bug in the program and not a condition in the data.

A failure the engine raised as a condition carries the whole error model of `dx/03` §5 rather than a sentence to read it back out of. `err.diagnostic()` gives the record, and on it are the code, the class those first two digits name, the standard's text for the condition, the severity, the place, the line that place is on and the page the condition is written up on; `err.retryable()` is the answer a retry loop tests, true for a transaction rolled back with nothing done and for a write that lost to a concurrent one, false for text that will not parse however many times it is sent. The place is a `Position` with an offset as well as a line and a column, so a caller pointing at the token slices the statement at the offset rather than counting newlines to find it again, and `excerpt` is the whole line that offset falls on, quoted at the moment the condition was raised, for the caller that still has the error and no longer has the statement. A failure with no place has `None` rather than a guessed one, and the message keeps saying the position too, so a program that only prints the error still prints a complete report.

A wrong program is held to the same standard as a right one, and `crates/zu/tests/misuse.rs` is where that standard is written down: 17 deliberately wrong programs, each with the phrases its message owes the caller. Clear is three things there. The message names the thing the caller named, being the file they opened, the column they asked for, the parameter they left out. It says what was expected instead wherever there is something to say. And it is the engine's own sentence rather than a syscall's, because "failed to fill whole buffer" is a true statement about a read that tells nobody which file was not a database. The failures that really are the operating system's, a database that is not there and a create over one that is, keep the `ErrorKind` a program branches on and gain the path the system declined to name, which `crates/zu-zu1/src/vfs.rs` adds at the one place every open goes through. A file too small to hold a header and a file of the right size and the wrong kind are the engine's answers rather than the system's, and both name the file and say which of the two it was.

The other two thirds of that line are no crash and no leak, and a leak is invisible from inside the call that caused it, so it is checked from outside twice. Every case is followed by a read of the database it was aimed at, which is what a session or a file handle a failure left pinned would end. And the failing opens are repeated five hundred times, past the descriptor limit a Unix process starts with, which is what a handle left behind by every failure would end. The suite also writes down what is not misuse, since a decision nobody wrote down is a decision somebody reverses by accident: a parameter the statement does not read is bound and ignored, a label no element carries matches no rows rather than raising, closing a prepared statement twice answers false rather than raising, a value of the wrong type compared against a column is false rather than a failure, and a stop that arrived while nothing was running is kept and spent on the next statement rather than dropped. `tamnd/zu-python` carries the same suite against the same list, which is what makes these the client program's answers rather than this client's.

Parameters go the other way and `params!` writes them: `&params! { "id" => 42, "ids" => vec![1, 2, 3] }` binds by the names the statement uses, without the `$`, which is the same spelling the C ABI and the JSONL protocol use. It expands to an array literal rather than a `Vec`, so the bindings live on the caller's stack and the `&` is the slice the query methods take, with no allocation for the call itself. Every Rust type that is a value converts with `From`, including lists, options as null, and temporals; a string that means a date does not, because `date($when)` is where the caller says which calendar type it meant and the wire has no business guessing that from the characters.

`crates/zu/benches/rows.rs` gates the claim that the typed layer is free. Tuple destructuring measures 0.97 to 1.12 times the same read written as a `match` on `Value`, and one borrowed string column 1.09 to 1.53 times, both of them under a nanosecond and a half per row on results of a hundred thousand rows. The defect the ceilings exist for is a string that starts being copied, which allocates per row and lands at eight times and up.

`conn.query_stream` is the same statement read a batch at a time instead of all at once (`dx/04` §4). It takes a sink, hands it a `Batch` of rows borrowed for the length of the call, and the sink answers `Flow::More` or `Flow::Stop`; `query_stream_batched` is the same with the batch size named, for a caller writing Arrow record batches or HTTP chunks of a size of its own. It returns a `Streamed` rather than rows, because by then the rows are gone: the column names, how many rows were handed over, whether the caller stopped it, and whether the engine made the rows as it handed them over or had to make them all first. A sink is the shape rather than a cursor because a cursor over this engine would have to hold a borrow of the graph and the operator state across a caller's call, and the crate forbids unsafe, so the honest version of that is the callback that already has both.

Not every statement can answer its first row before it has read its last, and three of them never can: ORDER BY does not know which row sorts first until it has read the last one, DISTINCT is the same argument with a set instead of a sort, and an aggregate has no row at all until its groups close. Those run whole and are cut into batches afterwards, so the caller's loop is the same and `Streamed::streamed` is what says which happened. SKIP and LIMIT do stream, spent across the batches rather than inside each one, so a streamed answer is the buffered answer row for row. `Flow::Stop` and an exhausted LIMIT both stop the scan under it at the next morsel, which is the boundary an interrupt is answered at, and a sink that returns an error returns that error from the call unchanged.

`crates/zu/benches/stream.rs` measures the trade over a scan of two hundred thousand rows. Streaming costs 1.18 to 1.75 times the wall clock of the buffered read, which is real and is the price of interleaving the query with the consumer instead of running two tight loops, and it holds 0.018 times the bytes: one batch and the morsel feeding it against every row of the answer. A caller that reads the first batch and stops pays 0.015 of the whole scan. The bytes are counted by an allocator that records the live heap above where it stood when the statement started, because peak resident set counts every page the block cache touched and both sides touch the same ones.

A plan comes back as operators and a profile comes back as counters, both of them structures a program reads rather than text a program parses (`dx/04` §4). `conn.explain_plan` gives a `QueryPlan`: the operator tree, the columns the statement answers with, the parameters it wants bound, and whatever the optimizer wanted said about the plan that the tree does not carry. A `PlanNode` says what the operator is in `op`, what it is working on in `detail`, which bracket group it belongs to, which variables it introduces, and which tables it touches, so a viewer colouring the expands or a test asserting that a scan reached an index asks a field rather than a substring. `conn.explain` is `QueryPlan::render` and nothing else, which is what keeps the listing and the structure from ever describing different plans.

`conn.profile` runs the statement with the counters on and returns a `Profile`: one `StageProfile` per stage with its sink, its row count and its wall time, and one `OpProfile` per operator with pulls, rows, the flattened row count, the optimizer's estimate and ceiling where there was one, and self time with the children's time taken out. The operator's kind and its detail are separate fields there too, so grouping a hundred profiles by operator is a comparison rather than a parse, and `qerror` and `bound_violation` are the two derived numbers worth asking for by name: how far the estimate was out, and whether the count passed a ceiling the optimizer promised, which is a bug rather than a number. Profiling costs the execution, so a caller that wants a plan beside a latency it measured elsewhere wants `explain_plan`, which compiles and renders and runs nothing. A statement that writes is refused, because it runs as the parts it was split at its write into rather than as the one plan a profile describes.

`conn.interrupt()` hands out the one part of a `Connection` another thread may touch: the handle that stops the statement running on it and counts the rows it has read so far. A statement runs on the thread that asked for it, so stopping one means having taken the handle before the call, which is the shape both callers that want this already have, a shell answering a keystroke and a server answering a client that hung up. Asking is a relaxed store, the answer comes back at the next chunk boundary as `ZuError::Interrupted` and carries no condition code because nothing failed, and the connection runs the next statement as if the stopped one had never been asked for. Clearing the handle is the caller's to do and belongs before the next statement rather than after the stopped one. §2 has what the executors check, what the count is counted in, and what it costs.

`crates/zu/benches/connect.rs` holds both halves of that to a number, and the second is the one that matters: the warm point read through a `Connection` measures 0.99 to 1.03 times the same read through the engine's own `Session`, which is the noise floor of two ten-thousand-read medians. A public API that costs something over the engine is one the people who care about latency route around, so it is gated rather than asserted.

Loading data goes through an appender rather than through statements. `conn.appender("person")` gives one, `append_row` takes a row as a tuple or a slice of fields, and `close` returns how many rows went in. A row is every column of the table in the order the table declares them, and a column is a position rather than a name, because naming the columns per row costs a lookup per value on the one path where per-value cost is the whole story. The reason for the type is the arithmetic: a statement per row is a commit per row, and a commit is the expensive part, so a million rows loaded that way is a million commits. Buffering makes it one.

A flush is that one commit. The buffered columns are sealed into the data file as segments and the log gets a single frame naming them, which is the bulk-load WAL bypass of `docs/08-transactions-mvcc.md` §6: the log stays the same handful of bytes whether the flush carries ten rows or ten million. The fold that follows seals those segments into the base the query path reads, so when a flush returns the rows are both durable and visible, and before it returns neither. That fold costs time proportional to the table rather than to the batch, which is the whole reason to buffer: flush once per load, not once per row.

`crates/zu/benches/append.rs` gates both ends. Buffering a row costs 26 to 42 ns on a two-column table, one column of which is a string and so costs a copy, which is what says the row path allocates nothing. Two thousand rows loaded with one flush cost 0.0007 to 0.0011 times the same rows loaded with a flush each, both timed in one run, which is the design stated as a ratio.

Because a commit is durable at the log frame and visible at the fold, a crash between the two would leave rows on disk that no statement could see. Every writable open therefore replays a sidecar log that still has something in it and folds it before the first statement runs, so that window closes at the next open rather than staying open forever. A read-only open cannot fold and does not pretend to: it reads the base as the last fold left it.

Data a caller already holds does not have to be loaded at all. `conn.register(frame)` names columns that are in the caller's memory as a table of that connection, and a statement matches them under that name the way it matches a stored table. Nothing is copied, at registration or at read: a frame is a name, a pointer and a length per column, and whatever handle keeps those bytes alive, and a scan of one builds vectors that point straight into them. That is the same trick DuckDB's replacement scan plays on an Arrow array, and it works here for the same reason, which is that a vector was never more than a pointer, a length and a type. The layouts that already agree are read where they lie: eight-byte integers, doubles, and the characters behind a string column, which never move even though the sixteen-byte views over them are built per chunk. The layouts that do not agree widen into the morsel arena as each chunk is scanned, which is a 32-bit integer column, a float column, a bitmap, and the microseconds Arrow counts a timestamp in against the nanoseconds this engine counts one in. So a statement reading one column of a hundred touches one, and reading it twice does not widen it twice as a conversion at registration would.

`Column` says what a value means and `Layout` says where its bytes are, and the two are deliberately separate: the engine never sees an Arrow schema, only widths and pointers, because what kind of Arrow a caller is holding is the client's business and not the engine's. Everything that can fail is checked once, when the frame is registered: alignment, an unsigned value too large for the signed lane, a scale that would overflow, a string offset outside its buffer. A read of a registered frame cannot fail, which is what lets a scan be a loop rather than a chain of checks. A frame is read only and has no edges, so a statement that writes one is refused by name; ids count down from the top of the table id space while the catalog counts up from zero, so a registration never collides with the file's own tables; and registering a name that is already registered replaces what it stands for while keeping the id, so a prepared statement stays bound to the same table. `conn.unregister` takes one away and a statement already running keeps reading the one it started with, because a registration builds a new set rather than editing the one in use.

`crates/zu/benches/frames.rs` gates the claim as a slope rather than a constant, against the cheapest copy there is. Ten million rows of two columns register in 0.1 ms against 19 ms to `memcpy` the same 152 MiB, and registering a hundredth of the rows takes the same time, because what registration walks is the columns and not the rows.

## 2. CLI (`zu`)

```
zu shell                           # REPL on a database in memory, no file made
zu shell social.zu1                # REPL: readline, tables, timing, EXPLAIN
zu query social.zu1 -c "MATCH ..." --format json|csv|table|arrow
zu lsp --stdio [--db social.zu1]   # language server for an editor, over stdio
zu copy --from follows.parquet --to social.zu1 --table Follows --reorder degree
                                   # a column that is neither src nor dst loads
                                   # as an edge property of that name: from the
                                   # parquet schema, or from an LDBC style csv
                                   # header (:START_ID,:END_ID,name:INT64)
zu convert social.db social.zu1    # engine ↔ engine
zu verify social.zu1               # CRC/structure audit
zu stat social.zu1 [--format json] # sizes, encodings, bits/edge, cache stats
zu analyze social.zu1              # rebuild the optimizer's COLOR summaries (§07 §6)
zu corpus conformance/cases        # run the cross-client conformance corpus (§7)
zu bench ldbc --sf 1 --engine zu1  # built-in benchmark harness (§11)
zu s3 gc s3://bucket/graphs/social # manual GC / checkpoint / inspect manifest
zu mcp social.zu1                  # MCP server over stdio (2026 table stakes)
zu version [--format json]         # version, C ABI revision, features, engines
```

REPL niceties are product features, not extras: `\d` schema, `\timing`, `EXPLAIN (ANALYZE, FORMAT text|json)` with per-operator rows/time/factorization stats, ASCII plan trees.

Naming a file is optional, and leaving it out is not an error. `zu shell` with nothing after it opens a database in memory and says so in its greeting, because somebody trying the language out wants a prompt and not a decision about where a file they will delete in a minute should live, and a file appearing in the working directory they did not ask for is the opposite of that. `zu shell :memory:` is the same thing spelled the way every embedded database spells it, and it makes no file called `:memory:` either. Everything the session can do it can still do: the same catalog, the same writes through the same log, the same recovery, all of it in memory and all of it gone when the process is.

Which shell you get is answered rather than asked. Standard input being a terminal is a question `zu shell` can settle for itself, so a person gets the editor and a pipe gets the frames, and `--format jsonl` is there for the harness that drives zu under a pty and would otherwise be handed a prompt it never asked for. The editor is multi-line by default: return runs a statement whose brackets and quotes are closed or that ends in a semicolon, and adds a line when they are not, so a pattern that reads as four lines is typed as four lines. `Ctrl-J` adds a line whatever the text looks like, which is the escape hatch for the statement the completeness rule reads differently from its author. Up and down walk the lines of the buffer first and the history second, so editing the middle of a three-line MATCH does not throw it away and a one-line buffer is still one key from the last statement. `Ctrl-A`, `Ctrl-E`, the arrows, `Ctrl-W`, `Ctrl-U` and `Ctrl-K` are the motions and the kills every terminal has trained, a modified arrow is a word motion whichever modifier the terminal spells it with, `Ctrl-L` repaints, `Ctrl-C` abandons the line and keeps the session, and `Ctrl-D` on an empty line leaves, as do `quit` and `exit`. A history that outlives the process is the rest of this section and lands with it.

Colour and completion are the two things a person typing wants that a plain line editor does not give, and both are written here for the reason the editor is. `highlight.rs` is a scanner and not a parser, because the only thing that can be said about `MATCH (a:Per` is what its characters are and a parser's answer to a half typed statement is a syntax error rather than a colour: keywords, strings, numbers, comments and `$parameters` each get one of the sixteen colours every terminal has had for fifty years, the escapes go into the text that is written and never into the text the geometry is measured from, and `NO_COLOR` with any value or `TERM=dumb` turns the whole of it off. Tab completes against the open file rather than against a word list, which is the half worth having: a colon takes labels and rel table names, a dot takes the properties the graph types declare, and anything else takes keywords, tables and graphs, all filtered by what was typed and all gathered again after every statement, since a statement is how a table comes into being. One candidate is inserted, several insert what they share and print the rest in columns above the prompt, and a keyword comes back in the case it was typed in, so `matc` finishes as `match` and `MATC` as `MATCH`. A tab inside a string or a comment does nothing, and neither does a tab on nothing, because a screen of every keyword in the language is not an answer to a question anybody asked. The keyword list is a display list, so a word missing from it comes out uncoloured rather than wrong, which is the trade for keeping the scan a scan; the tree-sitter and Shiki grammars this section also lists are for editors and for the documentation, where a real grammar earns what it costs.

The backslash commands are the questions the shell answers itself. `\?` lists them, `\d` lists the tables with what each one holds and what a rel table joins, `\d NAME` prints one table's columns with their declared types and whether any row leaves them out, `\l` lists the graphs, `\i FILE` runs the statements in a file, `\timing` prints how long each statement took, and `\q` leaves. They are psql's spellings because a database user arrives with those in their fingers, and they are here rather than in the language because the questions they answer are the ones a person asks between statements and the language has no catalog view to ask them through. The columns come from the property directory rather than from the declared graph type, since a table loaded from a CSV has columns and no declaration and a `\d` that read only the declarations would tell that user their table is empty. A file read by `\i` is cut at its semicolons rather than at the balance rule the editor uses, because a person typing is waiting and a file is not, and it stops at the first statement that fails and says which one that was: a file is a program, and the statement after a failed one was written expecting it to have worked.

An answer taller than the window is paged rather than scrolled past. Space takes the next screen, return takes one row, and `q` or `Ctrl-C` stops printing, which are `more`'s bindings and therefore the ones a terminal user already has. There is no going back and no alternate screen, on purpose: the rows go into the terminal's own scrollback, where the terminal's scrolling and the terminal's search already work, and a pager that took the screen away would owe the user both of those back. `$PAGER` is not spawned either, since handing the rows to whatever that variable names is handing a user's data to a program zu did not choose, on top of leaving raw mode and hoping the child gives the terminal back the way it found it. What fits is printed the way it always was, so a one-row result waits for nothing.

None of that is a dependency. The workspace has no terminal crate and no line editing crate, and the reason is the same one T7 gives for the binary cap: a line editor is the part of a database people judge in the first ten seconds, and owning it costs one file of syscalls, `crates/zu-cli/src/term.rs`, against a dependency tree that would arrive with its own opinions about signals, threads and Unicode tables. Everything above those syscalls is pure. `keys.rs` turns bytes into keys, including an escape sequence split across reads, which is the normal case on a slow link and a first-class result rather than a guess. `line.rs` turns keys into a buffer and returns the escape sequence that shows it, so the geometry of a wrapped multi-line statement is checked by a test that asks where the cursor would be drawn rather than by a person looking at a terminal. Every escape written is ANSI, which the Windows console has spoken since 1803 and which is the floor `install.ps1` already claims, and a platform with neither termios nor a console reports no terminal and falls back to the line loop, which is a smaller promise honestly kept.

Raw mode is held while a statement is typed and dropped while it runs, so a query that takes a minute takes it with the driver back to normal and `Ctrl-C` at that moment is the signal it has always been rather than a byte nobody is reading. What that signal now does is stop the statement instead of the process, which is the paragraph after this one. `crates/zu-cli/benches/editor.rs` holds the typing path to a number, since a redraw rebuilds the whole buffer per key: 0.21 to 0.46 microseconds for a key on a one-line statement and 0.47 to 1.03 on a six-line one, the spread being what else the machine was doing, 2.17 to paint that six-line statement and 2.85 for a tab weighed against a hundred labels and a hundred tables, against a 50 microsecond ceiling in `bench/budgets.toml` that a per-character allocation or a reparse per keystroke would not fit under.

`Ctrl-C` on a running statement stops the statement and keeps everything else, which takes a word the engine reads and a handler that writes it. The word lives on the session, rides with the switches in `exec::Options` so that no execution path can be the one that was never wired, and is read at the boundaries both executors already stop at: the single pull entry point of the chunk executor, which every operator's inner loop goes through, so a filter rejecting a million rows without emitting one is still interruptible, and the stop flag the push pipeline's workers already test per morsel, which folds the ask into a load that was happening anyway. A stopped run is an error rather than a short answer, because workers that drained at their next boundary hold a piece of a result and a piece of a result printed as a result is worse than no result. Stopping is not failing, so `Interrupted` carries no GQLSTATUS, the standard having no condition for it, the session stays warm and answers the next statement, and the ask stays where the caller put it until the caller clears it, since a handle that cleared itself would race the statement still winding down. The signal handler does nothing but set an atomic, which is all a unix handler may do, and the shell polls it rather than acting inside it. Fifty milliseconds from the press to the answer is the number, and it is asserted on all three surfaces rather than described: `crates/zu-cli/tests/press.rs` drives the shell under a pseudoterminal, presses, and reads the interrupted line back at 11 ms; the C ABI's stop test times the ask against the return of `zu_query`; and the Python client's suite times a press against the `KeyboardInterrupt` it raises. The shell's watcher wakes two hundred times a second because a press pays that wait twice, once for the wake that reads the flag and once for the wake that finds the statement over.

Progress rides on the same handle, because a person watching a statement that has taken ten seconds is asking a question the engine can already answer. The count is rows read from storage, incremented once per chunk at the scan and once per claimed morsel in the pipeline rather than once per row, so the counter is a relaxed add per thousands of rows and not a shared word on the hot path. The shell runs a statement on a scoped thread only when it has a terminal, so the JSONL path and every snapshot around it spawn nothing, polls two hundred times a second, and paints nothing for the first four hundred milliseconds: a statement that answers immediately must not flicker a progress line on the way. What it paints is the elapsed time, the rows read grouped in threes, and the fact that `Ctrl-C` stops it, redrawn in place and erased before the answer goes out. A statement the user stopped says so and says the session survived, the process exits 130 if that was the last thing it did, which is the number a shell reports for a process killed by the signal, and a host on the C ABI reads the same fact as `ZU_INTERRUPTED`.

`zu shell --format jsonl` is the same session over a pipe, one JSON frame per line, for a harness or an editor rather than a person: `query`, `prepare`/`execute`/`close_stmt`, `explain`, `explain_analyze`, `hello`, `quit`. The two explain frames are deliberately distinct. `explain_analyze` runs the statement and reports what each operator actually did; `explain` compiles and renders and runs nothing, which is the one a caller can afford beside a latency it measured separately, and the only one that is safe to ask about a statement that writes.

That wire is a protocol rather than an output format, so it is versioned and written down: `docs/api/jsonl-protocol.md` is version 1, and the first line of every session is the greeting that names it, before any line has been read. The number moves when a frame or a reply changes meaning and never when one is added, which is what lets a client check it once, ignore the fields it does not know, and keep working across a release; `hello` asks for the same object again, for the client that attached to a session somebody else started. Parameters take the five JSON scalars and, because the data model already implies the mapping, an array as a list and an object as a record, nested as deep as they are written. A temporal has no spelling on the wire on purpose, since JSON has no date and a string that looks like one is a string, so a statement wanting one calls `date($text)` and says which calendar type it meant. The two references are the exception that proves it: a graph and a binding table are values a statement can be handed and neither is a JSON shape, so each is written as an object with one dollar named member, `{"$graph": "/social"}` and `{"$table": {"columns": [], "rows": []}}`, and a dollar sign is the one character no field of a record can begin with. Failures keep the distinction the SDKs make: a condition the engine raised comes with the GQLSTATUS code, the standard's text and the severity as fields, and a fault of the protocol itself, a malformed frame or an unknown op, comes with a message and no code rather than a plausible one.

`zu lsp --stdio` is the language server, and it is this binary rather than another one. A server shipped separately drifts from the engine it describes, and the day it drifts is the day it tells somebody a table exists that does not, so the completion list comes out of the catalog the shell reads, the diagnostics come out of the front end that would refuse the statement, and the colours come out of the scanner the prompt paints with. Five things are served, which are the five an editor is judged on: diagnostics, completion, hover, formatting and semantic tokens. Nothing here runs a statement, because an editor that ran what was in the buffer as the buffer was typed would be an editor that deleted a graph on the way to writing `MATCH`. The transport is headers and a JSON body over standard input and output, written on `zu_json` the way the argument parsing is written by hand, since T7 caps this binary at 15 MiB and a JSON-RPC framework is not worth a megabyte of it.

`--db` is optional and it is the whole difference between an editor that knows the language and one that knows the file. Without it the diagnostics are the parser and nothing behind it, which is everything that can be said about text with no catalog: a syntax error at a place, or nothing. A server with no database that complained about `Person` would be complaining about the user's file being somewhere else. With one, the database is opened read only, because an editor is a reader and a server that took the write side would lock the file the user is about to open a shell on, and the check becomes a prepare, which parses, binds and plans without running, so an unknown function and an undefined variable are squiggles rather than surprises. A file that will not open is published as a warning and not a reason to exit, since the parser half still works. Labels are the case the binder does not cover: `MATCH (a:Persno)` prepares, plans and runs, and returns nothing at all, which is the answer a misspelling deserves least because it looks exactly like a table that is empty, so the front end warns about a label the catalog does not carry and warns rather than refuses, a label being a name a statement is allowed to write before the table exists. Telling a label from a map key is the bracket it sits in, `(a:P)` and `[:P]` against `{name: value}`, and the text is cut into tokens the way the formatter cuts it, so a colon inside a string or a comment is not a colon at all.

Formatting moves whitespace and nothing else. The test that says so compares the token stream before and against after, and runs the formatter over its own output to check it settles, over thirteen inputs chosen for being awkward. A formatter that also re-cased keywords would be a formatter that renamed `count` and `abs`, since those sit in the same display list the highlighter colours with, and a tool that edits the text it was asked to lay out is a tool nobody leaves on save. The lexer underneath is deliberately not the engine's: the engine refuses a string that is not closed and an editor buffer is a string that is not closed several times a second, so an unterminated string or comment here runs to the end of the text as one token, which is the reading that keeps the rest of the buffer from being re-read as code halfway through a word.

Positions are counted in whatever the client asked for. The protocol's default is UTF-16, a number that means something to an editor written in JavaScript and nothing to anybody else, so a client that says it reads UTF-8 gets UTF-8 and a column is then a byte offset with no conversion at all, which on a document being retyped a character at a time is the difference between free and a walk over the text per keystroke. `serve` takes a reader and a writer rather than reaching for the process's own streams, which is what lets twenty protocol tests drive a whole session through a pair of buffers with no editor and no subprocess, and a protocol implementation nobody can test without an editor open is a protocol implementation nobody tests.

`editors/vscode` is the extension that bundles that server, and the thing worth saying about it is how little of it there is. It starts `zu lsp --stdio` and gets out of the way. There is no second parser in it, no keyword list, no completion of its own and no copy of anything the engine knows, because an extension holding any of those is a thing that drifts from the engine in the gap between two releases. The binary is found in three places in the order a user would expect to win: a path they set, then the one bundled in the package, then `zu` on `PATH`, which are respectively the build somebody is testing, a marketplace install, and a `cargo install` or a package manager. None of the three being there is a message with a button to the setting rather than a stack trace, since the usual reason is that zu is not installed yet.

`zu.database` is the setting that matters and it is the same difference `--db` is. Without it the editor knows the language, with it the editor knows your file, and which one you have is on the status bar because it is the one fact about the server that is invisible from anywhere else in the window and it decides whether completion has any table names in it. Clicking the bar lists the `.zu1` files in the workspace and includes no database, since a query file written before its database exists is normal and there has to be a way back to it. What the extension decides before it talks to the editor at all is a command line, so that half is a file of its own with no `vscode` import and the tests beside it run under plain node in a second: a relative path is from the workspace folder rather than from wherever the editor was launched, a `~` is a home directory because a settings file is a text file and people write `~` in text files, and the binary is called `zu.exe` on the one platform that calls it that. The manifest is checked against the code both ways in the same second, since a command contributed with no handler is a menu entry that throws when it is clicked and a handler with no contribution is code nobody can reach.

The extension carries a TextMate grammar and it is the generated one, byte for byte the copy the website uses, checked by `cargo xtask grammar --check` and again by a test in the package. It is there because a file is coloured the moment it opens and a server takes a moment to start; once the server is up the semantic tokens it sends are what you are looking at.

`zu stat --format json` prints the same facts as one object, including the store's size split into schema, free and data. The schema figure is what a database of this shape costs holding nothing, and it exists so that a tool dividing a store by the graph in it can subtract the part that is not the graph. Four blocks of 256 KiB is more than most test fixtures weigh, and a bits-per-edge figure that has not had them taken out of it is a measurement of the header.

`copy`, `convert`, `verify`, `stat` and `version` all take `--format json` and print one object on stdout, so a pipeline never parses a column layout meant for a terminal. `verify` is the exception that proves what the flag means: its JSON verdict goes to stdout whether the file passed or not, because the verdict is the answer that was asked for rather than a diagnostic about the answer, and an auditor recording a fleet reads one stream and gets both. `zu version --format json` carries the crate version, the C ABI revision, the zu1 format version, the compiled features and the engines this build supports, which is the four-line answer a bug report needs and a build system tests against.

Help is generated from one table, and that table is the same source the dispatch, the per-command pages and every usage message come out of, so a mistyped command line prints exactly the synopsis the documentation carries. Every subcommand has a one-line summary, a synopsis, worked examples and a see-also. `zu --help --format json` is a supported versioned output, not a debugging aid, because the CLI reference pages are built from it; a test holds the table to the dispatch in both directions, so a command that ships without a page and a page without a command are both build failures rather than gaps nobody sees. Commands the specification names and this build does not carry yet say so and exit 2 instead of reporting themselves unknown.

The exit codes are the half of the interface a script reads: 0 success, 1 query error, 2 usage error, 3 file or io error, 4 corruption, 5 conflict, 130 interrupted. Where the failure is the library's, the code is derived from the error it returned rather than chosen at the call site, so a new failure path cannot invent a new code; where it is the command line's, every command routes through one usage reporter, which is why they all exit 2 and all print the same synopsis the page carries. A snapshot suite runs the built binary over every subcommand, in both formats where a command has two, and compares the whole transcript including stderr and the exit code against a committed file; what it scrubs is the version, the uuid, the temporary paths and every decimal, since a measurement in a snapshot is a clock. Text an operating system wrote stays out of those files and is asserted on its exit code instead, because a missing file reads one way on linux and another on Windows.

## 3. Server (optional, crate `zudb-server`)

- Thin: HTTP/1.1+2, endpoints `/query` (JSON), `/arrow` (Arrow IPC stream), `/healthz`, `/metrics` (Prometheus). Auth: bearer token. TLS via rustls.
- Statelessly serves one or more attached graphs; for s3 engine this is the horizontal read-scale deployment unit (readers poll manifests).
- Explicitly *not* a coordination layer, no cluster membership.

## 4. The C ABI, and the bindings on it

Python first (PyO3, Arrow-native `.to_arrow()/.to_pandas()`), then Node (napi-rs), WASM (browser demo, zu1 read-only over HTTP range requests), Swift last (post-v1). All bindings sit on the C ABI crate `zu-capi` (stable, versioned, generated header). Nine repositories compile against that header and nothing else, which is ADR 0005, so its shape is the one decision here that cannot be taken back once it is frozen: dx/02 R9 makes the surface additive after v1, and a signature that was wrong stays wrong in six languages.

The header carries the revision of that surface as `ZU_ABI_VERSION`, so a build system can compile one way against 0.9 and another against what comes after it without inferring the answer from a crate version that moves for unrelated reasons. The same string is a constant in the workspace, is what `zu version` reports, and is checked by `cargo xtask package` against the `#define`, so a header and a binary that disagree are a failed check rather than an afternoon spent in a debugger.

The object model is the one §1 describes, because both come from `dx/02` §3. `zu_database_open` checks a path and a configuration against a real file and gives back a handle holding no descriptor and no cache, and `zu_connect` gives back the state that cannot be shared. A host that queries from four threads opens once and connects four times, which is the shape every pooling binding needs and the shape a single handle conflating the two could not express. `zu_open` stays as the convenience for a host that wants exactly one connection, and it returns the connection rather than both, since a database is only a path and a configuration and nothing outlives it. `zu_database_create` and `zu_create` are the same two calls over a path that is not there yet, and they exist because writing a client found that a C host could not make a database at all: a bulk load builds one with a table in it, and a host wanting an empty one to run statements against had nowhere to begin. They refuse a path that exists rather than opening it, because a create that quietly wrote into data somebody else put there is worse than a call the caller has to make twice.

`zu_database_memory` and `zu_memory` are the same pair again over a database that is nowhere: the blocks a file would hold are held in memory, and the log beside it too, so nothing above the file layer knows the difference and nothing survives the process. It is not a mode the storage layer grew but a second answer to one question, where a file comes from, which the engine now asks through a `Vfs` rather than of the filesystem directly. That is why it costs nothing on the ordinary path and why it is the same headers, the same log and the same recovery on either. A host reaching for it is reaching for a scratch graph: a test, a fixture, a load it is about to throw away, and in every one of those the point is not having to find somewhere writable first and not having to clean up after. Every call makes a database of its own, two connections on one handle are two views of one graph, and `zu_database_path` answers with a name that is deliberately not a path, since what the caller needs it for is an error message. `zu_database_is_memory` is how a host asks rather than parsing that name, which is the question anything that offers to back a database up has to ask first.

`zu_conn_duplicate` is the other half of the split, from the connection's side: a second connection on the database a connection is already on, made without a path. A pool that seeds itself, hands the database handle back and then wants to grow has a connection and nothing else, and until this call its only way to a second one was to keep the handle alive for the sole purpose of calling `zu_connect` on it later. On a database in memory there was no other way at all, since the name it answers with is not something to open. What comes across is the switches and the read-only setting, because a pool handing out connections configured differently from the one it was built from would be a trap nobody would look for; what does not is the plan cache, the block caches, the interrupt and the transaction, because those are exactly what makes it a connection rather than a second name for one. The two share the write side and queue behind each other to write, which is what two connections from one database do and is the only sense in which either is not alone.

Every fallible call returns a `zu_status` and writes what it produced through an out-parameter (`dx/02` R2). One returned pointer cannot say both "this failed" and "this succeeded and there is nothing here", and a binding that cannot tell those apart turns an empty result into an exception or an error into an empty result, which is the single most common bug in hand-written FFI wrappers. The out-parameter is written on every path, `NULL` when there is nothing to point at, so a caller who ignores the status is never left holding a pointer from the call before. `ZU_DONE` is the case that returning `NULL` could not express, and it is what a column of a result with no rows answers.

What a user reads comes back on a separate `zu_error` handle carrying the whole error model `dx/03` §5 fixes as fields rather than as one string to parse: the GQLSTATUS code, the standard text for it, the severity, the place, the line that place is on, the page the condition is written up on, whether running the same statement again could get anywhere, and the message. Those are what a binding needs as data rather than as prose: the code picks which exception class to raise, the severity decides whether to raise at all, the position underlines the token, the retryable flag decides whether a retry loop goes round again, and none of them survives being formatted into a sentence and parsed back out. A failure with no condition reports no code rather than a guessed one, because a binding mapping codes to classes has to tell a missing code from one it does not recognize. `zu_error_position` answers the same way about a place: `ZU_OK` and the line and column for a condition raised at a token, `ZU_DONE` for one raised somewhere a token cannot be pointed at, such as a division by zero, which happens while the statement runs. The message says the position too, and keeps saying it, so printing the message alone is still a complete report; the pair is for the caller that would rather point than read. The status enum stays small on purpose and carries no conditions: there are several hundred of those and no `switch` should ever be written over them. The engine's own error type maps onto the enum in one exhaustive `match` with no wildcard arm, so a new variant fails to compile there rather than reaching nine bindings as whichever status a wildcard happened to name. `ZU_INTERRUPTED` is the one non-zero status that reports nothing wrong: a caller stopped the statement, the connection is unharmed, and the next call on it runs normally.

The place is said twice because two callers want it two ways. `zu_error_position` gives the line and column a person reads and a caret is printed under, and `zu_error_offset` gives the byte the condition was raised at, which is what a caller slicing the statement, highlighting a span in an editor or mapping into a source map needs and what neither counting lines nor counting columns yields without walking the text again. Both answer `ZU_DONE` together, so a caller tests one. `zu_error_excerpt` is the line that place is on, quoted out of the statement, because the caller most in need of it is the one holding an error and no longer holding the text: a driver that logged the failure, a notebook that ran the cell an hour ago, a server that answered a request. It is the whole line rather than a window around the column, so the column stays a valid index into it and a caret built from the pair lands where the pair says; a line longer than four kilobytes is dropped whole rather than cut, since a cut line would put the caret somewhere else entirely. `zu_error_doc_url` is `https://zu.dev/docs/errors/` and the code, which every binding would otherwise build itself from the code and half of them would build differently, and `zu_error_retryable` is true only for `40000`, a transaction rolled back with nothing done, and not for `40003`, where the statement's completion is unknown and running it again could do the work twice.

Stopping a statement is the one call in the surface meant to be made from another thread while a connection is in use, so `zu_conn_interrupt` takes no claim on it and does not answer `ZU_MISUSE_CONCURRENT`: a cancellation that had to wait for the connection to be free could only ever arrive after the statement it was meant to stop. It sets the word the executors already check at a chunk of rows, so the statement stops within a vector rather than at the end of the query and answers `ZU_INTERRUPTED`, and the connection keeps its plans and its warm caches. An ask raised while nothing is running is dropped when the next statement starts, which is the rule the shell follows for the same reason: a `Ctrl-C` at a prompt must not end whatever the user types next.

Progress is the same watch said two ways, because two kinds of host want it two ways. `zu_conn_rows_read` is the poll, counting rows read out of storage from zero at each statement and holding its last value once one ends, which is what a host prints beside "cancelled" and what the shell's own progress line is built on. `zu_conn_set_progress` is the callback, called every `interval_ms` with the rows read and the milliseconds elapsed, and returning zero from it stops the statement exactly as the interrupt would. Rows read rather than rows answered, because the statement a person is waiting on is exactly the one reading a hundred million rows to answer one.

The callback runs on a thread of the library's, one per statement, never two at once and never after the call it belongs to has returned. That is a deliberate choice against calling it from the executor's own boundaries, which would give a host asking for a report every 100 ms one report per chunk instead, and which on a parallel stage would reach the host on several worker threads at once. What follows from it is stated in the header: the `user_data` pointer has to be usable from another thread, and the callback must not call back into the library on the connection it is reporting on. It costs a thread for the length of a statement, and only for a host that asked to be told about one, which is only ever a statement somebody is sitting and watching.

`zu_begin`, `zu_commit`, `zu_rollback` and `zu_conn_in_transaction` are the transaction boundaries, and the first three are the statements `START TRANSACTION`, `COMMIT` and `ROLLBACK` called rather than written. That is deliberate on both counts: they run that text, so a host that sends the words and a host that calls get the same parser, the same session state and the same conditions, and a host that would rather call gets a signature instead of a string to build, which is what a binding wrapping this in a block, a `using` or a `defer` actually needs. Every statement outside a transaction is already one, so these do not turn transactions on; what they do is make several statements one. `zu_begin` with a nonzero `read_only` starts a `READ ONLY` transaction, which is enforced at the statement that wrote rather than at the commit, so the host is told which statement was the one it should not have sent. Beginning inside a transaction is `25G01` rather than a nesting this engine does not have, and committing or rolling back with nothing running is `2D000` rather than a call that quietly did nothing, because a host that rolls back in an error path wants to hear that the transaction it meant to undo was not the one it thought. `zu_conn_in_transaction` is the one thing about a transaction that no statement answers, and the cleanup path of every block a binding offers needs it: it has to know whether the body already ended the transaction before it tries to. Closing a connection with one still running rolls it back, which is the only answer that does not depend on a destructor running somewhere.

`zu_appender_open`, the `zu_append_*` calls, `zu_append_end_row`, `zu_appender_flush`, `zu_appender_discard`, `zu_appender_close` and `zu_appender_free` are how values get into a table that already exists, which is the half of loading `zu_loader_create` does not cover: the loader builds a database that is not there yet, and this adds to one that is. A statement is the wrong shape for the job, since every row written as one is parsed, bound, planned and committed and the commit is the expensive part, so a million rows is a million syncs nobody asked for. An appender buffers rows and pays one commit per flush. A row is written a value at a time in the order the table declares its columns and `zu_append_end_row` is what makes it a row; the column is a position rather than a name because naming one per value would cost a lookup on the one path where per-value cost is the whole story, and `zu_appender_cols` and `zu_appender_col_name` are there for the host that wants to check the order it is writing in. A refused value ends the row it was in and the values that row had already written come back off, so what the loop writes next is a row rather than the tail of a broken one, and the error names the column and says what it holds rather than leaving a host to work out which of five columns it was. A rel table has no property columns: a row of one is the two ends of an edge as offsets into the tables it runs between, so those are its two columns, and a negative offset is refused where it was appended while an edge to a row that is not there is refused at the flush, before anything is written. `zu_appender_free` writes what is still buffered, because rows that were appended are rows the host meant to write, and what it cannot do is say that the write failed, which is what `zu_appender_close` is for; a host that wants the rows gone rather than written calls `zu_appender_discard` and gets exactly that.

`zu_result_gqlstatus`, `zu_result_notices` and `zu_result_notice` are the half of the GQLSTATUS envelope a host reading rows and errors could not see. The status a call returns says whether it worked; the completion condition says which way it worked, in the standard's own terms, and it is `00000` for a statement that answered with columns and `00001`, successful completion with the result omitted, for one that had none to give back. That is the value the JSON Lines protocol already writes into every record and the value a conformance harness grades, so a C host that had to work it out from the column count was reconstructing something the engine already knew. The notices are the conditions a statement raised and carried on through: an exception replaces a result and arrives as an error, while a warning rides along with one, because a statement that dropped a null out of an aggregate still has rows to give you and the standard still wants you told. A notice comes back as a `zu_error`, which is one shape rather than two, since a diagnostic record is a diagnostic record and the code, the standard text, the severity, the place and the doc page are the same accessors either way; what tells the two apart is `zu_error_severity`, so a binding that already turns one of these into an exception gets its warning class for the cost of reading a field. It is a copy rather than a borrow, so the rule for every `zu_error` a host is handed stays the one rule, free it, and the result keeps its own and can be asked again. An index past the end is `ZU_DONE` with the out-parameter cleared, which is what a host walking them gets at the end of the walk rather than a failure, and almost every statement raises none, so asking costs one call and no allocation.

Strings cross the boundary as a pointer and a length (`dx/02` R7), because most source languages have counted strings and a NUL-terminated parameter makes every one of them allocate a copy of a string that already knew how long it was. Each of those calls has a `_z` variant for a caller who genuinely has a C string, so the counted form is the default rather than the only form. A `NULL` pointer with a zero length is the empty string, which is what an empty string looks like coming out of Go and which building a slice from would otherwise be undefined behaviour.

A node is its own type across the boundary. `zu_result_col_node_offset` reads the row offset that identifies one, and `zu_result_col_i64` refuses a node column rather than punning it, which is how an internal row number otherwise reaches a user who asked for an identity.

Every column reads out a second way, a chunk of rows at a time, through `zu_result_chunk_count`, `zu_result_chunk`, and the matching `zu_result_chunk_col_*` accessors. Which one to reach for is a question of size. A point read wants the whole column, because the answer is small and one call beats a loop. Anything large wants chunks, because the whole-column call converts every row before it returns any of them and keeps the conversion alive until the result is freed: half a million rows of integers is 3.9 MB of buffer beyond the rows themselves, and a host that reads the first screenful and stops has paid for all of it. A chunked read converts the chunk it was asked for into a buffer of a fixed size that the next chunk reuses, so the memory is flat in the row count and the work is what was actually read. The measured numbers are 244 times less buffer and, on a host that stops after the first chunk, between 179 and 337 times less time; the whole-column scan is no faster, because summing a 16 KiB buffer while it is still warm makes up for the per-chunk call.

Not every value has a column to be read into, which is what `zu_result_cell` and the `zu_value_*` accessors are for. A temporal is a count and a unit, a list recurses, a node carries the table its offset counts in, and none of the three fits an `int64_t *`, so before the cell reader those values were visible to a C host and unreadable by it: `zu_result_cell_type` would say `ZU_TYPE_TEMPORAL` and nothing would say which temporal or how many nanoseconds. `zu_value_temporal` answers with the kind, the count and the offset from UTC, on the understanding that the unit follows the kind: days for a date, months for a year-month duration, nanoseconds for the other five. `zu_value_len` and `zu_value_at` walk a list, a path or a record with the same accessors that read the parent, which is what makes a list of lists a walk rather than a second API, and `zu_value_field` names a record's fields, which are in name order because that is what makes two records written in different orders one value.

A node value is a table id and a row offset, and an edge value is a table id and two of them, and the id is not a name. Two tables both number their rows from zero, so the id is the only thing that tells a node of one from a node of the other, and the catalog is the only thing that says what it is an id of. Every other client reaches a catalog through the language it is written in, and a C host had no reach at all, which left `zu_value_node` an answer a caller could compare and not one they could print. `zu_conn_table_name` is that reach and `Connection::table_name` is the same call in Rust. Node and rel tables share one id space, so one call answers for both kinds and a caller does not have to know which of the two it is holding. The name comes back NUL terminated with its length beside it, owned by the connection and good until the next call of it on that connection, because the catalog's own copy goes when the next statement that creates or drops a table replaces it and a pointer into that would be a use after free somebody finds in the field. An id no table has answers `NULL`, rather than a name that would be a guess. It is what took the ABI revision to 0.13.

A cell is a pointer into the result's own rows rather than a handle, so there is no `zu_value_free` and reading one allocates nothing: measured at a nanosecond a value, and faster over a whole int column than the whole-column accessor is, because that one builds a 3.9 MB buffer first and this one reads the rows where they already are. The price is that `zu_value_str` gives a pointer and a length and no NUL, since a string inside a list has no row and column to be cached under and a copy per element is a cost every caller would pay so that the ones using `printf` need not think; `zu_result_cell_str` is still there for a top-level cell, and it keeps the copy it makes. The other difference from the columnar accessors is strictness: `zu_result_col_i64` reads bools and nulls too, because a column is one host array and something has to go in every slot, while `zu_value_i64` on a bool is the caller asking the wrong question and answers `ZU_MISUSE`.

What that costs is pointer lifetime. A whole-column pointer is good until the result is freed, and a chunk pointer is good until the next call for the same column and accessor, which replaces its contents. A host that needs one chunk to outlive the next copies it, which is the copy it was making anyway on the way into a host array. Chunks are not promised to be the same size as each other, so a caller asks each one rather than multiplying: they are uniform today except the last, and they will stop being once a chunk is what the executor produced rather than a slice of what it already materialized. A result with no rows has no chunks at all, which is how the chunked path says what `ZU_DONE` says on the other one, without needing a status to say it.

A result goes out one more way, and it is the way a caller who already speaks Arrow wants. `zu_result_arrow` hands the whole of one over as an `ArrowArrayStream`, the C Data Interface's own struct, which the header declares behind the guard names the specification gives everybody, so a translation unit that already has them from `arrow/c/abi.h` or from another library gets one definition and not two and nobody has to install Arrow to compile against this. Nothing on that path is a copy: the arrays that cross are the buffers the executor filled, at the addresses it filled them at, which is what `QueryResult::into_columns` and `zu_arrow::Table::taken` are for, so an export costs a pointer a column and nothing at all a row where the chunked accessors cost a conversion a row. What pays for that is the one thing this call does that nothing else here does, which is spend the result. The handle goes in through a pointer to it and `NULL` comes back through the same pointer on every path, the failing ones included, because once the buffers have left there is nothing to read a second time and a handle to an answer with no rows in it is the shape a double free starts with. The connection goes in as well and may be `NULL`: a node column names its table out of the catalog, and with no catalog to ask it names it `#7` after the id, which is still an answer for a host that closed the connection and kept the result. Arrow is a default-on cargo feature rather than a hard dependency and the symbol is exported either way, answering `ZU_UNSUPPORTED` when the feature is off, because a binding that opens this library by name should learn what it can do from a status and not from a lookup that failed. Carrying it costs 421 KiB, 4.91 MiB of shared library against 4.50, and it is what took the ABI revision to 0.12.

Values get in through `zu_loader_*`, which is the other half of what a binding does and in v0 the only way to do it: `CREATE` and `INSERT` need a table and no statement makes one, so a host holding data and an empty file had nowhere to go. It is also the entry point the Rust appender and `zu copy` are already built on rather than a second mechanism beside them, which is why a client that agrees with the corpus through this loader agrees with the ones that do not use it. A loader is columnar for the same reason a result is: `zu_loader_table` names the node table, the rel table and how many rows there are, then one call per column and as many calls as you like for edges, then `zu_loader_finish`. The row count is given rather than counted from the first column, so a column with a value missing is an error and not a shorter table, and it is checked at the call that passed the column rather than at the end, where the caller no longer knows which one it was building.

`zu_loader_col_temporal` is `zu_value_temporal` read backwards, deliberately: one kind tag and the count each row holds in the unit that kind implies, so a date read out as 19782 days goes back in as 19782 days and a host needs one mapping rather than two. The two zoned kinds answer `ZU_UNSUPPORTED`, because a stored column has nowhere to keep the offset that makes them what they are, which is a fact about v0 storage rather than about the caller and reads as one. Strings go in as pointers and lengths and are checked for UTF-8 there, rather than read back later as something no query could have returned.

The loader copies every array it is given, which is the one place this ABI chooses a copy over a borrow. The alternative is a rule saying that every array a host passed stays alive and unmoved until a call it makes later, which no header comment can enforce and which a host that broke would discover as a corrupt database rather than as an error. Measured, the copy is free: the same table built both ways, once through the loader and once through `bulk_load_keyed` and `store_props` directly, runs within the noise of the filesystem either way, because a memcpy per column is nothing against a load that writes every one of those bytes to disk. Nothing reaches the file until `zu_loader_finish`, so a load either happened or did not, and a loader is spent afterwards, including after a finish that failed: every further call is `ZU_MISUSE_CLOSED` and freeing is all that is left. A loader freed before it finished wrote nothing and leaves the empty file it created for the caller to remove, since deleting a path this library was handed is not a thing a free should do.

Values also get in without getting in at all, which is `zu_frame_new`, the `zu_frame_col_*` calls and `zu_conn_register`. The loader copies because it is writing a database, and that is the right trade for a load; a host that already holds its columns in memory and only wants to ask a question of them is paying that copy for nothing, and the copy is usually the whole cost of the question. A registered frame is a table of one connection made of the pointers the host gave and of nothing else, and a statement naming it reads the host's own arrays where they lie: nothing is copied at registration and nothing is copied at read. This is DuckDB's replacement scan taken from first principles rather than reproduced, because the same idea, that the fastest way to load a table is not to load it, brings the same requirement with it, which is a way of saying when the engine is finished with memory it does not own. Frame table ids count down from the top of the id space while the stored catalog counts up from zero, so a frame and a stored table can be named in one statement and neither has to know about the other.

The layouts are the ones a host is already holding. `zu_frame_col_int` takes 8, 16, 32 or 64 bits, signed or not, with a scale that says what one value is multiplied by to reach the unit its meaning counts in, so Arrow's microseconds go in as microseconds and a scale of 1000; `zu_frame_col_float` takes 32 or 64; `zu_frame_col_bool` takes one bit a row, low bit first, which is Arrow's bitmap and this engine's alike; `zu_frame_col_str` takes Arrow's Utf8 and LargeUtf8 as offsets and a data buffer; and `zu_frame_col_view` takes Utf8View, whose sixteen bytes a row are already this engine's own view of a string, byte for byte. Sixty-four signed bits at a scale of 1 and sixty-four bit floats are the lanes the executor reads natively, and those columns cost nothing at all. Everything narrower is widened per scanned chunk into a buffer that the next chunk reuses, rather than once into a copy of the whole column, so the memory a frame costs is flat in the row count and a host that reads the first screenful pays for the first screenful. Strings never copy their payload on any path, only the views that point into it.

What follows from borrowing is the release callback, which is the whole reason the surface has one. The engine finishes with a host's arrays at a moment when no call of the host's is on the stack, so a return value could not say it and only a callback can. `zu_conn_register` does not spend the frame handle, on any path: the description is names, widths and pointers, the registration takes a copy of that, and the same handle registers on a second connection over the same memory. `zu_frame_free` ends the handle and not the memory. The arrays go back when the last table naming them goes, which is an unregister, a connection closing, or a frame handle freed that nothing had registered, and a statement already running keeps the frame it started with, so the callback waits for it. It runs on a thread of the library's rather than the caller's, which is the fact a binding needs most: a client holding a Python object as the owner has to take the GIL before it decrefs. An unwind out of it is caught rather than allowed to cross the boundary, since it would be unwinding through a drop. The engine reads a frame and never writes one, so a statement that would insert into, set on or delete from a registered name is refused with `25G03` at binding time rather than left to fail somewhere lower down, and registering inside a transaction is `25G01`, because a table appearing halfway through one is not something the transaction could then be rolled back over.

Configuration is the one thing that crosses by value, which R1 allows exactly because the struct is versioned: `size_t struct_size` comes first, `zu_config_init` stamps it, and every field after it is read only when that size says the caller's struct is long enough to hold it. A field appended later is therefore invisible to a binding compiled against the older header rather than fatal to it, and the alternative, an opaque handle with an allocator and a destructor, costs a heap allocation and two more calls to express three integers a caller already has on its stack. `zu_config_set` sets one option by name beside that, so a binding can forward a user's option map without this ABI growing a setter per option and without the binding hard-coding a layout it would have to keep in step. An unrecognized key is refused and named, because the binding has to tell its user which entry was the typo. A byte count is decimal and a suffix such as `MB` is deliberately not parsed here, since its two readings differ by 4.9% and the language the user typed it in is a better place to decide which one they meant.

The threading contract of `dx/02` §5 is checked rather than described, because a rule that lives only in a header is followed only by the hosts that were not going to break it. A connection may move between threads and may not be used from two at once, so every call claims it for its length and a second thread arriving finds it taken and gets `ZU_MISUSE_CONCURRENT` rather than a corrupted plan cache. A statement shares that state with the connection it was prepared on, so using one after the connection closes is `ZU_MISUSE_CLOSED` rather than a dangling pointer followed, and closing the statement afterwards is still the right thing to do. Both checks cost one uncontended atomic swap per call, which against a query is nothing. A result is the case where nothing needs checking: it owns its rows outright and holds nothing of its connection, so it stays readable after that connection has gone back to a pool, which is the ordinary thing for a host to do and no reason for an error.

There is one more way in, and it is the one nobody had to write a client for. `crates/zu-adbc` is an ADBC 1.1.0 driver: a `cdylib` a driver manager opens by name, `ZuDriverInit` as its entrypoint, and an Arrow stream as the only thing it hands back, so a program in Python, R, Java, Go or C++ that already has a driver manager has a zu client without a package of ours in its dependency list. It is cheap because ADBC is the one database interface whose result is Arrow rather than rows and this engine's result already is: the batches it returns are the buffers `zu-arrow` builds for the Python and TypeScript clients, cut where the caller asked, with no row built anywhere on the path. It sits beside the C ABI rather than on it, since both are surfaces over the same `zudb::Connection` and a driver going through C to reach a Rust engine would be describing in C what it has in Rust on both sides of the call; what the two do share is `zu-arrow` and the taken result under it, so the stream a driver manager reads and the stream `zu_result_arrow` writes are the same buffers built the same way. The forty function pointers of `AdbcDriver` are laid out by Apache's `adbc_ffi` rather than by us, because a field written into the wrong slot of that struct is a segfault in somebody else's process, and the five characters of GQLSTATUS go across as the five characters of `sqlstate` with the doc URL and the position in the detail keys 1.1.0 added. `docs/clients/adbc.md` is what it takes, what it refuses, and why.

## 6. The API model

Every generated description of the API is built from one file, `docs/api/model.json`, extracted from rustdoc's JSON by `cargo xtask model` and committed to the tree: the reference pages, the SDK feature matrix, the `zu.h` header, and the `api-map.toml` completeness check. `docs/api/README.md` documents its schema and what the generator does that rustdoc does not. CI runs `cargo xtask model --check` on a pinned nightly, so a pull request that changes the public API and does not regenerate the model fails, and one that does regenerate it shows the change in its own diff.

`docs/api/api-map.toml` is the other half: the model says what the API is, the map says what a binding owes it. Every entity is classified tier 1 (every tier-1 SDK exposes it), tier 2 (a binding may) or tier 3 (none does, and a reason is required). `cargo xtask api-map` joins the two and fails on a public symbol nothing classifies, on a classification for code that is gone, and, run against a binding repository's own map, on a tier-1 entity that binding stopped naming. The first of those runs as a test, so it fires on the machine of whoever added the symbol and not only in CI.

## 7. The cross-client conformance corpus

The map above says what a binding owes the API. The corpus says what a value means once it has crossed the boundary, which is the other half of the same problem and the one no API surface check can reach: nine clients in seven languages, each decoding values with code no other client shares, and the question is whether a value put in through one and taken out through another means the same thing.

`conformance/cases` holds it, as YAML files, each a statement and the rows it owes. Every value is a `{type, value}` pair, and the rule the encoding exists for is which types are written in quotes: INT64, UINT64, the floats and every temporal type are, because a bare `9007199254740993` is a number and a reader that hands it to a double gives back `9007199254740992`. A case that writes one of them bare is refused rather than read leniently. `conformance/README.md` is the schema and the reasoning.

A suite may also carry a `load:`, being a table of typed columns and the edges between its rows that every runner puts into each case's own database through its own bulk load path before the case runs. That is the half of the question an expression cannot ask, because a client that decodes a date correctly and encodes it a day early passes every expression case there is. It is bulk load rather than a statement because in v0 that is the only way in, and because every client has to expose a loader anyway.

A case may also carry `params:`, being values bound to the statement by name in the same encoding a row is written in. That is the same half of the question through the door a client actually uses, since a loader is a bulk path and a parameter is what an application binds all day. The one type a parameter cannot be yet is a list, because the C ABI has a bind call per scalar and none that carries a composite, and a case no C runner can run is not a case.

`crates/zu-corpus` is the Rust runner, the first of nine and the reference for the rest; `zu corpus <dir>` is the same runner in the shipped binary, for an unpacked artifact. It runs as a test in this repository so it fires on the machine of whoever adds a case. The cases stay here because they are versioned with the engine and gate its releases (ADR 0005). `tamnd/zu-kit` holds the other eight runners and not the cases, because a case that lives beside one runner is a case that runner cannot fail.

`cargo xtask corpus-pack` builds the release artifact, `conformance-<version>.tar.zst`: the case files as committed, their README, and a `manifest.json` giving the engine version, the case counts and a CRC32C per file. It is a plain tar of text and every language has a reader for it, which is the point. The archive is reproducible, because every header field that could carry the packing machine's clock or user id is fixed, so two mirrors of one release are comparable rather than merely trusted. `--check` packs and writes nothing, and runs on every pull request, because packing parses every case and an artifact that does not load is not a thing to find out about on release day.

Not to be confused with `conformance.toml` at the repository root, which shares a word and nothing else: that is what this engine declares it can do, for the gql-compat harness, generated by `zu conformance --declare`.

## 8. The terminology table

Nine repositories in seven languages write prose about one database. An element that is a `vertex` on one page and a `node` on the next is two data models to a reader who does not already know it is one, and the fix is one table rather than nine style guides that agree until they do not.

`style/zu/terms.yml` in `tamnd/zu-web` is that table: every term, the group it belongs to, a one sentence definition somebody wrote, and the forms that must give way to it. It is in the site's repository because the site is where this program's prose is published from and because the glossary it renders is the table. `cargo xtask terms` is the reader, and it is here, because the prose with the most readers is here and because a table checked by nine repositories against nine readers would be nine tables. `style/README.md` has the schema and the rule for adding a term.

What is checked is prose, and only prose: markdown, and the `//!` and `///` comments that become reference pages. Not identifiers, which answer to the language they are written in; not code spans or fenced blocks, because a check that fires on `Vertex` in a signature teaches people to ignore it; not link targets, which are addresses. A form matches whole words only, the last word of a form may pick up a plural `s`, the words of a multi-word form have to be one phrase, and case is ignored except where a form differs from its own term only in case, which is what lets `zu` refuse `Zu` without refusing every other capitalised word.

A page that quotes somebody else, or writes about another system in that system's words, exempts the form and says which: `<!-- terms: allow row group, vertex -->`. It has to name the forms, so it can never become a blanket switch, and a form it names that the page does not contain is reported as stale, which is the rule the API map follows for a classification of code that is gone.

Two consumers are named in the checklist and are not covered yet, deliberately and not quietly: the CLI's help text and the text of an error. Neither is extractable today, the help living in usage strings among a hundred other literals and an error's message being built where it is raised, and both become extractable when `cli.json` and `errors.json` exist, which are two items of the same release artifact contract. Checking them by grepping for string literals and guessing which ones a user sees would be a check nobody could trust the silence of.

CI runs it with zu-web cloned beside this tree, tracking that repository's main rather than a pin, because a word that changed meaning has changed for this repository the moment it changed for the site. The whole tree is 3.7 MiB of source and the check is about 14 ms, because forms are indexed by their first word: a line costs one hash lookup per word no matter how large the table gets, which is what makes adding a term a decision about the word and not about the budget. `cargo bench -p xtask --bench terms` asserts both, the cost staying linear in the prose and flat in the size of the table.

## 9. The word list and the two grammars

A statement is read in four places and run in one. `crates/zu-query/src/parser.rs` is the one that runs it and is therefore the definition of the language; the other three only look at a statement, because the shell colours a line while it is being typed, an editor parses a file that is half finished, and the site colours a block printed on a page. dx/13 §1 asks for the two grammars those three need, tree-sitter for editors and a TextMate grammar for Shiki, and the part worth deciding is not either grammar but what keeps four readers agreeing on which words zuQL has. None of the three is a second parser. Neither grammar decides what a statement means, and a statement one of them and the engine disagree about is a bug in that grammar rather than a dialect. One of the two is in this repository and one is not: the tree-sitter grammar is `tamnd/tree-sitter-gql`, which left `grammar/tree-sitter-gql` in August 2026 because a tree-sitter grammar commits its generated parser so that an editor can build it without the CLI, that file is 2.2 MB, twelve commits rewrote it, and every clone of the engine was paying for all of them.

`grammar/vocabulary.toml` is the one list, grouped by what a word is: a keyword the parser gives meaning to by position, a literal, a built-in function, a graph algorithm, a value type name. It is 191 words today, being 107 keywords, 3 literals, 20 functions, 10 algorithms and 51 types, and it records the date it was audited against the parser. `cargo xtask grammar` puts it where each consumer needs it, `--check` writes nothing and fails on any drift, and `--list` prints `kind<TAB>word` for whoever wants the list without a TOML reader.

Three files are written from it and all three are committed, `grammar/shiki/gql.tmLanguage.json` and `editors/vscode/syntaxes/gql.tmLanguage.json` here and `queries/highlights.scm` in the grammar's repository, because an editor package and the website consume the files rather than the generator, and all three are checked, so a word added to the list and not regenerated fails. The two TextMate copies are the same bytes and are a copy rather than a reference for one reason: a `.vsix` is a zip of one directory and a package cannot reach outside itself. The second consumer is the shell, whose table in `crates/zu-cli/src/highlight.rs` is checked rather than written: it is sorted for a binary search and read by a scanner on the keystroke path, so it stays hand written and the check holds it to the list, which is the 130 words that are keywords, literals or functions.

The check runs the other way for the tree-sitter grammar as well, since every keyword the grammar spells has to be a word the list knows, a word the grammar parses and nothing colours being one that comes out plain in an editor. The reverse is not required, and that asymmetry is the point: the list also holds the words the parser refuses by name, `CREATE` where it is not a catalog statement and `SESSION`, which are coloured everywhere and parsed nowhere, because an error is easier to believe when the word looked like a word.

That half of the check needs a grammar to check, and the grammar is somewhere else, so `cargo xtask grammar` looks for a checkout of it at `$ZU_TREE_SITTER` and then at a sibling directory called `tree-sitter-gql`, does the shell and the site either way, and prints which halves it did rather than passing quietly on two of three. A variable that points at nothing is an error rather than a skip, because a job that set it meant to check something. Where that always happens is the grammar's own CI, which checks this repository out and runs this command against its own tree, so a word added here and not carried across turns the grammar's build red rather than this one. This repository's grammar job checks the grammar out for the same reason from the other side, and it tracks main rather than a pin, since a grammar pinned to a zu nobody runs is the failure the job exists to catch.

What holds the grammars to the engine is the conformance corpus of §7, which is 1021 statements the engine answers and the one body of zuQL written without either grammar in mind. `cargo xtask grammar --queries` writes them out as files through the engine's own reader, so neither grammar parses a YAML file or keeps a second copy of a statement. The 994 the engine accepts have to parse with no error node in the tree, the 27 it answers with a syntax error have to fail to parse, and the highlight query is compiled over every one of them, so a node renamed in `grammar.js` fails there rather than in somebody's editor. Two of the 27 parse anyway and both are decisions written down beside the check: `CAST(1 AS NOPE)` names a type nobody has, which is a table the binder holds rather than a shape a grammar can see, and the empty statement is what an editor opens with. That check moved with the grammar and runs in its repository, against a checkout of this one.

The TextMate grammar is a list of regular expressions rather than a grammar, so it cannot tell a type from a variable of the same name and does not try; what it has is the word lists and the shapes that are unambiguous on their own, which is what a code block on a page needs. `grammar/shiki/check.mjs` loads it the way the site does and checks it twice: 16 statements where the traps are, a keyword inside a string being a string and a type name standing where a value stands being a variable, and then every one of the 13178 scoped pieces of the corpus, which is what caught a rule that painted any word before a quoted string as a temporal type and so made `RETURN 'x'` a type.

The grammar's `src` is committed there, so it builds without the tree-sitter CLI, which is what an editor package or a Neovim install needs, and its CI regenerates it and fails if the committed files move, so the C is derived rather than maintained. Alongside it, `tree-sitter test` holds 59 hand written trees, which is where a statement whose shape is wrong shows up as a wrong tree rather than as a parse that merely succeeded. The word list against the tree costs 0.08 ms and the per-word cost is flat as the list grows, which `cargo bench -p xtask --bench grammar` asserts; the Shiki check wants node, so it is `make grammar` and a CI job of its own rather than part of `make lint`.

## 10. The pinned toolchain table

Nine repositories build one release out of one set of versions, and the question "which Rust do we build against" stops having one answer the moment it is written in nine workflows: one is bumped, the others are not, and the bug that follows is found by a user on the platform nobody bumped.

`toolchains.toml` at the root of this repository is that table. A row is a component, the version it is pinned to, the oldest version still promised, the repositories that build against it, and a sentence saying why the numbers are what they are. A pin is exact, because "the newest 1.97" is a range and a range is how two machines end up building different things. A floor is a promise rather than a fact, and the conformance matrix runs the floor as well as the pin, because a library that only ever builds against the newest release finds out its floor is broken from a bug report. The table records the date it was audited against the registries.

A component this repository builds against says where its version is written, in a `[[site]]` naming the file, the key, whether the site holds the pin or the floor, and whether it has to say the version exactly or name the series it is in. Exact is what `rust-toolchain.toml` and a workflow say, since those name a release to install. A series is what a cargo requirement of `59` says against `59.2.0`, since writing the patch level in a manifest is a lockfile in the wrong file.

`cargo xtask pins` checks it in both directions, which is the shape the API map already has. Forward: every site exists, holds the key it claims, and agrees with the version. Backward: every `toolchain:` a workflow pins is one the table names, so a job added next month cannot quietly introduce a tenth answer, and a component this repository builds against with no site is reported, since a row nothing holds is a row nobody maintains. It runs as a test on all three platforms of the matrix and as a command in CI, the second because a command nothing exercises is a command that rots.

The whole table against the whole tree is under a millisecond, because a site is one scan of the file it names and there are as many scans as sites. `cargo bench -p xtask --bench pins` asserts that shape rather than the number, the per-site cost staying flat as the table grows, since the way a check like this dies is the accidental square that costs nothing at six sites and is unaffordable at two hundred.

Bumping a version is therefore a pull request that touches this table and every site of it together, which is the entire point of writing it down.

What installs a pinned toolchain in a job is `.github/actions/rust`, a local composite action that runs three rustup commands, and it is local for two reasons. The first is the moving reference: the action it replaced was used at `@master`, a mutable branch of somebody else's repository, in every job of a repository that pins nine languages' toolchains to the patch level and writes down why. The second is where an action is fetched from. Every action a job uses is downloaded from codeload.github.com before the job's first step, so a workflow is only as available as that host, and when it answers 429 or 503 the job dies in `Set up job`, which is before any step exists to rerun or to mark as allowed to fail. That happened through the GitHub incident of 2026-08-17 and cost most of a day's checks across three pull requests. Neither reason is a complaint about the action, which is a good one; both are arguments for three rustup commands in the tree. It also installs rustup itself where there is none, which is what the manylinux rows need, since that image carries a compiler for somebody else's ecosystem and not this one. A job asks for a channel or for a version: a channel is what the format check and the fuzzer want, whatever it is today, and `cargo xtask pins` holds versions and leaves channels alone, because there is no version written down to hold. A floating nightly is the one case that falls back, walking back a fortnight of dated nightlies when the newest is missing a component, which is how miri goes missing for a day or two at a time.

## 11. The platform table and the libzu matrix

Seven targets are tier 1: linux x86_64 and aarch64 against glibc, the same two against musl, both Macs, and Windows on x86_64. Tier 1 means a prebuilt binary for every SDK, a full matrix per release, and a release that stops when one of them fails, which is a promise worth exactly what CI proves of it. So all seven build on every pull request rather than for the first time on the day of a release.

`platforms.toml` is the table, and it is the tiers of dx/14 §2 as data rather than as a paragraph nine repositories each read differently. A row is a target, its tier, the runner that is that machine, the image it builds in where that matters, what the three artifacts are called there, and whether the runner can run what it built. Three, because a platform builds three: the shared library a package manager installs, the static archive a binding links into itself so that its own users install one file, and the CLI. dx/09 C-5 ships both library forms and they are not the same promise, so a table that named one of them would be a release that quietly shipped one of them. `cargo xtask platforms` holds `.github/workflows/libzu.yml` to it in both directions: a tier-1 target the matrix does not build is a promise nothing keeps, and a matrix row for a target the table does not have is a platform being shipped by nobody's decision. The check runs as a test, so it fires on the machine of whoever edited one of the two files.

The glibc floor is 2.28, which is manylinux_2_28 and covers RHEL 8 and everything newer, so the two gnu rows build inside that image rather than against the runner's own glibc. A library linked against a newer glibc loads on the machine that built it and dies on the user's, which arrives as a bug report saying the install is broken. The musl rows are what makes a container work, and they are built inside Alpine rather than on the runner: a musl shared library links musl's libc and the unwinder beside it, which an Ubuntu machine does not have, so the row would fail to link here long before it failed to load there. Building where the artifact runs also makes the smoke test the real one. Rows a hosted runner cannot run at all, freebsd and riscv64, are recorded as tier 2 with no runner rather than left out, since the table is the promise and the promise is smaller there.

Every row that can run what it built runs a C program whose only knowledge of zu is `zu.h`, compiled by a compiler that is not rustc and linked against the package that job staged. The Rust test in `zu-capi` calls the same functions and proves something else, because it links the rlib the compiler had in hand: the artifact test is the one that fails when a symbol is not exported, when the header and the library disagree about a type, or when the build for a platform picked up the wrong libc. It builds a configuration and checks its size against the header's, opens a database, connects twice, counts the nodes through each connection, closes the database and keeps querying, walks a column chunk by chunk and checks the chunks add up to it, reads an empty column back as `ZU_DONE`, takes a refusal apart into its code and severity, and asks a statement to run after its connection has closed, so the struct layout and the failing paths cross the boundary too.

What it links against is an install prefix rather than a pile of files, and `cargo xtask package --stage` builds it: `include/zu.h`, `lib/` holding both library forms, `bin/` holding the CLI, `lib/pkgconfig/libzu.pc`, `lib/cmake/zu/` holding the package config and its version file, the export list in each linker's syntax beside them, and the license. The layout is the requirement rather than a preference, because pkg-config resolves everything from `${pcfiledir}` and `find_package` from `CMAKE_CURRENT_LIST_DIR`, so a flat directory of the same files is two build systems that find nothing. It is a command with tests on it rather than a heredoc in the workflow, since seven platform jobs spelling one layout is seven chances to spell it differently, and the command CI runs is then the command anybody can run here.

`libzu.pc` and `zu-config.cmake` both offer the two library forms, and the thing a generated file is most likely to be quietly wrong about is what a static link needs beside the archive. That list is asked of rustc, `--print native-static-libs`, rather than written down, because it differs per target and moves with the toolchain, and a `Libs.private` that is a guess is a `pkg-config --static` line that does not link. `zu-config-version.cmake` is stricter than CMake's same-major default: compatible means the same major and the same minor, because before 1.0 a minor bump is where a break is allowed to go, and this ABI is additive-only only from its DX5 freeze.

The export list is generated from the header and shipped rather than passed to our own link, which is worth saying because the requirement reads like the opposite. rustc already narrows a cdylib to its `no_mangle` set on all three formats, with an anonymous version script on ELF and an exported-symbols list on Mach-O, and handing it a named version script on top fails the link outright. Who needs the list is the consumer who links `libzu.a` into a shared library of their own, whose linker exports everything it was given unless told otherwise: that is the collision that makes two plugins embedding one copy of a native library unusable in one process (dx/02 §9). So `lib/zu.map`, `lib/zu.exports` and `lib/zu.def` ship for them, and the build script runs `nm` over what was actually produced, since a symbol that leaked is a fact about the library on disk and no amount of checking the source will see it.

`cargo xtask package` with nothing to stage is the source half of that: every function `zu.h` declares is defined in `zu-capi` and every function `zu-capi` exports is declared in `zu.h`, both directions, refusing an exported function that is not `extern "C"` and a name exported twice. It runs as a test, so a function added to one file and not the other fails on the machine of whoever added it rather than in a platform job twenty minutes later. Between the two, a smoke row links the same C program four ways, against the shared library, against the archive, through `pkg-config` and through `find_package(zu)`, because a package can be wrong in four places and each one is a different user's first five minutes.

The same table carries the size ceilings of dx/14 §4, and `cargo xtask platforms --measure` weighs what a build produced against them on every platform. Binary size is a real adoption factor for serverless and mobile targets and it only ever drifts upward, so it is a number with a limit rather than a graph somebody looks at once a quarter. Today `libzu` is 2.6 MiB against a ceiling of 14 and the CLI is 10.8 against 15, most of the difference between them being the Arrow reader §13 explains why the shipped CLI carries and the shipped library does not. The shared library is what is gated because it is what a user installs, and the archive is not, since it is object files and a consumer's linker takes the ones their calls reach. A file the build did not produce is an error rather than a zero, since a missing artifact is otherwise the cheapest way to pass a size gate.

## 12. The release-artifact contract

A release is a tag on this repository and a run that drives the eight others (dx/14 §6). Every one of them builds against what this one published, which makes the list of what gets published a contract rather than a step in a workflow. A binding that fetches `model.json` for the version it pins and finds nothing cannot tell a release that dropped the artifact from a version that never had it, and the failure surfaces in somebody else's CI a day later, which is the worst place for it.

`artifacts.toml` is that list, and the release workflow has none of its own: it assembles from the table and reads the directory back against it. A row is a name, where it comes from, the repositories that fetch it, and a sentence saying why they do. There are five ways a row comes to exist, because there are five ways an artifact does. A `file` is a path this tree already holds, `zu.h` and `model.json` being the two. A `corpus` is packed by the packer of §7. A `platform` row is one artifact per tier-1 target, expanded against `platforms.toml`, so the seven move with that table rather than with this one. A `sums` row is `SHA256SUMS`, the digest of every other file of the release, written last because it is over the rest of them and read first by anything that installs from them. And a `later` row is an artifact the contract names that nothing makes yet, carrying the milestone that will make it: `cli.json` with D1, `gql.json` and `errors.json` with D2. Naming those early is the point rather than an oversight, since a consumer needs to know what a release will eventually carry and the alternative is eight repositories each guessing.

The digests are recomputed by `--verify` rather than read, which is the only version of that check worth having: a list the release wrote and then trusted proves that the file was hashed once, not that the file beside it now is that file. So a rebuilt artifact copied in after the list was written fails the release that would have published it, and a published file with no line in the list fails too, since an installer cannot check it and this one refuses to install what it cannot check. The hasher is a hundred lines in `xtask` rather than a dependency, for the same reason the tar writer is: a build tool that pulls a crate in to hash ten files has added a supply chain to the thing whose whole job is to be the trusted end of one. It runs at about 230 MiB/s on a laptop, so the digests of a whole release cost under a second.

`cargo xtask artifacts --assemble` gathers a release into a directory and `--verify` reads it back, in both directions like every other table here: an artifact the contract publishes and the directory does not hold is a consumer's failure tomorrow, and a file in the release that no row accounts for is something somebody will fetch that nothing promises. The check that runs on every pull request is the third direction, holding the table to the tree and to the workflow: a `file` row whose file has moved, and a release workflow that does not assemble from the table, which is what would turn the table back into a document. Who the consumers are is checked by §14, because the list of repositories is one list and this is not where it lives. Assembling a release of ten files takes about as long as compressing them, and the bookkeeping either side of it is a hundredth of a millisecond.

A platform's build stages an install prefix into a directory named for the target, and that directory is the artifact: `libzu-<target>.tar.zst` unpacks to something a build system can be pointed at rather than to four levels of somebody's build path. Both archives are written by the same tar writer, reproducibly, so two mirrors of one release can be compared rather than trusted. Reproducible means every header field that could carry the packing machine's clock, user id or umask is fixed, and the permission bits are decided from the name for the same reason: the CLI in `bin/` and the shared library beside it unpack executable and everything else does not, which is otherwise the install one-liner failing at its last step.

`.github/workflows/release.yml` is the train of dx/14 §6 with its publish steps as no-ops. What is real is the build, which is the same matrix every pull request runs, the assemble, and the verify. What prints instead of running is the publishing, in the order it will happen: crates.io before the repositories that build against it, and the Go tag last of the registries because pushing a tag is the one publish that cannot be taken back. A rehearsal runs on `workflow_dispatch` with a version rather than a tag, because a release train is exactly the machinery that must not run for the first time on the day of a release.

## 13. The install one-liners

dx/12 §6 asks for five ways in, and they are five because the way a person installs a database is the way they already install everything else. `install.sh` and `install.ps1` are the ones a page can print in a box; Homebrew and Scoop are the ones a machine already has; and the container is the one a CI file names. All five land the same thing: the platform archive of §12, unpacked as the install prefix it is, so a user who installed the CLI on Monday has the header, both library forms, the pkg-config file and the CMake package config on Wednesday when they compile against it. An install that gave out only the binary is a second download later, which is a second version to keep straight.

Every one of them checks the digest before it unpacks anything, which is why `SHA256SUMS` is fetched first and why it is a row of the contract rather than a step in the installer. A `curl | sh` that pipes an unverified download into a shell is the install story every audit stops at, and the answer is not to stop offering the one-liner but to make it the thing being verified. The shell script refuses to continue when no hasher exists rather than skipping the check, because an installer that verifies where it can is an installer that did not verify on the machine where it mattered. The formula and the manifest carry the same numbers out of the same file, so `brew install` and `scoop install` check what the script checks.

The two scripts are hand written and the two manifests are not. A script that detects a platform is a script: `uname -m` and `uname -s` map to a triple, and on Linux the libc is the part `uname` cannot answer, so `ldd --version` and the loader on disk decide between the gnu and musl rows, which is the difference between a binary that runs and one that dies at its first dynamic symbol. A Homebrew formula, by contrast, is four URLs and four digests, all of which `platforms.toml` and the release already know, so `cargo xtask packaging` renders both manifests and `--check` holds the committed copies to the tables. A hand maintained formula is the file that still installs the previous version three days after a release. The committed copies carry a digest of sixty-four zeros, since the release that fills them in has not happened when they are written, and that placeholder is a well-formed digest of the wrong value on purpose: a manifest published by mistake fails at the checksum and installs nothing.

The check also runs the other way, and that is the half worth having: every tier-1 target has to be carried by some channel. Homebrew takes macOS and glibc Linux, Scoop takes Windows, the container takes musl, and the scripts take everything, so an eighth platform added to `platforms.toml` arrives with a way in rather than as a build nobody can install the easy way. The container builds from source on Alpine so the link is musl's and the binary needs no loader at all, which is what lets somebody copy it into a distroless stage of their own, and its compiler is pinned out of `toolchains.toml` like every other compiler here.

What cannot be unit tested is tested end to end: the suite builds a release directory holding a real archive and a real digest list, points `ZU_BASE` at it over `file://`, and runs the script. The case with no `--target` is the one that matters, because the archive is named for the platform this build is for, so a script that read `uname` differently asks for a file that is not there. Beside it are the failures that have to stay failures: an archive whose digest does not match installs nothing, an archive with no line in the list is refused rather than installed unchecked, and a platform the release does not publish gets that sentence rather than the fetcher's opinion of a 404.

That suite fakes the program, though. The `bin/zu` inside its archive is four lines of sh that echo a version, which is the right trade for a test that runs on every commit and proves the downloading rather than the download. What proves the rest is the platform matrix: every tier 1 row that can run its own binaries assembles a release of its own platform out of the package it just staged, by the same contract and the same tar writer a real release uses and at a compression level nobody waits two minutes for, pipes `install.sh` into `sh` with `ZU_BASE` pointing at it, and then does the first thing a user came to do, which is convert an edge list to Parquet, load it and print `zu stat`. Piped rather than run as a file, because that is the invocation with a failure mode of its own: a script read from standard input cannot read from standard input, and an installer that prompted would work perfectly every way but the one it is published as. The target is not passed either, so the fetch is the check on the platform detection: name the machine wrongly and the release has no such archive, which is the error that user would have got.

Windows installs from a step of its own rather than from the same script, since its installer is PowerShell and driving PowerShell from bash would test neither. It runs under Windows PowerShell 5.1, which is the floor `install.ps1` claims and a claim only the shell in the box can settle, and it is piped through `Invoke-Expression` for the same reason the other one is piped through `sh`. The one thing that script gained for this is a fetch that reads `file:` itself: `Invoke-WebRequest` is a FileWebRequest on Windows PowerShell and an HttpClient on PowerShell 7, and the newer one has no such scheme, so an installer that took a mirrored release from a share would work on one of the two shells.

The Parquet step is why the shipped CLI is built with the Arrow feature compiled in. Without it `zu copy edges.parquet` answers `rebuild with --features arrow`, which is a fair answer from a `cargo install` and a broken promise from a one-liner whose whole claim is that a user with a Parquet file is three commands from a database. It is the CLI's feature and not the library's: the C ABI loads columns a caller already holds in memory, so a Parquet reader behind it would be weight every embedder pays and nobody calls. That costs the CLI about 5.7 MiB, inside the ceiling of §11, and costs the shared library nothing at all, since nothing in it reaches that code and the linker can see so. The library does carry the other half of Arrow, being the arrays and the schema `zu_result_arrow` writes, which §4 weighs at 421 KiB; reading a file and handing over a result are different appetites and only the second one is every embedder's.

Unpacking is where the platforms disagree, and the fallback is the half worth exercising. `tar --zstd` wants GNU tar 1.31, the manylinux image is RHEL 8 and ships 1.30, and busybox tar on Alpine reads no compression it was not built with, so four of the seven rows take the `zstd -dc` path instead of the first choice. They take it because that is what a user on those images does, which is also why `zstd` is installed into both containers rather than the archive being packed as something older tar can read.

## 14. The repository table and the conductor

The split of ADR 0005 put eight repositories outside this one, and a split is a decision made once: after it, the list of what was split out is a thing every part of the project quotes. The release train dispatches to it, the README publishes it to everybody arriving through a package manager, and the artifact contract of §12 names its consumers from it. Three copies of one list is how a repository ends up on the train and off the README, which is a release publishing to a registry that no page tells anybody about.

`repos.toml` is the list. A row is a name, what the repository is to the train, its support tier, the milestone it appears at, the workflow the train dispatches there, and what it reports back. The last column is the one that makes the collect step of dx/14 §6 checkable rather than aspirational: a release collects scorecards, map completeness in both directions, perf and sizes, and which repository owes which is written down before any of them can quietly owe nothing. The roles are the reason a row can be checked at all: the engine is the one repository the train does not dispatch to, because the train is its own tag, and the site is the one without a tier, because a tier is a promise about an SDK.

`cargo xtask repos` holds three files to it, each in both directions. The conductor's matrix, so a repository the table drives and nothing dispatches to is caught along with a dispatch to a repository nobody decided to drive. The README's client table, including the tier column, since the tier is the promise a user reads before they depend on something. And the artifact contract's consumers, since a consumer that is not a repository is a fetch nobody will ever make and a repository that fetches nothing is either a gap in the contract or a repository that should not have been split out. Nine rows will not be nine forever, so the cost of holding all three is measured per repository and is about two microseconds of it.

`.github/workflows/conductor.yml` is the dispatching half of the train, and every dispatch in it is a no-op, because none of the eight has a release workflow to dispatch to until DX1 through DX5. What is real is the shape, which is the expensive part to get wrong late: two stages, the seven bindings and the kit first and the site after them, because a site deployed against a release whose wheels failed their corpus run documents something nobody can install. Each dispatch collects a file per report it owes, every one of them saying `pending`, and the collect step prints the eight repositories and their thirty-one empty results. When the dispatches become real, the gate is already there and the only change is what the files say.

## 15. The client table and the scorecard

A tier is a promise, and dx/01 §5 is the observation that a promise with nobody's name on it is a commitment nobody made. A user deciding whether to depend on the Go client wants three things before anything else: who answers for it, where it lives, and what tier 1 actually means. `clients.toml` is those three, and `cargo xtask clients` renders them to `/docs/clients/overview`, which is the page that answers the question rather than a paragraph in a README that answers a different one.

A scorecard has three axes. Surface is how much of the API model the client names, out of what its tier owes, which the map completeness check of §6 measures per release. Conformance is how much of the cross-client corpus it passes, which the corpus runner measures per release. Neither is a column in the table, and that is the point: a number a person types is a number nobody measured, so both arrive through the reports of §14 and are collected by the conductor. Practice is the third, and it is the half that can be checked today, because every item in it is a thing a client repository either has or does not and no release changes the answer. The README's programs run as printed, a generated reference, the language's own shapes, conditions carrying their code and doc URL, the misuse suite of dx/15 §4, sanitizer and leak jobs, the clean-machine install test, the stability gate of dx/15 §6, an api-map, and published benchmark numbers. Ten items weighing a hundred between them, refused at parse time if they weigh anything else, since a score out of a number that moves is not a score.

An item can name the report that makes it apply, and a client is scored out of the weight that applies to it rather than out of a hundred. That is not a loophole, it is the difference between a scorecard and a checklist: zu-c has no api-map because the C names are `zu.h` and `zu.h` is generated here, so scoring it against a map it is right not to have would mark a correct decision wrong. The thresholds come from dx/15 §8, where a tier 1 release is 100/100/>=90, which leaves room for one ten point item to be missing and none for two, and each lower tier is refused at parse time if it promises more than the tier above it.

The table is held to `repos.toml` in both directions, since that is already where the split and the tiers are. A repository owing a scorecard with no row here is a client the release collects a scorecard from and nothing defines one for; a row here for a repository owing no scorecard is a scorecard nothing collects; and a tier written twice is a client that can be tier 1 on one page and tier 2 on another. The maintainer is refused unless it is a person and a handle, because a name with nobody reachable behind it is the half that does not help somebody with a question.

`cargo xtask clients` writes the page and then checks the tree, so a page rendered from a table that disagrees with the split cannot be committed, and `--check` does the same without writing, which is what CI runs. The thresholds are behind `--gate` rather than on by default, and that is deliberate: every client is under its threshold until the apparatus of DX3 through DX5 exists, and a check that is red for two milestones is a check somebody turns off. The gate is the release's run and DX6's, which is where the promise has to hold. What the page publishes in the meantime is the standing, with what is missing named rather than counted, because a number nobody can act on is a number nobody reads.

## 16. What the clients are measured against

A scorecard says whether a client has the apparatus. It does not say whether the client is good, and the only honest way to answer that is to put it beside the one everybody already uses. `docs/clients/duckdb.md` is that measurement for the Python and TypeScript clients against DuckDB's, run rather than argued, and it is where the performance work on both of them comes from.

Its finding is one sentence long. We are twenty times faster on a point read and eleven times faster registering somebody else's columns, three times faster reading a result as rows, and twenty times slower turning one into Arrow, and all four of those numbers have the same cause: `QueryResult` is `Vec<Vec<Value>>`, so the row path starts where it wants to be and every columnar path has to transpose back out of it. `crates/zu-vector` is already a vector layer of the right shape, down to a `StrView` that is Arrow's `Utf8View` byte for byte, and the executor already works in it. What is missing is a result that keeps the vectors rather than a sink that flattens them, which is the same thing §4 says about the C ABI's chunked reads being a slice of what was already materialized.

The answer to it starts at `zu::query::column`, which is a result read down its columns rather than across its rows: one contiguous buffer per column in the layout Arrow already uses, a validity bitmap that is absent when nothing is null, and strings as bytes and offsets. `QueryResult::columnar` fills it in two passes over the rows in row order, one to settle each column's type and one to fill each column's buffer, which is where the twenty went: a client used to walk the whole result once per column to infer and again per column per batch to gather, so a three column result was six strided passes and this is two sequential ones. A column of nodes, rels, paths, lists or records still arrives as values, borrowed rather than copied, because no buffer describes them and nobody exports a million of them.

It lives in the engine and not in a binding for one reason. The transpose is a transpose only until the sink stops flattening: `crates/zu-vector` is what the executor already computes in, [`SinkState`] is the one place the vectors die, and when that changes `columnar` hands back the buffers the executor filled and no client changes a line. A binding that had written the transpose for itself would have to be rewritten instead.

That is what happened, and it left one copy behind. The sink fills the buffers now, so `columnar` hands them over rather than transposing anything, but it hands them over borrowed: the result stays readable afterwards, and a buffer that leaves through a borrow has to be copied because the one behind it stays where it is. So an export of a half million row column was a memcpy of the whole answer, every time, purely because the caller was allowed to ask twice. `QueryResult::into_columns` is the other half of that bargain and `zu_arrow::Table::taken` is what calls it: the result is consumed, its buffers are moved into the Arrow arrays, and an export costs a pointer a column and nothing at all per row. Measured on a half million row integer column it is 0.375 ms borrowed against 0.001 ms taken, and the gap widens with the answer, because one of those two numbers grows with it and the other does not. A result the sink built across its rows instead has no buffers to move and is handed back untouched, so the borrowing path is still there and is still what a caller who wants to read the result again should use. It reaches everybody: the ADBC driver takes its result, so the Python, R, Java, Go and C++ programs that arrive through a driver manager are zero copy without knowing it, and `zu_result_arrow` in §4 is the same move over the C ABI, which is how a client that links the shared library gets it too.
