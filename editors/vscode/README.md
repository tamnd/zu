# zu for VS Code

zuQL in the editor: diagnostics as you type, completion against the tables in your database, hover, formatting and colour.

Everything here comes from the `zu` binary. The extension starts `zu lsp --stdio` and gets out of the way, which is deliberate: a language server shipped separately from the engine drifts from it, and the day it drifts is the day it tells you a table exists that does not. The completion list comes out of the catalog the shell reads, the diagnostics come out of the front end that would refuse the statement, and there is one answer to every question because there is one implementation of it.

## Installing

The extension needs the `zu` binary. It looks in three places, in this order:

1. `zu.server.path`, if you set it.
2. The binary bundled in the extension, which is what a marketplace install has.
3. `zu` on your `PATH`, which is what `cargo install zu-cli` or a package manager leaves.

If none of those is there the extension says so once, with a button to the setting, and stops. It does not keep trying.

## Pointing it at a database

`zu.database` is the `.zu1` file the server answers about, and it is the whole difference between an editor that knows the language and one that knows your file.

Without it you get syntax errors and keywords, which is everything that can be said about text with no catalog behind it. With it you get the table names, the labels and the properties in completion, hover that says how many nodes a table has, and diagnostics from the binder as well as the parser, so an unknown function or an undefined variable is a squiggle rather than a surprise at run time.

The status bar on the right says which database is attached. Click it to pick another, or `zu: Select Database` from the command palette. A relative path is from the workspace folder, and `~` is your home directory.

The file is opened read only. An editor is a reader, and a server holding the write side would lock the file you are about to open a shell on.

## Commands

- `zu: Select Database` picks the `.zu1` file to answer about, or none.
- `zu: Restart Language Server` starts it again, which you want after replacing the binary under it.

## Settings

- `zu.server.path`: the binary to run. Empty means bundled, then `PATH`.
- `zu.database`: the `.zu1` file to answer about. Empty means no database.
- `zu.trace.server`: `off`, `messages` or `verbose`, logged to the zu output channel.

## What is in this directory

`src/extension.js` starts the server and owns the status bar. `src/server.js` is the part that is a decision rather than a call into the editor: it takes the settings, the platform and a way to ask whether a file exists, and answers with a command line, so the tests in `test/` check it under plain node with no editor running.

`syntaxes/gql.tmLanguage.json` is generated by `cargo xtask grammar` from `grammar/vocabulary.toml`, along with the copy the documentation site uses, and CI fails if either drifts from the word list. It is here because a file is coloured the moment it opens and the server takes a moment to start. Once the server is up, the semantic tokens it sends are what you are looking at.
